## Contexto

A **Fintech Core** é uma conta digital que está saindo do papel. Neste primeiro marco, o objetivo é uma API funcional em memória, com um contrato bem definido, para o time do aplicativo começar a integrar.

## O contrato

Todos os erros seguem Problem Details com `type` = `https://fintech.dev/problemas/<slug>`.

| Requisição | Sucesso | Erros |
|---|---|---|
| `POST /contas` | `201` + `Location` + conta | `400` `dados-invalidos` / `requisicao-malformada` · `409` `conta-duplicada` |
| `GET /contas/{id}` | `200` + conta | `404` `conta-nao-encontrada` · `400` id não é UUID |
| `GET /contas?cpf=&pagina=&tamanho=` | `200` + página | `400` (tamanho de 1 a 100) |
| `POST /contas/{id}/depositos` | `200` + conta atualizada | `400` · `404` |
| `POST /contas/{id}/saques` | `200` + conta atualizada | `400` · `404` · `422` `saldo-insuficiente` (+ `saldoDisponivel`) |
| `GET /contas/{id}/extrato` | `200` + extrato | `404` |
| `GET /v3/api-docs` | `200` + especificação OpenAPI com todos os caminhos acima | |

**Abertura**: `{"titular": "Ana Souza", "cpf": "52998224725", "tipo": "CORRENTE"}` (`tipo`: `CORRENTE` ou `POUPANCA`).

**Conta**:

```json
{
  "id": "0f8b1c2e-6a4d-4f53-9a57-3c1e2b7d9a10",
  "titular": "Ana Souza",
  "cpf": "***.982.247-**",
  "tipo": "CORRENTE",
  "saldo": 0.00,
  "criadaEm": "2026-09-28T13:00:00Z"
}
```

**Movimentação**: `{"valor": 150.50}`. **Extrato**:

```json
{
  "contaId": "0f8b1c2e-...",
  "saldo": 100.25,
  "movimentos": [
    {"tipo": "DEPOSITO", "valor": 150.50, "saldoApos": 150.50, "dataHora": "2026-09-28T13:01:00Z"},
    {"tipo": "SAQUE", "valor": 50.25, "saldoApos": 100.25, "dataHora": "2026-09-28T13:02:00Z"}
  ]
}
```

**Página**: `{"itens": [...], "pagina": 0, "tamanho": 20, "totalItens": 2, "totalPaginas": 1}`, em ordem de abertura.

## Regras de negócio

1. `id` é um **UUID** gerado pelo servidor.
2. Titular obrigatório (até 120 caracteres); CPF válido (11 dígitos) e **sempre mascarado** nas respostas.
3. Uma pessoa (CPF) pode ter **no máximo uma conta de cada tipo**.
4. Valores de movimentação: obrigatórios, **positivos**, com no máximo **2 casas decimais**.
5. O saldo **nunca** fica negativo.
6. O extrato lista os movimentos em ordem cronológica, com o saldo após cada um.
7. **Concorrência**: 50 depósitos simultâneos de R$ 10,00 na mesma conta resultam em exatamente R$ 500,00 e 50 movimentos.

## Organização sugerida

O `LEIA-ME.md` do starter sugere os pacotes `api`, `aplicacao`, `dominio` e `infra`. **No marco 3 essa organização vira obrigatória** (verificada com ArchUnit), então vale começar assim:

- **dominio**: `Conta` (protege o saldo), `Cpf` (value object), `Movimento`, as exceções de negócio e a **interface** `RepositorioDeContas`;
- **aplicacao**: `ServicoDeContas` (casos de uso);
- **infra**: `RepositorioDeContasEmMemoria` (no marco 2, JPA), configuração (`Clock`, OpenAPI);
- **api**: controller, DTOs, `TratadorDeErros`.

### Decisões de design

- **A interface do repositório mora no domínio** (uma "porta", no vocabulário da arquitetura hexagonal do módulo 13). O serviço depende dela, não da implementação. No marco 2, trocar memória por JPA será escrever outra classe em `infra`.
- **`Conta` protege as próprias regras**: não existe `setSaldo`. O único jeito de mudar o saldo é `depositar`/`sacar`, que validam e registram o movimento. Isso é o oposto de um "modelo anêmico".
- **`Cpf` como value object**: se existe, é válido; e o `toString()` mascarado evita vazar CPF num log descuidado.
- **UUID como id**: não revela quantas contas existem e não permite adivinhar `id + 1`.
- **`Clock` injetado**: datas de abertura e de movimentos ficam testáveis.
- **`synchronized` agora, banco depois**: em memória, a trava da própria conta resolve a concorrência. Com várias instâncias da aplicação (e dados no banco), essa responsabilidade passa para o banco — o assunto do marco 2.
