## Contexto

A rede de clínicas do exercício 07.01 vai ganhar um aplicativo, e o aplicativo precisa de uma API. Você vai construir o recurso **pacientes**: cadastro, consulta, busca por nome, atualização e remoção.

O time de segurança deixou duas exigências: nenhum dado de entrada pode chegar ao sistema sem validação, e o **CPF nunca sai inteiro** nas respostas (LGPD — princípio da necessidade).

Os testes são **caixa-preta**: só enviam requisições HTTP e leem o JSON. Você é livre para organizar as classes como quiser dentro do pacote `dev.trilhajava.m08.pacientes`.

## A API

| Requisição | Sucesso | Erros |
|---|---|---|
| `POST /pacientes` | `201` + `Location: /pacientes/{id}` + paciente | `400` inválido · `409` CPF já cadastrado |
| `GET /pacientes/{id}` | `200` + paciente | `404` |
| `GET /pacientes?nome=&pagina=&tamanho=` | `200` + página | `400` paginação inválida |
| `PUT /pacientes/{id}` | `200` + paciente | `400` · `404` · `409` CPF de **outro** paciente |
| `DELETE /pacientes/{id}` | `204` | `404` |

**Entrada** (POST e PUT):

```json
{"nome": "Ana Souza", "cpf": "52998224725", "email": "ana@email.com", "nascimento": "1990-05-10"}
```

**Saída**:

```json
{"id": 1, "nome": "Ana Souza", "cpf": "***.982.247-**", "email": "ana@email.com", "nascimento": "1990-05-10"}
```

**Página**:

```json
{"itens": [ ... ], "pagina": 0, "tamanho": 20, "totalItens": 3, "totalPaginas": 1}
```

## Regras

| Campo | Regra |
|---|---|
| `nome` | obrigatório, até 120 caracteres |
| `cpf` | obrigatório, **11 dígitos sem máscara**, dígitos verificadores válidos, não pode ter todos os dígitos iguais — valide com uma anotação **`@CpfValido`** criada por você |
| `email` | opcional; se vier, formato válido |
| `nascimento` | obrigatório, no passado |

- JSON malformado → `400`.
- Listagem: `nome` filtra por "contém", **sem diferenciar maiúsculas**; ordem alfabética por nome (também sem diferenciar maiúsculas); `pagina` ≥ 0 (padrão 0); `tamanho` entre 1 e 50 (padrão 20).
- CPF mascarado na saída: `***.` + dígitos 4 a 6 + `.` + dígitos 7 a 9 + `-**`.
- O armazenamento é **em memória**, mas precisa ser correto com requisições simultâneas (é um bean singleton).

## Desafios opcionais

- Acrescente `PATCH /pacientes/{id}` para alterar só o e-mail. Qual a diferença de semântica para o `PUT`?
- Implemente paginação por **cursor**: `GET /pacientes?depoisDe=17&tamanho=20`.
- Faça a busca por nome ignorar acentos (`"joao"` encontra `"João"`). Dica: `java.text.Normalizer`.

<Dica nivel={3}>
A anotação própria:

```java
@Constraint(validatedBy = ValidadorDeCpf.class)
@Target({FIELD, PARAMETER, RECORD_COMPONENT})
@Retention(RUNTIME)
public @interface CpfValido {
    String message() default "CPF inválido";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

O `ValidadorDeCpf implements ConstraintValidator<CpfValido, String>` devolve `true` para `null` (o `@NotBlank` cuida da presença) e reaproveita o cálculo dos dígitos do exercício 01.
</Dica>

### Por que assim

- **Controller fino**: traduz HTTP em chamadas ao serviço e devolve DTOs. Status e headers ficam aqui; regras, no serviço.
- **Um DTO de entrada para POST e PUT**: as regras de validação são as mesmas. O `id` vem do caminho, nunca do corpo — o cliente não escolhe o id.
- **`PacienteResposta.de(...)`**: a conversão num só lugar garante que o CPF **sempre** sai mascarado, inclusive na listagem.
- **`synchronized` em `cadastrar` e `atualizar`**: sem ele, duas requisições simultâneas com o mesmo CPF passariam na verificação. Com banco de dados, a garantia real é a constraint `UNIQUE` do módulo 07 — e a exceção de violação vira o 409.
- **Validação de parâmetros sem código**: `@Min`/`@Max` nos `@RequestParam` são aplicados pelo Spring MVC 6.1+ e viram 400 automaticamente.

- O que acontece se o cliente mandar `"id": 999` no corpo do POST?
