## Regras

- **Sem `LIMIT 1` por cidade** nem subconsulta correlacionada na q1: use uma window function.
- Na q3, o primeiro mês não tem anterior, e a variação deve ser `NULL` (não `0`: "não sei" é diferente de "não mudou").
- Na q4, gere o calendário com **CTE recursiva**. `generate_series` existe no PostgreSQL, mas não no banco dos testes; e a CTE recursiva é portátil e cai em entrevista.

### Por que assim

- **q1: `RANK` e não `ROW_NUMBER`.** O enunciado pede todos os empatados. Com `ROW_NUMBER`, um deles sumiria de forma arbitrária, e o resultado mudaria de uma execução para outra.
- **q1: por que não `MAX`?** `MAX(total)` por cidade diz **quanto** foi o maior total, mas não **quem**. Para trazer o nome, você teria de juntar de volta com a tabela, e aí os empates dão trabalho. A janela resolve de uma vez.
- **q2: janela sobre agregação.** O `GROUP BY` roda primeiro; depois a window function percorre as linhas já agrupadas. Por isso `SUM(SUM(x)) OVER (...)` é válido: o `SUM` de dentro é do grupo, o de fora é da janela.
- **q3: `NULL` honesto.** `COALESCE(LAG(...), 0)` faria janeiro parecer "estável", quando na verdade não há mês anterior para comparar.
- **q4: gerar o que não existe.** Uma tabela de fatos só tem os dias **com** evento. Para achar ausências, é preciso um conjunto completo (o calendário) e um anti-join contra os fatos.

### Performance: SQL × Java

As quatro consultas devolvem poucas linhas, independentemente do tamanho da base. O rascunho em Java trafegava todos os pedidos pela rede e os segurava na memória. **Agregue no banco e traga o resultado**, e use o Java para regras de negócio que o SQL expressa mal.
