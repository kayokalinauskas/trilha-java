## Contexto

Uma rede de clínicas guarda tudo em planilhas. Já apareceram pacientes com o mesmo CPF cadastrados duas vezes, consultas de 5 minutos, valores negativos lançados por engano e — o pior — dois pacientes marcados com o mesmo médico no mesmo horário, porque duas recepcionistas agendaram ao mesmo tempo. Você vai criar o esquema do novo sistema de um jeito que o **banco** recuse esses dados, não importa quem tente gravá-los.

## Onde escrever

Edite o arquivo `java/m07-sql/starter/src/main/resources/sql/0701/schema.sql`. O teste executa o script num banco H2 em **modo PostgreSQL**, insere dados válidos e inválidos e confere se o banco aceita ou rejeita cada um. Use SQL padrão do PostgreSQL: a solução também foi verificada num PostgreSQL 18 de verdade.

## Requisitos

Os nomes de tabelas e colunas abaixo são **obrigatórios** (o teste depende deles). Todas as tabelas têm `id` gerado automaticamente.

| Tabela | Colunas e regras |
|---|---|
| `paciente` | `cpf`: 11 caracteres, obrigatório e único · `nome`: obrigatório · `nascimento` (data): obrigatório · `email`: **opcional**, mas único quando informado |
| `medico` | `crm`: obrigatório e único · `nome`: obrigatório · `especialidade`: obrigatória |
| `consulta` | `paciente_id` e `medico_id`: obrigatórios, referenciam as tabelas acima · `inicio` (data e hora): obrigatório · `duracao_min`: entre **15 e 120** · `status`: só `AGENDADA`, `REALIZADA` ou `CANCELADA`, padrão **`AGENDADA`** · `valor`: dinheiro, **nunca negativo** |

## Regras de negócio que o banco deve garantir

1. Um médico **não pode ter duas consultas com o mesmo horário de início** — mesmo que duas pessoas agendem no mesmo segundo.
2. Uma consulta não pode apontar para paciente ou médico inexistente.
3. **Não é permitido apagar** um paciente que tem consultas: o histórico médico precisa ser preservado.
4. Vários pacientes podem ficar sem e-mail.

## Exemplos

```sql
INSERT INTO consulta (paciente_id, medico_id, inicio, duracao_min, valor)
VALUES (1, 1, TIMESTAMP '2026-10-01 09:00:00', 30, 250.00);   -- ok, status = AGENDADA

-- cada um destes deve FALHAR:
INSERT INTO consulta (...) VALUES (1, 1, TIMESTAMP '2026-10-01 09:00:00', 30, 100);  -- mesmo médico e horário
INSERT INTO consulta (...) VALUES (1, 1, TIMESTAMP '2026-10-02 09:00:00', 10, 100);  -- 10 minutos
INSERT INTO consulta (...) VALUES (1, 1, TIMESTAMP '2026-10-03 09:00:00', 30, -1);   -- valor negativo
DELETE FROM paciente WHERE id = 1;                                                    -- tem consultas
```

## Critérios de aceite

- [ ] Todos os testes de `ModelagemClinicaTest` passam.
- [ ] O dinheiro usa `NUMERIC`, nunca ponto flutuante.
- [ ] As constraints importantes têm **nome** (ex.: `uk_consulta_medico_inicio`).
- [ ] Existe um índice para buscar as consultas de um paciente.

## Desafios opcionais

- Rode o script num PostgreSQL de verdade: `docker run --rm -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:18` e conecte com o IntelliJ ou o `psql`.
- A regra 1 só impede o **mesmo início**. Uma consulta às 9h00 de 60 minutos e outra às 9h30 ainda se sobrepõem. Pesquise a **exclusion constraint** do PostgreSQL (`EXCLUDE USING gist` com `tsrange`) e resolva isso de verdade.
- Faça o DER (diagrama entidade-relacionamento) do esquema no [dbdiagram.io](https://dbdiagram.io) ou no IntelliJ.

<Dicas>
<Dica nivel={1}>
Cada regra da tabela vira uma constraint: "obrigatório" → `NOT NULL`, "único" → `UNIQUE`, "entre 15 e 120" e "só estes valores" → `CHECK`, "referencia" → `REFERENCES`. O padrão do status é um `DEFAULT`.
</Dica>
<Dica nivel={2}>
A regra "mesmo médico, mesmo horário" é um `UNIQUE` **composto**: `CONSTRAINT uk_consulta_medico_inicio UNIQUE (medico_id, inicio)`. Para "não apagar paciente com consultas", você não precisa fazer nada além da FK: o comportamento padrão já impede a exclusão. O que **não** pode é colocar `ON DELETE CASCADE`.
</Dica>
<Dica nivel={3}>
Para o id: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. Para o CPF: `cpf CHAR(11) NOT NULL UNIQUE CHECK (LENGTH(cpf) = 11)`. Um `UNIQUE` em `email` sem `NOT NULL` já permite vários pacientes sem e-mail, porque `NULL` não é igual a `NULL`.
</Dica>

### Por que assim

- **Regras no banco, não só na aplicação.** A validação no Java continua útil para dar mensagens amigáveis, mas scripts, outros sistemas e bugs não passam por ela. As constraints valem para qualquer um que escreva.
- **`UNIQUE (medico_id, inicio)` resolve a concorrência.** Um `SELECT` para ver se o horário está livre, seguido de um `INSERT`, é *check-then-act*: duas recepcionistas passariam juntas. A constraint faz o banco rejeitar a segunda, sempre.
- **FK sem `CASCADE`.** Histórico médico não pode sumir porque alguém apagou um cadastro. Se o paciente pedir para ser removido (LGPD), o caminho é **anonimizar** os dados pessoais, não apagar as consultas.
- **`NUMERIC(10, 2)`** para o valor: exato, como o `BigDecimal` do Java.
- **`TIMESTAMP` sem fuso** aqui é uma escolha consciente: consulta é "hora de parede" da clínica, que funciona num único fuso. Um sistema com clínicas em fusos diferentes usaria `TIMESTAMPTZ`.
- **Índice em `consulta(paciente_id)`**: o PostgreSQL não cria índice para FKs, e "consultas do paciente" é a busca mais comum dessa tela.

### Avalie sua solução

- Suas constraints têm nomes que ajudariam a entender um erro em produção?
- O que acontece no seu esquema se alguém tentar gravar `status = 'agendada'` (minúsculo)? Isso é o comportamento que você quer?
- Você usou `SERIAL`? Funciona, mas `GENERATED ... AS IDENTITY` é o padrão SQL atual.
