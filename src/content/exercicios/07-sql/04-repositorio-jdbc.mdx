## Contexto

Uma fintech pequena começou com um "repositório" que montava SQL concatenando strings e fazia a transferência em dois comandos soltos, com autocommit ligado. Em uma semana, apareceram: um cliente chamado `Robert'); DROP TABLE conta; --` no formulário de cadastro, transferências que debitavam a origem e não creditavam o destino (quando a conta de destino não existia) e saldos negativos em transferências simultâneas.

Antes de passar para o Spring e o JPA (módulos 08 e 09), você vai reescrever esse repositório com **JDBC puro**, para entender exatamente o que essas ferramentas fazem por você.

## O esquema (pronto, criado pelo teste)

```sql
CREATE TABLE conta (
    id      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    titular VARCHAR(120) NOT NULL,
    saldo   NUMERIC(12,2) NOT NULL CHECK (saldo >= 0)
);
CREATE TABLE movimento (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    conta_id  BIGINT NOT NULL REFERENCES conta(id),
    valor     NUMERIC(12,2) NOT NULL,          -- positivo = crédito, negativo = débito
    descricao VARCHAR(200) NOT NULL
);
```

`Movimento` (record), `SaldoInsuficienteException` e `ContaNaoEncontradaException` já estão prontos. Você implementa `RepositorioDeContas`, que recebe um `DataSource` no construtor.

## Requisitos

| Método | Comportamento |
|---|---|
| `abrir(titular, saldoInicial)` | Insere a conta e devolve o **id gerado pelo banco** |
| `saldo(contaId)` | `Optional` com o saldo; vazio se a conta não existe |
| `movimentos(contaId)` | Movimentos da conta, **na ordem em que foram gravados** |
| `transferir(origem, destino, valor)` | Debita, credita e grava um movimento em cada conta — **tudo ou nada** |

## Regras da transferência

1. `valor` precisa ser **positivo**, e origem e destino, **diferentes**. Caso contrário, `IllegalArgumentException`.
2. Saldo insuficiente → `SaldoInsuficienteException`, e **nada muda**.
3. Conta de origem ou destino inexistente → `ContaNaoEncontradaException`, e **nada muda** (inclusive o débito que já tinha sido feito).
4. Descrições dos movimentos: `"Transferência enviada para a conta {destino}"` (valor negativo, na origem) e `"Transferência recebida da conta {origem}"` (valor positivo, no destino).
5. A verificação de saldo e o débito não podem ser dois passos separados (*check-then-act*).

## Regras gerais

- **Sempre** `PreparedStatement` com `?`. Nenhum valor concatenado no SQL.
- **Sempre** try-with-resources para `Connection`, `PreparedStatement` e `ResultSet`.
- `SQLException` vira `IllegalStateException` (unchecked), **com a causa preservada**.

## Critérios de aceite

- [ ] Todos os testes de `RepositorioDeContasTest` passam.
- [ ] O titular malicioso é gravado literalmente e a tabela continua existindo.
- [ ] Todos os comandos da transferência usam **a mesma conexão**.
- [ ] Existe `rollback()` para qualquer exceção depois do `setAutoCommit(false)`.

## Desafios opcionais

- Rode duas transferências simultâneas da mesma conta com saldo para só uma delas (use o `CountDownLatch` do módulo 06) e confirme que uma falha com `SaldoInsuficienteException`.
- Conecte o repositório num PostgreSQL real via Docker e o `PGSimpleDataSource` do driver oficial.
- Adicione **idempotência**: `transferir` recebe uma chave (`UUID`); se a mesma chave chegar duas vezes, a segunda não faz nada. Qual constraint resolve isso?

Os três métodos de leitura e o `abrir` seguem o mesmo molde: `try (Connection c = ...; PreparedStatement ps = ...)`, `ps.setXxx(índice, valor)` (os índices começam em **1**), executar e ler o `ResultSet`. <Dica nivel={2}>
Na transferência, abra **uma** conexão, chame `setAutoCommit(false)` e envolva todo o trabalho num `try/catch` que chama `c.rollback()` e relança a exceção. O `commit()` é a última linha do `try`. Faça as validações do valor e das contas **antes** de abrir a conexão.
</Dica>
<Dica nivel={3}>
Débito sem *check-then-act*: `UPDATE conta SET saldo = saldo - ? WHERE id = ? AND saldo >= ?`. O `executeUpdate()` devolve o número de linhas afetadas: `0` significa "conta não existe **ou** saldo insuficiente". Para diferenciar, consulte a conta na mesma conexão. No crédito, `0` linhas significa destino inexistente: lance a exceção e deixe o `catch` fazer o rollback do débito.
</Dica>

### Por que assim

- **`PreparedStatement` em tudo.** O SQL vai ao banco com `?`, e os valores vão separados. O nome `Robert'); DROP TABLE conta; --` é só um texto estranho gravado na coluna, nunca um comando.
- **Débito condicional e atômico.** `WHERE id = ? AND saldo >= ?` verifica e debita num único comando, com a linha travada. Duas transferências simultâneas não conseguem, as duas, ver saldo suficiente. E o `CHECK (saldo >= 0)` fica como última defesa.
- **Uma conexão, uma transação.** Com `setAutoCommit(false)`, nada é definitivo até o `commit()`. Se o crédito falha porque o destino não existe, o `rollback()` desfaz o débito. É a atomicidade do ACID aplicada.
- **Por que a ordem débito → crédito?** Debitar primeiro valida o saldo cedo e evita creditar dinheiro que não existe. Com a transação, a ordem não muda o resultado final, mas muda o que dá errado primeiro, e a mensagem de erro fica mais útil.
- **`catch (RuntimeException | SQLException e)`** cobre tanto as exceções de negócio (que você mesmo lança) quanto as do banco. Um `catch (SQLException)` sozinho deixaria o `ContaNaoEncontradaException` passar **sem rollback**, e a conexão voltaria ao pool com uma transação aberta.
- **Exceções unchecked com causa.** `new IllegalStateException("...", e)` mantém o stack trace original para o log. O Spring faz a mesma tradução, para a hierarquia `DataAccessException`.

### O que o Spring vai fazer por você

| Aqui, na mão | No módulo 09 |
|---|---|
| `getConnection()`, try-with-resources | `JdbcTemplate` / repositórios do Spring Data |
| `setAutoCommit(false)`, `commit`, `rollback` | `@Transactional` |
| passar a mesma `Connection` para todos os métodos | a conexão é ligada à thread pela transação |
| `SQLException` → `IllegalStateException` | tradução automática para `DataAccessException` |
