## Contexto

A rede de bibliotecas municipais vai expor uma API para o app de empréstimos. O time de front-end fez um pedido claro: **"quando algo der errado, precisamos de um código de erro estável para mostrar a mensagem certa"**. Hoje, o sistema lança `RuntimeException("erro")` para tudo, e o app mostra "Algo deu errado" até para "você já tem 3 livros emprestados".

Além disso, o acervo é carregado de um CSV enviado pela equipe de catalogação, e um arquivo com uma linha quebrada já deixou o acervo **pela metade** em produção.

## Requisitos

### Hierarquia de exceções

| Exceção | Código | Quando |
|---|---|---|
| `BibliotecaException` (abstrata) | — | Superclasse de todas as falhas de negócio; expõe `codigo()` |
| `LivroNaoEncontradoException` | `LIVRO_NAO_ENCONTRADO` | ISBN não existe no acervo |
| `LivroIndisponivelException` | `LIVRO_INDISPONIVEL` | Todos os exemplares emprestados |
| `LimiteEmprestimosException` | `LIMITE_EMPRESTIMOS` | Usuário já tem 3 empréstimos ativos |
| `UsuarioComAtrasoException` | `USUARIO_COM_ATRASO` | Usuário tem empréstimo vencido |
| `EmprestimoNaoEncontradoException` | `EMPRESTIMO_NAO_ENCONTRADO` | Devolução de empréstimo inexistente ou já devolvido |
| `ArquivoAcervoInvalidoException` | — (checked) | Problema no arquivo de importação; expõe `linha()` |

### Regras de empréstimo (`Biblioteca`)

- Prazo: **14 dias**. Limite: **3** empréstimos ativos por usuário.
- Ordem das verificações em `emprestar`: livro existe → usuário sem atraso → limite → exemplar disponível.
- Uma tentativa recusada **não altera nada** (nem estoque, nem empréstimos).
- `devolver` devolve a **multa**: R$ 2,00 por dia de atraso, com teto de R$ 50,00.

### Importação (`ImportadorAcervo`)

Formato: `isbn;titulo;exemplares`, com cabeçalho na primeira linha e linhas em branco ignoradas.

- **Tudo ou nada:** se qualquer linha for inválida, **nenhum** livro é cadastrado.
- A mensagem de erro indica a linha: `"Linha 3: esperadas 3 colunas..."`, e `linha()` devolve 3.
- `exemplares` não numérico: a `NumberFormatException` original é a **causa**.
- `importar(Path)` abre o arquivo com **try-with-resources**; um `IOException` vira `ArquivoAcervoInvalidoException` **com a causa preservada**.

## Critérios de aceite

- [ ] Todos os testes de `BibliotecaTest` passam.

- [ ] As mensagens incluem o contexto (ISBN, usuário, limite).
- [ ] Nenhum `catch` vazio e nenhuma exceção relançada sem a causa.

## Desafios opcionais

- **Fila de espera:** quando o livro estiver indisponível, o usuário entra em uma fila (`Deque`) e é notificado na devolução.
- **Relatório de importação** com **todos** os erros do arquivo, e não só o primeiro. Pense em como a exceção carregaria uma lista de problemas.

### Decisões de design

- **Unchecked para negócio, checked para arquivo.** Um livro indisponível é tratado no topo da aplicação (a API converte o código em uma resposta HTTP 409 ou 422). Já um arquivo inválido é uma situação esperada, em que quem chama tem uma ação clara: avisar o operador e pedir um arquivo corrigido. O compilador obrigar esse tratamento é uma vantagem.
- **Validar tudo, depois mudar o estado.** Em `emprestar`, nenhum mapa é alterado antes de todas as regras passarem. No importador, a lista `linhas` é preenchida e validada por completo antes do primeiro `cadastrar`. É o mesmo princípio de atomicidade do exercício 02.01, e o mesmo que transações de banco garantem no módulo 09.
- **Tradução de exceções.** `IOException` e `NumberFormatException` nunca escapam do importador: viram `ArquivoAcervoInvalidoException` com a **linha** e a **causa**. Quem usa o importador só precisa conhecer uma exceção.
- **`catch (NumberFormatException)` antes de `catch (IllegalArgumentException)`.** A primeira é subclasse da segunda. Com a ordem invertida, o código nem compila.
