Na aula anterior, o Redis apareceu como cache. Ele é mais que isso: é um **servidor de estruturas de dados em memória**. Contadores, filas, rankings, conjuntos e locks, todos acessíveis pela rede, compartilhados entre as instâncias da sua aplicação, e com operações **atômicas**.

É por isso que ele aparece em quase toda entrevista de system design. E é por isso que vale conhecer os limites: o Redis é ótimo para estado compartilhado de curta duração, e perigoso quando tratado como banco de dados principal ou como fonte de verdade para exclusão mútua.

## As estruturas

| Estrutura | Comandos típicos | Uso no backend |
|---|---|---|
| **string** | `GET`, `SET`, `INCR`, `SET ... EX` | cache de JSON, contadores, flags, locks |
| **hash** | `HSET`, `HGET`, `HINCRBY` | um objeto com campos (sessão, carrinho) |
| **list** | `LPUSH`, `RPOP`, `LRANGE` | fila simples, últimos N itens |
| **set** | `SADD`, `SISMEMBER`, `SINTER` | conjuntos sem repetição (tags, quem já votou) |
| **sorted set** | `ZADD`, `ZRANGE`, `ZREMRANGEBYSCORE` | ranking, janela deslizante por tempo, agendamento |
| **stream** | `XADD`, `XREADGROUP`, `XACK` | log de eventos com grupos de consumidores |

Toda chave pode ter **expiração**: `SET sessao:abc ... EX 1800`, ou `EXPIRE chave 60` depois. `TTL chave` mostra quanto falta. Chaves expiradas somem sozinhas, o que torna o Redis natural para dados temporários.

## Atomicidade: o que faz o Redis ser útil

O Redis executa os comandos **um de cada vez**, num único fluxo de execução (há threads para E/S de rede, mas os comandos em si não se intercalam). Consequências:

- **`INCR` é atômico.** Dez instâncias incrementando o mesmo contador nunca perdem uma contagem, sem lock nenhum.
- **`SET chave valor NX PX 30000`** grava **só se não existir** (`NX`) e expira em 30 s (`PX`). Em um comando: é a base de locks e de deduplicação ("já processei esta requisição?").
- Um comando lento (um `KEYS *` numa base grande) **bloqueia todos os outros**. Use `SCAN` para varrer chaves.

Para combinar comandos, há três ferramentas diferentes:

| | O que faz | Atômico? |
|---|---|---|
| **pipeline** | envia vários comandos de uma vez e lê as respostas no final | não: só economiza idas à rede |
| **`MULTI` / `EXEC`** | enfileira comandos e os executa juntos, sem intercalar | sim, mas **sem rollback** se um falhar |
| **script Lua** (`EVAL`) | lógica com `if` executada no servidor | sim; o servidor fica ocupado enquanto roda, então mantenha curto |

## Rate limit distribuído

No módulo 11, o rate limit por IP morava na memória de cada instância. Com três instâncias, cada uma tinha o seu balde. Com o Redis, o contador é um só. A versão mais simples é a **janela fixa**: um contador por cliente por minuto.

```java
@Component
public class LimitadorDeRequisicoes {

    // INCR e PEXPIRE no mesmo script: se a instância cair entre os dois,
    // não sobra uma chave sem expiração bloqueando o cliente para sempre
    private static final RedisScript<Long> INCREMENTAR = RedisScript.of("""
            local atual = redis.call('INCR', KEYS[1])
            if atual == 1 then
              redis.call('PEXPIRE', KEYS[1], ARGV[1])
            end
            return atual""", Long.class);

    private static final long LIMITE_POR_MINUTO = 100;

    private final StringRedisTemplate redis;

    public LimitadorDeRequisicoes(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public boolean permitir(String cliente) {
        long minuto = Instant.now().getEpochSecond() / 60;
        String chave = "limite:" + cliente + ":" + minuto;
        Long usos = redis.execute(INCREMENTAR, List.of(chave), "60000");
        return usos != null && usos <= LIMITE_POR_MINUTO;
    }
}
```

A janela fixa deixa passar até o dobro do limite na virada do minuto (100 no fim de um, 100 no começo do outro). Se isso importa, use uma **janela deslizante** com sorted set (cada requisição é um membro com o horário como *score*; `ZREMRANGEBYSCORE` remove as antigas e `ZCARD` conta) ou um token bucket, como o do Bucket4j com backend Redis.

## Lock distribuído, e por que desconfiar dele

Duas instâncias rodam o mesmo job agendado; só uma deveria processar o fechamento do dia. O lock no Redis:

```java
public Optional<String> tentarTravar(String recurso, Duration validade) {
    String dono = UUID.randomUUID().toString();   // identifica QUEM travou
    Boolean travou = redis.opsForValue().setIfAbsent("lock:" + recurso, dono, validade);
    return Boolean.TRUE.equals(travou) ? Optional.of(dono) : Optional.empty();
}

private static final RedisScript<Long> LIBERAR = RedisScript.of("""
        if redis.call('GET', KEYS[1]) == ARGV[1] then
          return redis.call('DEL', KEYS[1])
        end
        return 0""", Long.class);

public void liberar(String recurso, String dono) {
    redis.execute(LIBERAR, List.of("lock:" + recurso), dono);   // só apaga se ainda for o dono
}
```

O valor aleatório e o script de liberação evitam um bug clássico: o lock do processo A expira, B adquire, e A, ao terminar, apaga o lock **de B**.

Mas há um problema mais fundo. O lock **expira**, e um processo não sabe quando está pausado. Uma pausa de GC, uma VM congelada ou um pacote atrasado podem fazer o lock vencer enquanto o dono ainda acha que o tem:

Martin Kleppmann analisou esse problema no texto *How to do distributed locking* (2016), uma crítica ao **Redlock**, o algoritmo proposto pelo criador do Redis para locks sobre vários nós independentes. O argumento central: um lock baseado em tempo não garante exclusão mútua diante de pausas e relógios imprecisos; para **correção**, o recurso protegido precisa verificar um **fencing token**, um número que cresce a cada aquisição. Nem o `SET NX PX` nem o Redlock geram esse número: ele precisa vir de algo com ordem garantida (uma sequência do banco, por exemplo), e o recurso precisa saber verificá-lo. O criador do Redis, Salvatore Sanfilippo, publicou uma resposta (*Is Redlock safe?*), e o debate é leitura recomendada.

A conclusão prática:

- Lock no Redis para **eficiência** (evitar trabalho duplicado, em que rodar duas vezes custa só processamento): ótimo.
- Lock para **correção** (dois processos escrevendo quebram o dado): o recurso precisa se defender. Um `UPDATE ... WHERE versao = ?` (lock otimista, módulo 9), uma constraint única ou um fencing token resolvem; o lock sozinho, não.

## Outros usos

- **Sessões.** O Spring Session com Redis guarda a sessão HTTP fora da instância: qualquer instância atende qualquer usuário.
- **Filas leves com streams.** `XADD` acrescenta, `XREADGROUP` distribui entre consumidores de um grupo, `XACK` confirma. Mensagens não confirmadas ficam numa lista de pendentes e podem ser reassumidas (`XAUTOCLAIM`). Serve para volumes moderados; para retenção longa, reprocessamento e alto volume, o Kafka (módulo 12) é a ferramenta.
- **Deduplicação.** `SET processado:<id> 1 NX EX 86400` responde "já vi esta mensagem?" numa operação.

## Persistência, memória e o que o Redis não é

O Redis guarda tudo em memória, e pode persistir em disco de dois jeitos:

| | RDB | AOF |
|---|---|---|
| Como | fotografia periódica da base | registro de cada escrita |
| Perda numa queda | tudo desde a última fotografia | com `appendfsync everysec`, cerca de 1 s |
| Restaurar | rápido | mais lento (replica as escritas) |

Os dois podem ser usados juntos. Mesmo assim, o Redis **não é, por padrão, um banco primário**: a replicação é assíncrona (uma falha do primário pode perder as últimas escritas) e o volume de dados é limitado pela memória. Trate o que está nele como algo que pode ser reconstruído.

<Callout tipo="erro" titulo="Redis como cache sem política de memória">
A política padrão de memória cheia (`maxmemory-policy`) é `noeviction`: ao atingir o limite, as **escritas falham**. Para um Redis usado como cache, configure `maxmemory` e uma política como `allkeys-lru` ou `allkeys-lfu`, para que as chaves menos usadas sejam descartadas.
</Callout>

<Callout tipo="novidade" titulo="A licença do Redis e o Valkey">
Em 2024, o Redis deixou a licença BSD e passou a licenças de código disponível (RSALv2 e SSPLv1). Em resposta, a Linux Foundation criou o **Valkey**, um fork a partir do Redis 7.2, com licença BSD. Em 2025, o **Redis 8** voltou a oferecer uma opção open source, a **AGPLv3**. Para o código da aplicação, os dois falam o mesmo protocolo nos comandos desta aula; a escolha costuma ser do time de plataforma ou do provedor de nuvem. Confira a licença vigente na documentação oficial antes de decidir.
</Callout>

## Spring Data Redis

O `spring-boot-starter-data-redis` configura o cliente **Lettuce** (o padrão) e os templates:

- `StringRedisTemplate`: chaves e valores como `String`; você serializa o JSON. É o mais previsível.
- `RedisTemplate` com serializadores configurados, para objetos.
- `opsForValue()`, `opsForHash()`, `opsForZSet()`, `opsForStream()`: uma API por estrutura.
- `execute(RedisScript, chaves, argumentos)` para Lua; `executePipelined(...)` para pipelines.

Nos testes, o Testcontainers sobe um Redis real (módulo 10), com `@ServiceConnection`.

<Callout tipo="dica" titulo="Redis Cluster e chaves relacionadas">
No Redis Cluster, as chaves são distribuídas em 16384 *hash slots*. Comandos com várias chaves (e scripts Lua) só funcionam se todas estiverem no mesmo slot. Use *hash tags*: só o trecho entre chaves entra no cálculo, então `carrinho:{usuario-42}` e `sessao:{usuario-42}` caem no mesmo slot.
</Callout>

<Callout tipo="entrevista">
"Como você faria um rate limit com várias instâncias?" ou "Como garantir que só uma instância rode o job?"

- O Redis é estado compartilhado de curta duração, não banco primário.
</Callout>

## Resumo

- Redis: estruturas em memória compartilhadas (string, hash, list, set, sorted set, stream), com **expiração** por chave.
- Comandos executam **um de cada vez**: `INCR` e `SET NX PX` são atômicos; comandos lentos bloqueiam todos.
- Pipeline economiza rede; `MULTI`/`EXEC` não intercala; **Lua** dá lógica condicional atômica.
- Rate limit: contador + expiração no mesmo script; janela deslizante com sorted set.
- Lock com `SET NX PX` serve para **eficiência**; para **correção**, **fencing token** ou verificação no recurso.
- RDB e AOF reduzem a perda, mas o Redis não é banco primário por padrão; configure `maxmemory-policy` num cache.
- Licença: Redis 8 com opção AGPLv3; o fork **Valkey** existe. Spring Data Redis usa o **Lettuce**.
