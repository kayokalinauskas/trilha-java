## Git em 10 minutos

O Git registra a **história** do seu código em *commits*: fotografias do projeto em um momento, cada uma com autor, data e mensagem. Com isso você pode voltar no tempo, entender por que algo mudou e trabalhar em paralelo com outras pessoas sem que um sobrescreva o trabalho do outro.

### O ciclo do dia a dia

```bash
git status                       # o que mudou? (rode o tempo todo)
git switch -c feat/saudacao      # cria uma branch e muda para ela
# ... edita arquivos ...
git add src/main/java/.../Saudacao.java
git commit -m "feat: implementa saudação com capitalização"
git push -u origin feat/saudacao # envia a branch para o remoto
```

Depois do `push`, no GitHub ou GitLab, você abre um **Pull Request** (ou *Merge Request*): um pedido para outra pessoa revisar e juntar sua branch na `main`. Em qualquer empresa, **nenhum código vai para a `main` sem revisão**.

### Boas mensagens de commit

O mercado adota amplamente o padrão **Conventional Commits**:

| Prefixo | Quando usar | Exemplo |
|---|---|---|
| `feat:` | Nova funcionalidade | `feat: adiciona cálculo de frete expresso` |
| `fix:` | Correção de bug | `fix: evita NPE quando o nome é nulo` |
| `test:` | Só testes | `test: cobre saque acima do limite` |
| `refactor:` | Mudança interna sem alterar comportamento | `refactor: extrai método capitalizar` |
| `docs:` | Documentação | `docs: explica como rodar os testes` |

## O que é um teste automatizado

Um teste automatizado é **código que verifica outro código**. Em vez de rodar o programa e conferir o resultado "no olho", você escreve uma vez o que espera e deixa o computador conferir sempre que quiser — em segundos.

Veja um teste real do exercício 00.01:

```java title="SaudacaoTest.java"
class SaudacaoTest {

    @Test
    @DisplayName("cumprimenta a pessoa pelo nome")
    void cumprimentaPeloNome() {
        // Arrange (preparar) + Act (executar)
        String resultado = Saudacao.para("Ana");

        // Assert (verificar)
        assertThat(resultado).isEqualTo("Olá, Ana!");
    }
}
```

- **`@Test`** marca o método como teste para o **JUnit**, o framework de testes padrão do Java (a trilha usa o JUnit 6).
- **`@DisplayName`** dá um nome legível, que aparece no relatório.
- **`assertThat(...).isEqualTo(...)`** vem do **AssertJ**, uma biblioteca de asserções fluentes. Se o valor for diferente, o teste falha e mostra os dois valores.

A estrutura **Arrange → Act → Assert** (preparar, executar, verificar) é o esqueleto de praticamente todo teste bem escrito.

### Testes parametrizados

Quando a mesma regra vale para várias entradas, você não copia o teste. Você o **parametriza**:

```java
@ParameterizedTest(name = "nome inválido [{0}] vira visitante")
@NullAndEmptySource
@ValueSource(strings = {"   ", "\t"})
void semNome(String nome) {
    assertThat(Saudacao.para(nome)).isEqualTo("Olá, visitante!");
}
```

O JUnit roda esse método **quatro vezes**: com `null`, `""`, `"   "` e `"\t"`.

## Rodando os testes com Maven

Na pasta de um starter:

```bash
cd java/m00-comece-aqui/starter
mvn test
```

Sem implementação nenhuma, a saída termina com algo assim:

```text
[ERROR] Tests run: 7, Failures: 0, Errors: 7, Skipped: 0
[ERROR] cumprimentaPeloNome  <<< ERROR!
java.lang.UnsupportedOperationException: Implemente Saudacao.para
    at dev.trilhajava.m00.Saudacao.para(Saudacao.java:23)
[INFO] BUILD FAILURE
```

Como ler:

- **`Tests run: 7`** — quantos testes rodaram.
- **`Failures`** — asserções que não bateram (o código rodou, mas o resultado estava errado).
- **`Errors`** — exceções inesperadas (o código nem chegou ao fim). Aqui, é o `UnsupportedOperationException` do stub.
- **O *stack trace*** diz **onde** o problema aconteceu: `Saudacao.java:23`. Sempre procure a primeira linha que aponta para o **seu** código.

Para rodar só uma classe de teste, use `-Dtest`:

```bash
mvn test -Dtest=SaudacaoTest
```

## Vermelho → verde → refatorar

Todo exercício da trilha segue este ritmo, que vem do **TDD** (*Test-Driven Development*):

1. 🔴 **Vermelho:** rode os testes e veja-os falhar. Isso prova que o teste consegue detectar o problema.
2. 🟢 **Verde:** escreva o código **mais simples** que faz o teste passar.
3. 🔵 **Refatorar:** melhore nomes, extraia métodos e remova duplicação — com a garantia de que os testes continuam verdes.

<Callout tipo="entrevista">
"Você escreve testes?" é pergunta certa em qualquer entrevista. Mais forte do que dizer "sim" é descrever **como**: "uso JUnit e AssertJ, organizo em Arrange-Act-Assert, uso testes parametrizados para variações da mesma regra e rodo tudo no CI a cada push". Você vai conseguir dizer isso com propriedade ao final do módulo 10.
</Callout>

## Resumo

- Git: `status` → `add` → `commit` → `push`, sempre em branches, com revisão via Pull Request.
- Um teste JUnit segue **Arrange → Act → Assert**. O AssertJ deixa as verificações legíveis.
- `mvn test -Dtest=Classe` roda os testes de um exercício. *Failures* são resultados errados; *errors* são exceções.
- Ritmo da trilha: **vermelho → verde → refatorar**.
