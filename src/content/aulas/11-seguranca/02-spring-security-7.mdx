  - frente: Qual o papel do DelegatingFilterProxy e do FilterChainProxy?
    verso: O DelegatingFilterProxy é o filtro de servlet que o Spring Boot registra no Tomcat (ordem -100, nome springSecurityFilterChain); ele só repassa a requisição ao bean FilterChainProxy. O FilterChainProxy escolhe a PRIMEIRA SecurityFilterChain cujo matcher casa com a requisição e executa os filtros dela.
  - frente: Por que duas SecurityFilterChain sem securityMatcher impedem a aplicação de subir?
    verso: A primeira casaria com qualquer requisição e a segunda nunca seria usada. O Spring Security detecta isso na subida e lança UnreachableFilterChainException. A cadeia "pega-tudo" precisa ser única e a última (@Order maior).
  - frente: Onde fica o usuário autenticado durante a requisição?
    verso: Num Authentication (nome, autoridades) dentro do SecurityContext, acessado pelo SecurityContextHolder, que por padrão usa uma variável da thread. Entre requisições, quem guarda e recupera o contexto é o SecurityContextRepository (sessão HTTP, por exemplo); numa API stateless, nada é guardado.
  - frente: Quem confere usuário e senha no Spring Security?
    verso: O filtro (ex. BasicAuthenticationFilter) monta um pedido e chama o AuthenticationManager. A implementação padrão, ProviderManager, delega ao DaoAuthenticationProvider, que carrega o usuário pelo UserDetailsService e compara a senha com o PasswordEncoder.
  - frente: Quando é seguro desligar a proteção CSRF?
    verso: Quando nenhuma credencial vai sozinha pelo navegador. Com token no header Authorization, sim. Com cookie de sessão (aplicação web, BFF, SPA com cookie), não; numa SPA, use csrf.spa() no Spring Security 7.
  - frente: Por que 401 e 403 não passam pelo @RestControllerAdvice?
    verso: Eles nascem nos filtros, antes do DispatcherServlet. O ExceptionTranslationFilter chama o AuthenticationEntryPoint (401) ou o AccessDeniedHandler (403); é neles que se escreve o Problem Details.

    verso: hasRole acrescenta o prefixo ROLE_ e procura ROLE_ADMIN; hasAuthority procura o texto exato. Passar "ROLE_ADMIN" para hasRole faz a aplicação falhar na subida.
  - frente: O que @WithMockUser e jwt() NÃO testam?
    verso: A autenticação. Eles colocam um Authentication pronto no contexto e pulam a verificação de senha ou de token. Testam só a autorização; a autenticação precisa de testes com credenciais reais (httpBasic, tokens válidos e inválidos).

Uma clínica tem dois tipos de cliente falando com o mesmo backend. A recepção usa um aplicativo que marca consultas pela API, mandando a credencial em cada requisição. A equipe administrativa usa um painel web no navegador, com login, sessão e formulários. Um dia alguém pede um ajuste simples: "adicione um filtro que registre quem acessou cada consulta, para a auditoria da LGPD". O filtro entra, os testes passam, e duas semanas depois a auditoria descobre que **todas as negativas de acesso aparecem no log como `status=200`**. Em outro projeto, uma pessoa copia a configuração da API para o painel, a aplicação para de subir com uma exceção de dez linhas, e o time perde a tarde tentando entender o que é `UnreachableFilterChainException`.

Nos dois casos, o código estava "certo". O que faltava era o modelo mental de **onde** o Spring Security roda, **em que ordem** as coisas acontecem e **quem** decide cada resposta. Esta aula constrói esse modelo com uma API real: duas cadeias de filtros na mesma aplicação, um filtro de auditoria posicionado com precisão, respostas 401 e 403 no padrão Problem Details e uma matriz de acesso testada linha por linha. No caminho, você vai ver as mensagens de erro reais que aparecem quando cada peça sai do lugar.

## A intuição: a portaria de um hospital

Pense na entrada de um hospital grande. Logo na porta da rua há uma **recepção geral** que não decide nada: ela só olha para onde a pessoa vai e a encaminha para a **portaria certa**. Quem vai ao ambulatório passa por uma portaria rápida: mostra o crachá a cada entrada, ninguém guarda nome, e quem não tem crachá recebe um "identifique-se". Quem vai à área administrativa passa por outra portaria: ali se faz cadastro uma vez, recebe-se uma pulseira válida pelo dia e os formulários assinados precisam de um carimbo que só a pulseira dá.

Cada portaria é uma sequência de guichês, sempre na mesma ordem: conferir documento, registrar a entrada, verificar se a pessoa pode entrar naquela ala. Se o guichê de documentos barra alguém, os seguintes nem ficam sabendo. E o médico lá dentro (o controller) só vê quem passou por tudo.

O Spring Security é exatamente isso. A recepção geral é o `FilterChainProxy`. Cada portaria é uma `SecurityFilterChain`. Os guichês são filtros de servlet. O crachá mostrado a cada vez é o HTTP Basic (ou um token, na próxima aula), a pulseira do dia é a sessão, e o carimbo dos formulários é o token CSRF. A pergunta "em que guichê eu coloco o meu fiscal de auditoria?" é a pergunta "em que posição eu coloco o meu filtro?", e a resposta errada produz exatamente o `status=200` da história acima.

## Vocabulário

| Termo | O que é | Na API da clínica |
|---|---|---|
| **Filtro de servlet** (`jakarta.servlet.Filter`) | Código que roda antes (e depois) do servlet, podendo barrar ou modificar a requisição | `FiltroDeCorrelacao`, `FiltroDeAuditoria` |
| **`DelegatingFilterProxy`** | O único filtro do Spring Security que o Tomcat conhece; repassa tudo para um bean do Spring | Registrado pelo Boot com o nome `springSecurityFilterChain` |
| **`FilterChainProxy`** | O bean que recebe do proxy e escolhe qual cadeia aplicar | Escolhe entre `api` e `console` |
| **`SecurityFilterChain`** | Um *matcher* (quais requisições) + uma lista ordenada de filtros | `api` para `/api/**`; `console` para o resto |
| **`Authentication`** | Quem é o usuário (*principal*), com que credencial e com quais **autoridades** (`GrantedAuthority`) | `recepcao` com `ROLE_RECEPCAO` e `FACTOR_PASSWORD` |
| **`SecurityContextHolder`** | Onde o `Authentication` da requisição atual fica guardado (por padrão, numa variável da thread) | Lido pelo filtro de auditoria e pelo controller |
| **`SecurityContextRepository`** | Quem guarda o contexto **entre** requisições (sessão HTTP) ou não guarda (stateless) | Sessão no console; nada na API |
| **`AuthenticationManager`** / **`ProviderManager`** | Recebe um pedido de autenticação e delega a um `AuthenticationProvider` que saiba tratá-lo | Montado pelo Boot a partir do `UserDetailsService` |
| **`UserDetailsService`** | Carrega um usuário pelo nome (do banco, da memória, de um LDAP) | `InMemoryUserDetailsManager` com três usuários |
| **`AuthenticationEntryPoint`** | Decide a resposta quando falta autenticação (401, redirecionar para o login) | `RespostasDeSeguranca.commence` |
| **`AccessDeniedHandler`** | Decide a resposta quando o usuário autenticado não tem permissão (403) | `RespostasDeSeguranca.handle` |
| **CSRF** (*Cross-Site Request Forgery*) | Ataque em que outro site faz o navegador da vítima enviar uma requisição com os cookies dela | Proteção ligada no console, desligada na API |
| **Problem Details** | Formato padrão de erro HTTP em JSON (RFC 9457), com `type`, `title`, `status`, `detail`, `instance` | Corpo de todo 401 e 403 da API |

Dois termos de autorização aparecem o tempo todo. **Autoridade** é um texto qualquer que o `Authentication` carrega (`ROLE_ADMIN`, `SCOPE_consultas:ler`, `FACTOR_PASSWORD`). **Papel** (*role*) é só uma convenção: uma autoridade que começa com `ROLE_`. É por isso que `hasRole("ADMIN")` procura `ROLE_ADMIN`, e `hasAuthority("ADMIN")` procura `ADMIN` literalmente.

## O caminho de uma requisição

Quando uma requisição chega ao Tomcat, ela passa por uma lista de filtros de servlet antes de chegar ao `DispatcherServlet` do Spring MVC (aquele que chama os controllers, do módulo 08). O Spring Security entra nessa lista como **um único filtro**: o `DelegatingFilterProxy`. O Spring Boot o registra com o nome `springSecurityFilterChain` e a ordem `-100` (configurável pela propriedade `spring.security.filter.order`). Ele existe por um motivo técnico: o Tomcat cria os filtros antes de o contexto do Spring existir, então o proxy só guarda o nome do bean e, na primeira requisição, passa a delegar para ele.

Esse bean é o `FilterChainProxy`. Ele tem uma lista de `SecurityFilterChain`, em ordem, e faz uma coisa só: percorre a lista e usa **a primeira cadeia cujo matcher casa** com a requisição. As outras são ignoradas. Depois, executa os filtros da cadeia escolhida, um após o outro. Se nenhum filtro barrar a requisição, ela segue para o `DispatcherServlet` e chega ao controller.

Três consequências práticas saem dessa figura, e as três aparecem em entrevista e em incidente:

- **Os filtros rodam antes do Spring MVC.** Se um filtro barra a requisição, nenhum controller, nenhum `@ControllerAdvice` e nenhum interceptor do MVC fica sabendo. É por isso que um 401 gerado pela segurança nunca passa pelo seu `@RestControllerAdvice`.
- **Só uma cadeia roda por requisição.** Regras escritas na cadeia `console` não protegem `/api/**`, mesmo que pareçam mais gerais. E a ordem das cadeias é a ordem dos beans (`@Order`): a mais específica vem primeiro.
- **Dentro da cadeia, a ordem dos filtros é fixa e importa.** O Spring Security tem uma ordem registrada para cada filtro que ele conhece. Um filtro seu precisa ser encaixado relativamente a um deles (antes, depois ou no lugar), e a posição define o que ele consegue ver.

### Os filtros que importam, na ordem

A lista real da cadeia `api` desta aula tem treze filtros (você vai imprimi-la no passo 2). Nem todos merecem atenção no dia a dia. Os que você precisa conhecer pelo nome, na ordem em que rodam:

| Filtro | O que faz | Se ele barrar |
|---|---|---|
| `SecurityContextHolderFilter` | Carrega o `SecurityContext` do `SecurityContextRepository` (da sessão, por exemplo) e limpa o `SecurityContextHolder` no fim | — |
| `HeaderWriterFilter` | Escreve os headers de segurança (`X-Content-Type-Options`, `X-Frame-Options`, `Cache-Control`...) | — |
| `CsrfFilter` | Exige o token CSRF em métodos que alteram estado (POST, PUT, PATCH, DELETE) | 403 pelo `AccessDeniedHandler` |
| `LogoutFilter` | Trata `POST /logout` | — |
| `BasicAuthenticationFilter`, `UsernamePasswordAuthenticationFilter`, `BearerTokenAuthenticationFilter` | **Autenticam**: leem a credencial, chamam o `AuthenticationManager` e, se der certo, põem o `Authentication` no contexto | 401 pelo `AuthenticationEntryPoint` (credencial inválida) |
| `AnonymousAuthenticationFilter` | Se ninguém autenticou, coloca um `AnonymousAuthenticationToken` (usuário `anonymousUser`) | — |
| `ExceptionTranslationFilter` | Envolve os filtros seguintes num `try/catch` e traduz exceções de segurança em resposta | Escreve o 401 ou o 403 |
| `AuthorizationFilter` | **Autoriza**: aplica as regras de `authorizeHttpRequests` | Lança `AccessDeniedException` |

Repare em dois detalhes. Primeiro, a autorização é o **último** filtro: tudo o que vem antes serve para descobrir quem é a pessoa. Segundo, o `AuthorizationFilter` não escreve a resposta: ele lança uma exceção, e quem a transforma em HTTP é o `ExceptionTranslationFilter`, que está logo antes. Funciona assim (pseudocódigo da documentação, simplificado):

```java
try {
    cadeia.doFilter(requisicao, resposta);      // AuthorizationFilter e o resto
} catch (AuthenticationException | AccessDeniedException erro) {
    if (naoAutenticado || erro instanceof AuthenticationException) {
        entryPoint.commence(...);               // 401 (ou redirecionar para o login)
    } else {
        accessDeniedHandler.handle(...);        // 403
    }
}
```

"Não autenticado" inclui o usuário anônimo: se o `AnonymousAuthenticationFilter` pôs um `anonymousUser` no contexto e a regra exige um papel, o resultado é **401**, não 403. O raciocínio é que um anônimo ainda pode resolver o problema se autenticando; um usuário autenticado sem permissão, não.

### Passo 1: as duas cadeias

**O que vamos fazer e por quê.** A API e o console têm necessidades opostas. A API é usada por programas: cada requisição traz a credencial, não há navegador guardando cookies, e o servidor não deve criar sessão (assim qualquer instância atende qualquer requisição). O console é usado por pessoas num navegador: login uma vez, sessão, formulários protegidos contra CSRF. Tentar servir os dois com uma cadeia só obriga a escolher o pior dos dois mundos. A solução é ter **duas cadeias**, uma por tipo de cliente.

<CodigoJava caminho="m11-seguranca/aulas/src/main/java/dev/trilhajava/m11/aulas/filtros/SegurancaConfig.java" semImports destacar="27, 30, 35, 37-38, 42, 48, 54" />

**O que acabou de acontecer, linha a linha.**

- **Linhas 27 e 48:** `@Order(1)` e `@Order(2)` definem a ordem das cadeias no `FilterChainProxy`. Número menor, prioridade maior.
- **Linha 30:** `securityMatcher("/api/**")` diz **quais requisições pertencem a esta cadeia**. Não confunda com `requestMatchers` dentro de `authorizeHttpRequests`: o `securityMatcher` decide se a cadeia roda; os `requestMatchers` decidem, dentro da cadeia, qual regra de autorização vale. A cadeia `console` não tem `securityMatcher`, então casa com qualquer requisição. Por isso ela é a **última**.
- **Linhas 32 a 35:** as regras são avaliadas **de cima para baixo**, e vale a primeira que casar. `GET /api/status` é público; `POST /api/consultas` exige `RECEPCAO`; leitura exige `RECEPCAO` ou `MEDICO`. A linha 35, `anyRequest().denyAll()`, fecha o resto: uma rota nova sob `/api` nasce **negada** até alguém escrever a regra dela. Esse padrão (negar por padrão) é o que separa uma configuração segura de uma que vaza a cada endpoint novo.
- **Linha 36:** `httpBasic` liga o `BasicAuthenticationFilter`, que lê o header `Authorization: Basic base64(usuario:senha)`. Ele recebe o nosso `AuthenticationEntryPoint` para que uma senha errada também responda em Problem Details. HTTP Basic aparece aqui porque é o mecanismo mais simples para enxergar a arquitetura; na próxima aula, a mesma cadeia passa a aceitar JWT trocando esta linha.
- **Linha 37:** `SessionCreationPolicy.STATELESS` faz a cadeia não criar nem usar sessão HTTP. Cada requisição é autenticada do zero.
- **Linha 38:** CSRF desligado **só nesta cadeia**. A justificativa vem na seção sobre CSRF; por ora, guarde que ela depende da linha 37.
- **Linhas 39 a 41:** `exceptionHandling` conecta o `ExceptionTranslationFilter` às nossas respostas de 401 e 403 (passo 3).
- **Linha 42:** o filtro de auditoria entra **antes do `ExceptionTranslationFilter`**. O passo 4 explica por que exatamente ali.
- **Linhas 51 a 55:** a cadeia `console` libera `/error` (o Spring Boot encaminha erros para essa rota; se ela exigisse login, um 400 viraria um redirecionamento para a página de login), exige `ADMIN` em `/admin/**` e nega o resto. `formLogin(Customizer.withDefaults())` liga o login por formulário com a página padrão gerada pelo Spring Security. CSRF e sessão ficam com os padrões: ligados.
- **Linhas 59 a 71:** um `PasswordEncoder` delegante (gera hashes BCrypt com o prefixo `{bcrypt}`, como na [aula anterior](../../11-seguranca/01-autenticacao-e-senhas/)) e um `UserDetailsService` em memória. Como existe exatamente um bean de cada, o Spring Boot monta sozinho o `AuthenticationManager` global que as duas cadeias usam.

<Callout tipo="novidade" titulo="O que mudou do Spring Security 6 para o 7">
A versão 7 (que acompanha o Spring Boot 4) terminou várias migrações que a 6 tinha começado. As mudanças que você vai sentir em código antigo:

- **`and()` foi removido.** A DSL é só com lambdas: cada bloco (`csrf`, `sessionManagement`, `authorizeHttpRequests`...) recebe um `Customizer`. Código no estilo `http.csrf().disable().and().httpBasic()` não compila mais.
- **`authorizeRequests()` foi removido.** Use `authorizeHttpRequests()`, que é baseado em `AuthorizationManager` e roda no `AuthorizationFilter` (o antigo `FilterSecurityInterceptor` saiu de cena).
- **`AntPathRequestMatcher` e `MvcRequestMatcher` foram removidos**, substituídos por `PathPatternRequestMatcher`. Quando você passa uma `String` para `securityMatcher` ou `requestMatchers`, é ele que é criado: o log da subida mostra `PathPattern [/api/**]`. Para criar um à mão: `PathPatternRequestMatcher.pathPattern(HttpMethod.GET, "/api/**")`.
- **CSRF para SPAs** ganhou um atalho: `csrf(csrf -> csrf.spa())`.
- **Autenticação multifator nativa:** ao autenticar com senha, o `Authentication` ganha também a autoridade `FACTOR_PASSWORD` (você vai vê-la no passo 5). Código que converte **todas** as autoridades em papéis precisa filtrar pelo prefixo `ROLE_`; o exercício 11.02 cobra exatamente isso.
- A API antiga de `AccessDecisionManager`/`AccessDecisionVoter` foi para um módulo separado, `spring-security-access`.
</Callout>

### Passo 3: 401 e 403 no padrão da API

**O que vamos fazer e por quê.** Sem configuração, o `ExceptionTranslationFilter` da API responde 401 com um header `WWW-Authenticate` e corpo vazio, e o 403 sai pela página de erro padrão. O resto da API responde erros em Problem Details (RFC 9457, que substituiu a RFC 7807). Um cliente que trata `application/problem+json` em todo lugar não deveria ter um caso especial para a segurança. E como 401 e 403 nascem nos filtros, o `@RestControllerAdvice` não tem como ajudar: quem escreve a resposta precisa ser a própria segurança.

<CodigoJava caminho="m11-seguranca/aulas/src/main/java/dev/trilhajava/m11/aulas/filtros/RespostasDeSeguranca.java" semImports destacar="31, 36-41, 45-49, 51-60" />

**O que acabou de acontecer.**

- A classe implementa as duas interfaces. `commence` é chamado para **401**: falta credencial, a credencial é inválida, ou o usuário é anônimo e a rota exige alguém. `handle` é chamado para **403**: o usuário está autenticado, mas não tem a autoridade exigida.
- **Linha 38:** um 401 deve dizer ao cliente **como** se autenticar, no header `WWW-Authenticate` (RFC 9110). Para HTTP Basic, `Basic realm="clinica"`. Na próxima aula, com tokens, o valor passa a ser `Bearer`. O 403 não leva esse header: autenticar de novo não resolve.
- **Linha 31:** o `ProblemDetail` do Spring guarda campos extras num mapa interno. Para que `correlationId` saia no nível de cima do JSON (e não dentro de um objeto `properties`), o objeto precisa ser escrito pelo `JacksonJsonHttpMessageConverter`, que aplica a configuração própria do `ProblemDetail`, e não por um `JsonMapper` cru.
- **Linhas 51 a 60:** `type` é uma URI que identifica o tipo de problema (o cliente decide por ela, não pelo texto); `instance` é o recurso acessado; `correlationId` liga a resposta ao log do servidor.
- O detalhe da mensagem é genérico de propósito. Um 401 que diz "usuário não existe" ou "senha errada" ensina um atacante a descobrir quais usuários existem (enumeração de usuários, da aula anterior).

Na configuração, a mesma instância entra em dois lugares: em `httpBasic(...)` (senha errada é tratada pelo próprio `BasicAuthenticationFilter`, que chama o entry point sem passar pelo `ExceptionTranslationFilter`) e em `exceptionHandling(...)`. Esquecer o primeiro é um erro comum: a requisição sem credencial sai em Problem Details, mas a com senha errada sai com corpo vazio.

Suba a aplicação (o comando do passo 2, sem o argumento de log) e experimente com `curl`. Sem credencial, mandando um identificador de correlação próprio:

### Passo 4: um filtro de auditoria na posição certa

**O que vamos fazer e por quê.** A LGPD exige saber quem acessou dados pessoais de saúde. O filtro de auditoria registra, para cada requisição da API, o usuário, o método, o caminho e o status final. E põe o usuário no MDC, para que qualquer log feito durante a requisição (no controller, no serviço) diga quem a fez.

<CodigoJava caminho="m11-seguranca/aulas/src/main/java/dev/trilhajava/m11/aulas/filtros/FiltroDeAuditoria.java" semImports destacar="32-33, 35, 37-39" />

O filtro precisa de duas informações que ficam prontas em momentos diferentes da cadeia:

- **Quem é o usuário** (linha 32) só existe **depois** dos filtros de autenticação. Antes do `BasicAuthenticationFilter`, o `SecurityContextHolder` está vazio.
- **O status final** (linha 38) só existe depois que alguém escreveu a resposta. Se a autorização falhar, quem escreve o 403 é o `ExceptionTranslationFilter`, no `catch`. Então o filtro de auditoria precisa estar **fora** desse `try/catch`, ou seja, **antes** do `ExceptionTranslationFilter`. Assim, quando a exceção sobe, o tradutor escreve o 403 e só depois o `finally` da auditoria lê o status.

A única janela que satisfaz as duas condições é entre o `AnonymousAuthenticationFilter` e o `ExceptionTranslationFilter`. Daí `addFilterBefore(new FiltroDeAuditoria(), ExceptionTranslationFilter.class)`. Os três métodos de posicionamento do `HttpSecurity` são `addFilterBefore`, `addFilterAfter` e `addFilterAt` (este último coloca o seu filtro na mesma posição de um filtro conhecido, normalmente para substituí-lo). O segundo argumento precisa ser uma classe que o Spring Security conhece; você verá o erro do contrário em "Quando dá errado".

**O que acabou de acontecer.**

- `UsernamePasswordAuthenticationToken.unauthenticated(...)` cria o **pedido**: um `Authentication` com `isAuthenticated() == false`, carregando usuário e senha. O `DaoAuthenticationProvider` trata usuário e senha; num resource server, um `JwtAuthenticationProvider` trata tokens. Para autenticar contra um banco, você não reescreve nada disso: implementa um `UserDetailsService` que busca o usuário no repositório.

Por trás dessa igualdade, o `DaoAuthenticationProvider` também gasta tempo com um hash falso quando o usuário não existe, para que o tempo de resposta não denuncie quais usuários existem.
- O último teste põe o resultado no `SecurityContextHolder`, como o filtro faz. Ele limpa o contexto no `@AfterEach`: o holder é uma variável da thread, e o JUnit reaproveita threads.

<Callout tipo="info" titulo="SecurityContextHolder e SecurityContextRepository">
O `SecurityContextHolder` guarda o contexto **durante** a requisição, numa variável da thread (`ThreadLocal`). Quem guarda o contexto **entre** requisições é o `SecurityContextRepository`, e é o `SecurityContextHolderFilter` que o consulta no início de cada requisição. No console, o repositório usa a sessão HTTP: o login acontece uma vez e as próximas requisições recuperam o usuário pelo cookie `JSESSIONID`. Na API stateless, nada é salvo, e cada requisição precisa trazer a credencial. Desde o Spring Security 6, salvar o contexto é **explícito**: se você escrever um filtro de login próprio que põe um `Authentication` no holder, precisa também chamar `securityContextRepository.saveContext(...)`, ou o usuário "esquece" o login na requisição seguinte. Uma consequência do `ThreadLocal`: código que roda em outra thread (um `@Async`, um `CompletableFuture`) não enxerga o usuário, a menos que você propague o contexto (por exemplo, com `DelegatingSecurityContextExecutor`).
</Callout>

## Armadilhas e quando NÃO usar

<Comparar antes="Uma cadeia para tudo, com exceções" depois="Uma cadeia por tipo de cliente">
```java
http
    .csrf(csrf -> csrf.ignoringRequestMatchers("/api/**"))
    .authorizeHttpRequests(r -> r
        .requestMatchers("/api/**").hasAnyRole("RECEPCAO", "MEDICO")
        .requestMatchers("/admin/**").hasRole("ADMIN")
        .anyRequest().denyAll())
    .httpBasic(Customizer.withDefaults())
    .formLogin(Customizer.withDefaults());
// sessão criada para a API, redirecionamento
// para /login num cliente de API, Basic aceito
// no console...
```

```java
@Bean @Order(1)
SecurityFilterChain api(HttpSecurity http) { /*
    securityMatcher("/api/**"), Basic,
    STATELESS, sem CSRF, Problem Details */ }

@Bean @Order(2)
SecurityFilterChain console(HttpSecurity http) { /*
    sem matcher (pega-tudo, por último),
    formLogin, sessão, CSRF */ }
```
</Comparar>

A versão da esquerda funciona no caminho feliz e falha nas bordas: o console aceita HTTP Basic (um navegador vai abrir aquela janela cinza de usuário e senha), a API cria sessão para clientes que nunca vão usá-la, e um cliente da API sem credencial recebe um redirecionamento para uma página HTML. Cada exceção que você acrescenta (`ignoringRequestMatchers`, entry points por caminho) é uma regra a mais para esquecer.

As armadilhas de bolso:

- **Desligar CSRF por reflexo.** `csrf.disable()` é correto **só** onde nenhuma credencial vai sozinha pelo navegador. Se a sua SPA guarda a sessão num cookie (inclusive no padrão BFF, *Backend for Frontend*, em que o backend guarda o token e o navegador só tem um cookie), o CSRF precisa ficar ligado. No Spring Security 7, `csrf(csrf -> csrf.spa())` configura o padrão para SPAs: o token vai num cookie legível pelo JavaScript, que o devolve num header a cada requisição que altera estado.
- **Achar que `SameSite` resolve tudo.** Cookies com `SameSite=Lax` (o padrão de vários navegadores) barram boa parte dos ataques CSRF, mas não todos: requisições do mesmo site (outro subdomínio comprometido) e navegadores antigos escapam. Trate `SameSite` como camada extra, não como substituto do token.
- **`permitAll()` não desliga a segurança.** Uma rota com `permitAll()` ainda passa por toda a cadeia: headers, CSRF, autenticação (uma credencial inválida ainda gera 401). Para que a segurança ignore uma rota de vez (arquivos estáticos, por exemplo), o caminho moderno é uma cadeia própria com `securityMatcher` e `permitAll()`, e não o antigo `WebSecurityCustomizer.ignoring()`, que tira a rota até dos headers de segurança.
- **Esquecer o `/error`.** Sem liberá-lo, qualquer erro do MVC em uma rota pública (um 400 de validação, um 404) é encaminhado para `/error`, que exige login, e o cliente vê 401 ou um redirecionamento.
- **`@ExceptionHandler(Exception.class)` no `@RestControllerAdvice`.** Um handler "pega-tudo" captura também o `AuthorizationDeniedException` lançado pelo `@PreAuthorize` dentro do controller, e o 403 vira 500. Se você tem um handler genérico, relance as exceções de segurança ou trate `AccessDeniedException` explicitamente.
- **Só segurança de URL.** Regras de rota protegem a porta de entrada HTTP. Um job agendado, um consumidor de fila ou outra rota que chame o mesmo serviço passam por fora delas. Dados sensíveis merecem regra no método, como o prontuário.

**Quando NÃO usar o que você viu aqui:**

- **Não use HTTP Basic em produção para usuários finais.** A senha viaja em cada requisição (em Base64, que não é criptografia) e não há como revogar uma sessão sem trocar a senha. Basic é aceitável para integração entre sistemas, sempre com TLS e credenciais próprias para cada sistema; para usuários, use tokens (próxima aula) ou sessão.
- **Não escreva um filtro de autenticação próprio** se um mecanismo do framework resolve: `httpBasic`, `formLogin`, `oauth2ResourceServer`, `oauth2Login`. Um filtro próprio precisa tratar salvamento de contexto, eventos, mensagens uniformes, tempo constante e sessão, e é onde os bugs de segurança moram.
- **Não use `@EnableWebSecurity(debug = true)` fora da sua máquina**, nem log da segurança em TRACE em produção: os dois registram headers, incluindo `Authorization`.
- **Não crie uma segunda cadeia só para uma rota pública.** Se é uma rota dentro do mesmo tipo de cliente, um `permitAll()` resolve. Cadeias separadas são para clientes com necessidades diferentes (sessão contra stateless, mecanismos de autenticação diferentes).

## Visão de pleno e sênior: decisões e trade-offs

**Uma cadeia ou várias.** A regra que funciona: uma cadeia por **tipo de cliente**, não por recurso. API para aplicativos (stateless, token), console para pessoas (sessão, CSRF), talvez uma terceira para o Actuator (rede interna, autenticação própria, sem CSRF). Mais cadeias significam mais configuração duplicada (headers, CORS, handlers de erro); extraia essas partes para métodos ou para *modular configuration* (o Spring Security 7 aplica a todas as cadeias os beans `Customizer<HttpSecurity>` e os customizadores de bloco, como um `Customizer<HeadersConfigurer<HttpSecurity>>`). Menos cadeias significam exceções dentro de uma cadeia só, que é como a maioria das brechas nasce. Ao justificar para o time, mostre a lista de filtros de cada cadeia, lado a lado: ela torna a diferença concreta.

**Stateless ou sessão.** Stateless escala horizontalmente sem esforço (qualquer instância atende qualquer requisição) e não exige CSRF, mas transfere o problema para o token: revogação, expiração, armazenamento no cliente. Sessão dá revogação imediata (invalidou a sessão, acabou) e é o modelo mais seguro para navegadores, mas exige sessão compartilhada entre instâncias (Spring Session com Redis ou banco, ou *sticky sessions* no balanceador, que tornam o deploy e a queda de uma instância mais dolorosos). Para uma SPA do próprio produto, muitos times sêniores escolhem **sessão com cookie no padrão BFF** em vez de guardar JWT no navegador, justamente por causa da revogação e de não expor o token ao JavaScript. A decisão deve ser registrada num ADR, com o motivo.

**Custo de autenticação por requisição.** Com HTTP Basic e BCrypt, **cada requisição** calcula um hash de senha de propósito lento (dezenas a centenas de milissegundos com fator de custo 10 a 12). Numa API de alto volume, isso vira CPU e latência: mil requisições por segundo podem exigir dezenas de núcleos só para hashes. É um dos motivos para trocar a senha por um token emitido uma vez e validado barato a cada requisição (uma verificação de assinatura, na próxima aula). Se precisar manter Basic entre sistemas, use credenciais longas e aleatórias, que permitem um hash mais rápido sem perder segurança.

**Observabilidade da segurança.** Em produção, as perguntas são "quantas requisições estão sendo negadas, por quem, em quais rotas" e "houve pico de falhas de login". Logs de auditoria como o desta aula respondem a primeira; eventos de autenticação (`AuthenticationSuccessEvent`, `AbstractAuthenticationFailureEvent`) e de autorização (`AuthorizationDeniedEvent`, publicado quando você registra um `AuthorizationEventPublisher`) respondem a segunda e alimentam métricas e alertas. Um salto de 403 depois de um deploy é sinal de regra quebrada; um salto de 401 com usuários variados é sinal de ataque de *credential stuffing* (testar listas de senhas vazadas). Em logs, nunca registre o header `Authorization`, cookies de sessão nem o corpo de requisições de login.

**Falhar fechado.** A configuração desta aula termina as duas cadeias com `anyRequest().denyAll()`. O custo é atrito: cada endpoint novo precisa de uma regra explícita, e alguém vai reclamar de um 403 inesperado. O ganho é que o erro de esquecer uma regra resulta em acesso **negado**, que aparece no primeiro teste, e não em dado vazado, que aparece num relatório de incidente. Em revisão de código, trate `anyRequest().permitAll()` e `anyRequest().authenticated()` em APIs com várias rotas sensíveis como pontos de atenção.

**Matriz de acesso como contrato.** Em times grandes, a matriz de acesso é a forma de a área de negócio, a segurança e o desenvolvimento concordarem sobre quem pode o quê. Mantida como teste parametrizado (passo 6), ela quebra o build quando alguém altera uma regra sem discutir. O custo é que testes com `@SpringBootTest` são mais lentos que testes de fatia; o contexto é reaproveitado entre as classes com a mesma configuração (o cache de contexto do Spring), então o custo real é uma subida por configuração diferente, não por teste. Evite variar propriedades à toa entre classes de teste.

**Quando trocar de abordagem.** HTTP Basic com usuários em memória serve para esta aula e para ferramentas internas pequenas. Sinais de que está na hora de mudar: mais de um cliente externo (vá para OAuth2 com tokens), necessidade de login único entre sistemas (OpenID Connect, aula 07), requisitos de multifator (o suporte nativo a MFA do Spring Security 7, construído sobre as autoridades de fator), ou autorização que depende do **dono** do recurso e não só do papel ("a recepção só vê consultas da própria unidade"), que é o tema da aula 04.

<Callout tipo="entrevista">
**"Explique como o Spring Security funciona."** Uma boa resposta segue o caminho da requisição: o `DelegatingFilterProxy` registrado no contêiner repassa ao `FilterChainProxy`, que escolhe a primeira `SecurityFilterChain` que casa; filtros de autenticação usam o `AuthenticationManager` (`ProviderManager`, providers, `UserDetailsService`, `PasswordEncoder`) para pôr um `Authentication` no `SecurityContextHolder`; o `AuthorizationFilter` aplica as regras e o `ExceptionTranslationFilter` traduz falhas em 401 ou 403. Tudo antes do `DispatcherServlet`, e por isso o `@ControllerAdvice` não vê 401 e 403.

**"Quando você desliga o CSRF?"** Quando nenhuma credencial vai automaticamente pelo navegador (token no header `Authorization`, cadeia stateless). Com cookie de sessão, nunca; em SPA com cookie, `csrf.spa()`. Bônus: o `CsrfFilter` roda antes da autenticação, e por isso um POST sem token dá 403 até para quem não está autenticado.

**"Como você testa a segurança de uma API?"** Matriz de acesso com credenciais reais, cobrindo cada perfil em cada operação; testes de formato para 401 e 403; `@WithMockUser` e `jwt()` para regras finas, sabendo que eles pulam a autenticação; e testes com tokens inválidos para provar a validação. Bônus: um teste que confere a posição dos filtros próprios.

**"Qual a diferença entre 401 e 403?"** 401: não sei quem você é (sem credencial, credencial inválida ou anônimo), e a resposta traz `WWW-Authenticate`. 403: sei quem você é e você não pode. Armadilha que vale citar: um POST sem CSRF dá 403 com a mesma mensagem de "sem permissão", se o handler não distinguir.

**"Por que um filtro customizado pode rodar duas vezes?"** Porque o Spring Boot registra todo bean `Filter` no contêiner; se ele também for adicionado à cadeia, roda nas duas. Solução: não declarar como bean ou desligar o registro com `FilterRegistrationBean.setEnabled(false)`.
</Callout>

## Checkpoint

A clínica contratou um laboratório parceiro, que vai consultar resultados de exame pela API. Um colega propôs esta alteração na cadeia `api` (o resto da configuração continua igual):

```java
.authorizeHttpRequests(regras -> regras
        .requestMatchers(GET, "/api/status").permitAll()
        .requestMatchers("/api/**").hasAnyRole("RECEPCAO", "MEDICO")
        .requestMatchers(GET, "/api/exames/**").hasRole("LABORATORIO")
        .requestMatchers(POST, "/api/consultas").hasRole("RECEPCAO")
        .anyRequest().denyAll())
```

Sem rodar nada, preencha o status de cada linha e diga o que está errado e como corrigir:

1. Usuário com `ROLE_LABORATORIO`, `GET /api/exames/55`, com credenciais válidas.
2. `dra.helena` (`MEDICO`), `POST /api/consultas`.
3. `recepcao`, `GET /api/consultas/1/prontuario`.
4. Requisição anônima, `GET /api/exames/55`.

<details>
<summary>Solução</summary>

1. **403.** A regra `/api/**` vem antes e casa com `/api/exames/55`; como vale a primeira que casar, o papel `LABORATORIO` nunca é consultado. A regra de exames é código morto.
2. **201.** A mesma regra ampla casa com `POST /api/consultas` e aceita `MEDICO`. A regra que restringia o POST à recepção também virou código morto, e uma médica agora marca consultas. Isso é escalação de privilégio silenciosa: nenhum erro, nenhum log diferente.
3. **403.** A rota passa (a regra ampla aceita `RECEPCAO`), mas o `@PreAuthorize("hasRole('MEDICO')")` do serviço barra. É a segurança de método funcionando como segunda camada, e o motivo de ela existir.
4. **401.** O anônimo não satisfaz `hasAnyRole`, e o `ExceptionTranslationFilter` trata anônimo como não autenticado.

**Correção:** regras específicas antes das amplas, e nada de regra ampla que case com métodos de escrita:

```java
.requestMatchers(GET, "/api/status").permitAll()
.requestMatchers(GET, "/api/exames/**").hasRole("LABORATORIO")
.requestMatchers(POST, "/api/consultas").hasRole("RECEPCAO")
.requestMatchers(GET, "/api/consultas/**").hasAnyRole("RECEPCAO", "MEDICO")
.anyRequest().denyAll()
```

**Como provar:** acrescente à `MatrizDeAcessoTest` as linhas `GET, /api/exames/55, laboratorio, 200` (com um usuário `laboratorio` no `UserDetailsService`) e confira que a linha `POST, /api/consultas, dra.helena, 403` já existente falharia com a configuração do colega. Uma matriz completa teria pegado o erro antes do code review.

</details>

## Resumo

- O Tomcat conhece um único filtro do Spring Security, o `DelegatingFilterProxy` (ordem -100), que repassa ao `FilterChainProxy`. Ele usa **a primeira** `SecurityFilterChain` que casa; só os filtros dela rodam, antes do `DispatcherServlet`.
- Várias cadeias: `securityMatcher` decide quem entra, `@Order` decide a ordem, e só a última pode casar com tudo. Uma cadeia por tipo de cliente: API stateless sem CSRF, console com sessão e CSRF.
- Inspecione as cadeias pelo log DEBUG de `DefaultSecurityFilterChain`, pelo TRACE de `org.springframework.security` e, de forma permanente, com um teste sobre o `FilterChainProxy`.
- Autenticação: o filtro extrai a credencial, o `ProviderManager` delega ao `DaoAuthenticationProvider`, que usa `UserDetailsService` e `PasswordEncoder`. O resultado vai para o `SecurityContextHolder` (por thread); o `SecurityContextRepository` guarda entre requisições, ou não guarda nada na API stateless.
- DSL do Spring Security 7: só lambdas, `authorizeHttpRequests`, `PathPatternRequestMatcher`, `csrf.spa()`, autoridade `FACTOR_PASSWORD`. Regras em ordem, específicas primeiro, `anyRequest().denyAll()` no fim, `/error` liberado.
- 401 e 403 nascem nos filtros: escreva Problem Details no `AuthenticationEntryPoint` (com `WWW-Authenticate`) e no `AccessDeniedHandler`, e passe o entry point também ao mecanismo de autenticação.
- Filtro próprio: posicione relativo a um filtro do framework, pela informação de que ele precisa; não o declare como bean; prove a posição com teste.
- Teste com matriz de acesso e credenciais reais; `@WithMockUser` e `jwt()` testam só a autorização.
