Uma fintech pequena recebe, numa sexta-feira, o e-mail de um pesquisador de segurança: "a busca de contas do painel do atendente devolve contas de todas as agências se eu digitar `x' OR '1'='1` no campo de titular". Na segunda, o time descobre mais três coisas enquanto investiga. O endpoint de download de notas fiscais aceita `../config/application.properties`. A tela de cadastro de webhooks aceita `https://169.254.169.254/...`, o endereço de metadados da nuvem que entrega credenciais temporárias de quem roda o serviço. E qualquer erro do banco volta para o cliente com host, porta e usuário do PostgreSQL de produção. Nenhum desses bugs é exótico. Todos estão no **OWASP Top 10**, e todos têm a mesma raiz: o código tratou dado de fora como se fosse instrução, ou tratou uma falha como se fosse sucesso.

O OWASP Top 10 é a lista de referência dos riscos mais críticos em aplicações web, publicada pela OWASP (*Open Worldwide Application Security Project*, uma fundação sem fins lucrativos) a partir de dados de milhões de aplicações e de uma pesquisa com a comunidade. A edição **2025** é a oitava. Nesta aula você vai passar pelas dez categorias do ponto de vista de quem escreve backend Java com Spring: como cada uma aparece num projeto de verdade, um exemplo vulnerável e a correção, e como detectar antes da produção. Depois vai pôr a mão em oito pares de código **vulnerável e corrigido**, cada um com um teste que prova o ataque na primeira versão e o bloqueio na segunda. No fim, você vai saber usar o Top 10, o OWASP API Security Top 10 e o ASVS como ferramentas de trabalho, e não como uma lista para decorar.

## A intuição: o protocolo da recepção

Pense na recepção de um prédio comercial. Visitantes chegam com pedidos escritos num papel, e a recepcionista lê e age. Agora imagine visitantes espertos:

- Um escreve: "quero a sala 1204 **ou qualquer outra sala**". Se a recepcionista lê o papel em voz alta para um interfone que obedece a qualquer frase, todas as portas se abrem. É a **injeção**: o dado foi lido como **ordem**. A defesa não é desconfiar da palavra "ou"; é um formulário com campos (andar, sala) que o interfone só aceita **como valor**. Isso é o parâmetro de bind.
- Outro pede "o envelope que está em `../../diretoria/cofre`". Seguindo o caminho escrito, a recepcionista entra onde o visitante não pode. É o **path traversal**.
- Um terceiro pede: "ligue para este número e leia o que responderem". O número é o ramal da tesouraria, que só atende chamadas de dentro. A recepcionista vira o braço do visitante. É o **SSRF**.
- E se o sistema de crachás cai? Liberar todo mundo "para não atrasar" é falhar aberto; barrar até o sistema voltar é falhar fechado. É o **A10**.

O protocolo de uma boa recepção tem quatro regras, e elas atravessam a aula inteira: **dado de fora nunca vira instrução** (formulário com campos, não frases livres), **a lista de destinos é fechada** (allowlist, não lista de proibidos), **o que importa é onde a ação de fato acontece** (a sala real, o IP real, o caminho real) e **na dúvida, a porta fica fechada**.

## Vocabulário

| Termo | O que é |
|---|---|
| **Vulnerabilidade** | Um defeito que alguém pode explorar para fazer o sistema agir contra a vontade do dono |
| **CWE** | *Common Weakness Enumeration*: catálogo de **tipos** de falha (CWE-89 é SQL injection). Cada categoria do Top 10 agrupa várias CWEs |
| **CVE** | *Common Vulnerabilities and Exposures*: uma falha **específica** num produto específico (o Log4Shell é a CVE-2021-44228) |
| **Fonte e destino** (*source* e *sink*) | Fonte é por onde o dado de fora entra (parâmetro, cabeçalho, corpo, arquivo, fila). Destino é onde ele vira ação perigosa (SQL, caminho de arquivo, URL, log, desserializador) |
| **Allowlist** e **denylist** | Lista do que é permitido e lista do que é proibido. Allowlist falha fechada: o que ninguém previu fica de fora. Denylist falha aberta: o que ninguém previu passa |
| **Parâmetro de bind** | Um marcador (`?` ou `:nome`) no SQL cujo valor viaja separado do texto da consulta; o banco nunca o interpreta como SQL |
| **SAST** | *Static Application Security Testing*: análise do código-fonte sem executá-lo (Semgrep, CodeQL, SpotBugs com Find Security Bugs, SonarQube) |
| **DAST** | *Dynamic Application Security Testing*: ataque automatizado à aplicação rodando (OWASP ZAP, Burp Suite) |
| **SCA** | *Software Composition Analysis*: varredura das dependências contra bases de CVEs (Dependabot, OWASP Dependency-Check, Trivy) |
| **Gadget** | Uma classe legítima do classpath cujo construtor, setter ou `readObject` faz algo perigoso quando instanciada com dados do atacante |
| **Falhar fechado** (*fail closed*) | Diante de erro, negar a operação. O oposto, falhar aberto, é a CWE-636 |
| **ASVS** | *Application Security Verification Standard*: o padrão da OWASP com cerca de 350 requisitos verificáveis, em três níveis |

Uma distinção que organiza a aula: o Top 10 é uma **lista de conscientização** (o que mais dá errado, para priorizar), não um padrão. Quem quer saber "o que exatamente minha aplicação precisa cumprir" usa o ASVS. Voltamos a isso no fim.

## A lista de 2025

| # | Categoria | Em uma frase | CWEs ou exemplos |
|---|---|---|---|
| A01 | **Broken Access Control** | alguém faz ou vê o que não devia, incluindo SSRF | 22 (path traversal), 200, 201, 352 (CSRF), 918 (SSRF) |
| A02 | **Security Misconfiguration** | padrões inseguros, diagnóstico aberto, XXE | 16, 611 (XXE) |
| A03 | **Software Supply Chain Failures** | dependências, build e pipeline comprometidos *(nova)* | componentes vulneráveis ou maliciosos |
| A04 | **Cryptographic Failures** | dado sensível sem proteção ou com algoritmo fraco | algoritmos e aleatoriedade fracos |
| A05 | **Injection** | dado vira código: SQL, comando, LDAP, XSS | 78, 79, 89, 90, 94 |
| A06 | **Insecure Design** | a falha está no desenho, não na linha | regras de negócio abusáveis |
| A07 | **Authentication Failures** | senhas, sessões e tokens mal protegidos | força bruta, credenciais fracas |
| A08 | **Software or Data Integrity Failures** | confiar em código ou dado sem verificar a integridade | 502 (desserialização), 829, 915 |
| A09 | **Security Logging and Alerting Failures** | ataque acontecendo e ninguém fica sabendo | 117 (injeção em log), 532, 778 |
| A10 | **Mishandling of Exceptional Conditions** | erro tratado de um jeito que abre brecha *(nova)* | 209, 476, 636 (falhar aberto) |

O que mudou em relação a 2021, segundo a própria introdução da edição:

- **Duas categorias novas.** *Software Supply Chain Failures* amplia o antigo "componentes vulneráveis e desatualizados": não é só a biblioteca com CVE, é também o pacote malicioso, a action do CI trocada, o artefato publicado sem verificação. *Mishandling of Exceptional Conditions* reúne o que antes estava espalhado como "qualidade de código": mensagens de erro reveladoras, falhar aberto, estado inconsistente depois de uma exceção.
- **SSRF foi consolidado em A01.** Na edição 2021 ele era a A10. Faz sentido: SSRF é o servidor acessando, em nome do atacante, um recurso que o atacante não alcança.
- **Security Misconfiguration subiu de 5º para 2º.** Configuração é cada vez mais código (YAML, Terraform, Helm), e um padrão errado se replica em todos os ambientes.
- **Renomes.** A07 virou só *Authentication Failures*; A09 trocou *Monitoring* por *Alerting*, porque log que ninguém olha não protege nada.

Repare no desenho: os riscos que dão mais trabalho no dia a dia (injeção, path traversal, SSRF, desserialização, XXE) estão todos na **seta que sai do serviço para um destino perigoso**. É por isso que revisão de código de segurança começa procurando os destinos (`sql(`, `Files.`, `uri(`, `readValue`, `readObject`, `newDocumentBuilder`) e volta até a fonte, perguntando: "o que chega aqui pode ter vindo de fora sem passar por uma allowlist?".

## Os dez itens, um por um

Para cada categoria: o que é, como aparece num backend Java/Spring, o par vulnerável/correção e como detectar. Os itens que o backend mais erra ganham código testado na seção "Mão na massa"; os que outras aulas aprofundam aparecem aqui só com o essencial e o link.

### A01 — Broken Access Control

**O que é.** O sistema deixa alguém agir fora do que a política permite: ver o pedido de outro cliente, chamar uma rota administrativa, trocar o `id` na URL. Continua em primeiro lugar, com 40 CWEs mapeadas, e agora inclui o SSRF.

**Como aparece no Spring.** Três formas dominam. A primeira é o **BOLA/IDOR**: `GET /contas/{id}` que busca por id sem conferir o dono. A [aula 11.04](../../11-seguranca/04-autorizacao-e-bola/) trata disso a fundo, com a matriz de testes de autorização; aqui não repetimos. A segunda é o **path traversal** (CWE-22): um nome de arquivo vindo da requisição que vira caminho no disco. A terceira é o **SSRF** (CWE-918): uma URL vinda da requisição que o servidor busca.

```java
// Path traversal: o nome do arquivo vem da URL
@GetMapping("/notas/{arquivo}")
byte[] nota(@PathVariable String arquivo) throws IOException {
    return Files.readAllBytes(pasta.resolve(arquivo));   // "../config/application.properties"
}

// SSRF: a URL vem do corpo
@PostMapping("/webhooks")
void cadastrar(@RequestBody NovoWebhook pedido) {
    restClient.post().uri(pedido.url()).body(TESTE).retrieve().toBodilessEntity();
}
```

**Correção.** Para arquivos: não aceitar nome nenhum (receber o id do documento, conferir o dono, buscar o caminho no banco) ou, se o nome for inevitável, formato fechado mais confinamento à pasta. Para URLs: parser, allowlist de domínios, resolução DNS e recusa de faixas internas. Os dois estão nos passos 4 e 5.

**Como detectar.** Testes de autorização (aula 11.04) e testes de path traversal e SSRF como os desta aula; SAST com regras de *taint* (Semgrep e CodeQL rastreiam parâmetros até `Files.*` e clientes HTTP); DAST, que tenta `../` e IPs internos sozinho. Na revisão: "alguma rota lê arquivo ou busca URL com dado do cliente?".

### A02 — Security Misconfiguration

**O que é.** A aplicação está certa, mas foi ligada errado: endpoint de diagnóstico aberto, mensagem de erro detalhada, CORS liberado para qualquer origem, parser XML com recursos perigosos ligados, conta padrão. Subiu para segundo lugar. A CWE-611 (XXE) mora aqui, porque é um problema de **configuração do parser**.

**Como aparece no Spring.** O Spring Boot tem padrões bons, e quase toda falha desta categoria é alguém desligando um padrão bom:

```properties
# Vulnerável em produção
management.endpoints.web.exposure.include=*       # /actuator/heapdump, /env, /loggers, /threaddump...
server.error.include-stacktrace=always            # o padrão é never
server.error.include-message=always               # o padrão é never
spring.h2.console.enabled=true
```

Por padrão, o Actuator expõe só `health` pela web. O `heapdump` entrega um retrato da memória com tokens, senhas e dados de clientes; o `loggers` permite ligar `DEBUG` em produção. Exponha só o necessário, de preferência numa porta de gerenciamento separada (`management.server.port`) fechada na rede interna, e proteja o resto com autenticação.

**XXE** é um padrão perigoso que **não** é do Spring: a `DocumentBuilderFactory` do JDK, sem configuração, aceita entidades externas (passo 6). **CORS** com `*` e cabeçalhos de segurança estão na [aula 11.06](../../11-seguranca/06-defesas-da-api/).

**Como detectar.** Teste de fumaça contra a configuração de produção (`GET /actuator/env` dá 401/404; erro não devolve `trace`), varredura de configuração no CI (Trivy, Checkov) e DAST, que acha `/actuator/*` e erros verbosos em minutos. Na revisão: "algum padrão de segurança foi desligado, e por quê?".

### A03 — Software Supply Chain Failures *(nova)*

**O que é.** O seu código é uma fração pequena do que roda. Uma dependência com CVE conhecida (o Log4Shell, em 2021), um pacote malicioso com nome parecido com o original (*typosquatting*), uma action do GitHub que alguém sequestrou, um build que não é reproduzível, um artefato publicado sem assinatura: tudo isso compromete a aplicação sem que uma linha sua esteja errada.

**Como aparece no Spring.** Dependência transitiva antiga que ninguém escolheu, versão fixada à mão no `pom.xml` que impede o BOM do Spring Boot de atualizar, repositório Maven extra sem HTTPS, `uses: alguma-action@main` no workflow.

**Correção e detecção.** Atualização contínua, SCA no CI que quebra o build, SBOM e actions fixadas por hash: a [aula 11.06](../../11-seguranca/06-defesas-da-api/) mostra a configuração. Na revisão: "precisamos mesmo dessa dependência? Quem a mantém? Quantas transitivas ela traz?".

### A04 — Cryptographic Failures

**O que é.** Dado sensível sem proteção, ou protegido com algoritmo, modo ou aleatoriedade fracos.

```java
// Vulnerável
String hash = DigestUtils.md5Hex(senha);                     // senha com hash rápido e sem sal
Cipher cifra = Cipher.getInstance("AES/ECB/PKCS5Padding");   // ECB repete padrões do texto
String token = Long.toString(new Random().nextLong());       // previsível

// Correto
String hash = passwordEncoder.encode(senha);                 // BCrypt/Argon2id (aula 11.01)
Cipher cifra = Cipher.getInstance("AES/GCM/NoPadding");      // com IV de 12 bytes aleatório por mensagem
byte[] bytes = new byte[32];
new SecureRandom().nextBytes(bytes);                         // token de recuperação
```

Senhas estão na [aula 11.01](../../11-seguranca/01-autenticacao-e-senhas/). O resto da categoria é operacional: TLS em todo lugar (inclusive entre serviços e até o banco), chaves num cofre e não no repositório, dado pessoal cifrado em repouso quando a regulação exige (LGPD, PCI DSS). **Como detectar:** SAST encontra `MD5`, `SHA1`, `ECB` e `new Random()` com facilidade; na revisão, pergunte de onde vem cada chave e quem consegue lê-la.

### A05 — Injection

**O que é.** Dado de fora interpretado como código por um interpretador: SQL, JPQL, comando do sistema operacional, LDAP, SpEL, HTML no navegador (XSS). Caiu para quinto, mas continua sendo a categoria com mais CVEs, puxada pelo XSS.

**Como aparece no Spring.** Quase nunca é o `Statement` cru do JDBC dos anos 2000. É concatenação **em lugares que parecem seguros**:

```java
// JdbcTemplate com concatenação
jdbcTemplate.query("SELECT * FROM conta WHERE titular = '" + titular + "'", mapper);

// JPQL concatenada (o JPA não protege texto que você montou)
em.createQuery("SELECT c FROM Conta c WHERE c.titular = '" + titular + "'", Conta.class);

// Consulta nativa no Spring Data montada com String.format
@Query(value = "...", nativeQuery = true)   // ok, se usar :parametro; vulnerável se o texto for montado fora

// ORDER BY dinâmico: a armadilha mais comum em APIs com ordenação e paginação
jdbc.sql("SELECT ... ORDER BY " + ordenarPor)
```

**Correção.** Parâmetro de bind para **valores**, sempre: `?` no `JdbcTemplate`, `:nome` no `JdbcClient` e na JPQL, `@Param` no Spring Data, Criteria API para filtros dinâmicos. Para **identificadores** (coluna, tabela, direção), que não podem ser parâmetros, **allowlist** (passos 1 e 2). **Injeção em log** (CWE-117, mapeada em A09) tem a mesma mecânica: um `\r\n` no e-mail forja uma linha de log (passo 3). **XSS** numa API JSON é defendido principalmente no front, mas o backend ajuda com `Content-Type` correto, `X-Content-Type-Options: nosniff` (padrão do Spring Security) e validação de formato.

**Como detectar.** SAST: todo `sql(` ou `createQuery(` com argumento não constante merece olhar humano. Testes com `'`, `' OR '1'='1` e `D'Ávila` em todo campo de busca. DAST para o que escapar.

### A06 — Insecure Design

**O que é.** Nenhuma linha está errada, mas o desenho permite abuso: transferência sem idempotência que debita duas vezes quando o cliente repete; recuperação de senha que confirma se o e-mail existe; cupom aplicável infinitas vezes; preço que vem do front; limite de valor por operação que se contorna com cem operações pequenas.

**Correção e detecção.** Modelagem de ameaças no desenho da funcionalidade (assunto da [aula 11.08](../../11-seguranca/08-modelagem-de-ameacas-e-dados-sensiveis/), mais adiante neste módulo) e **casos de abuso como critérios de aceite**: "dado que o cliente reenvia a mesma transferência com a mesma chave de idempotência, então só um débito acontece". Ferramenta nenhuma encontra falha de desenho; quem encontra é a pergunta "como alguém abusaria disto?" feita antes do código.

### A07 — Authentication Failures

**O que é.** Senha fraca aceita, falta de proteção contra força bruta, enumeração de usuários, token sem expiração, sessão válida depois do logout, segredo de JWT fraco. Tudo isso foi tratado nas aulas [11.01](../../11-seguranca/01-autenticacao-e-senhas/) (hash adaptativo, NIST, mesma resposta e mesmo tempo no login), [11.02](../../11-seguranca/02-spring-security-7/) e [11.03](../../11-seguranca/03-jwt-e-resource-server/) (algoritmo, emissor e `exp` validados). **Como detectar:** testes que provam a mesma resposta para usuário inexistente e senha errada, testes de token expirado e de algoritmo trocado, e o limite de tentativas da aula 11.06.

### A08 — Software or Data Integrity Failures

**O que é.** Confiar em código ou dado que alguém pode ter alterado, sem verificar. Inclui a **desserialização de dados não confiáveis** (CWE-502), a **atribuição em massa** (CWE-915, o famoso `"admin": true` no JSON que o Jackson aplica num campo da entidade) e a inclusão de funcionalidade de fonte não confiável (CWE-829).

**Como aparece no Spring.**

- `ObjectInputStream.readObject()` sobre bytes de fora: cache, fila, cookie, um "token" serializado. O objeto é **criado antes** de qualquer cast, e uma classe *gadget* do classpath pode fazer o estrago já na criação.
- Jackson com polimorfismo por **nome de classe** (`@JsonTypeInfo(use = Id.CLASS)`) em campo genérico. O Jackson 3 recusa isso por padrão, como o passo 7 prova, mas é comum alguém "consertar" o erro afrouxando o validador.
- Webhook de pagamento sem verificação de assinatura: qualquer um envia "pagamento aprovado".
- Entidade JPA usada como corpo de requisição: o cliente manda campos que você nunca quis que ele mudasse (atribuição em massa; DTOs resolvem, como na aula 11.04).

**Correção.** Não desserialize formato nativo de fonte não confiável; se precisar, `ObjectInputFilter` com allowlist. No Jackson, polimorfismo por **nome lógico** com subtipos fechados. Webhook com HMAC conferido em tempo constante (`MessageDigest.isEqual`). DTO de entrada com só os campos editáveis. **Como detectar:** SAST acha `readObject` e `Id.CLASS`; SCA acha bibliotecas com gadgets conhecidos; na revisão, pergunte "quem consegue alterar estes bytes antes de chegarem aqui?".

### A09 — Security Logging and Alerting Failures

**O que é.** Um ataque de força bruta com 50 mil tentativas que não gera alerta nenhum. Ou o contrário: o log registra o corpo das requisições, com senhas e tokens (CWE-532). Ou ainda: o log pode ser forjado com quebras de linha (CWE-117).

```java
log.warn("login-falhou email={} ip={}", email, ip);       // evento útil... se o e-mail for neutralizado
log.info("requisição recebida: {}", pedido);              // perigoso se o toString() do DTO incluir a senha
```

**Correção.** Registre eventos de segurança (login com falha, bloqueio, acesso negado, mudança de permissão, exportação de dados) em formato estruturado, sem segredos, com identificador de correlação; crie alertas para picos; guarde os logs onde quem atacou a aplicação não consegue apagá-los. O Spring Boot tem log estruturado nativo (`logging.structured.format.console=ecs`, por exemplo), que escapa quebras de linha por ser JSON; com log de texto, neutralize você mesmo (passo 3). E sobrescreva o `toString()` de records com campos sensíveis. **Como detectar:** teste que confere que o evento é registrado; busca por `password`, `token`, `authorization` nos logs de homologação; um exercício de "simulação de incidente" em que alguém pergunta "como saberíamos?".

### A10 — Mishandling of Exceptional Conditions *(nova)*

**O que é.** A aplicação não previne, não detecta ou responde mal a situações anormais. As CWEs destacadas pela OWASP incluem a 209 (mensagem de erro com informação sensível), a 476 (`NullPointerException` como caminho de execução) e a 636 (falhar aberto). Os cenários de ataque da própria página da categoria são instrutivos: erro de banco que revela detalhes e facilita reconhecimento para injeção; transação financeira de várias etapas interrompida sem rollback; recurso que fica preso após exceção até esgotar.

**Como aparece no Spring.**

```java
// 1) Falhar aberto
try {
    autorizado = servicoDeLimites.pode(atendente, valor);
} catch (Exception e) {
    autorizado = true;                 // "para não travar o atendimento"
}

// 2) Tratador "amigável" que entrega a infraestrutura
@ExceptionHandler(Exception.class)
Map<String, Object> erro(Exception e) {
    return Map.of("erro", e.getMessage(), "tipo", e.getClass().getName());
}

// 3) Duas escritas sem transação: a primeira fica, a segunda não acontece
contas.debitar(origem, valor);
contas.creditar(destino, valor);       // lança exceção: dinheiro sumiu
```

**Correção.** Falhe fechado em toda decisão de segurança. Um tratador global (`@RestControllerAdvice`) que devolve Problem Details genérico com código de rastreio e registra o detalhe no log. `@Transactional` em operações de várias escritas. Limites explícitos (tamanho de payload, timeouts, paginação máxima) para que condição anormal não vire esgotamento. Passo 8. **Como detectar:** testes que **injetam a falha** (a dependência lança exceção) e conferem o resultado; DAST que manda entradas malformadas e procura `Exception`, `at org.` e nomes de host na resposta; na revisão, todo `catch` merece a pergunta "e depois daqui, o sistema está num estado seguro?".

### Passo 1: SQL injection com JdbcClient

**O que vamos fazer e por quê.** O painel do atendente busca contas de uma agência pelo nome do titular. A versão vulnerável monta o SQL concatenando; a corrigida usa parâmetros. Para o banco, usamos H2 em memória: a falha é de montagem de texto, não de um banco específico, e o mesmo teste funcionaria contra o PostgreSQL com Testcontainers. A dependência de JDBC entrou no `pom.xml` do módulo como `spring-jdbc` (sem o starter), com o H2 só no escopo de teste.

**O que acabou de acontecer.**

- Na versão vulnerável, o texto final é `WHERE agencia = '0001' AND titular = 'x' OR '1'='1'`. Como `AND` tem precedência sobre `OR`, a condição vira "(agência 0001 e titular x) **ou** verdadeiro": todas as quatro linhas voltam, inclusive as da agência 0002. Foi o vazamento do e-mail do pesquisador.
- Na versão corrigida, `:titular` é um marcador. O `JdbcClient` envia o texto da consulta e o valor **separados** ao driver (por baixo, um `PreparedStatement`). O banco procura um titular chamado literalmente `x' OR '1'='1` e não encontra ninguém.
- O quarto teste é o argumento que convence o time de produto: o sobrenome `D'Ávila` **quebra** a versão vulnerável com `BadSqlGrammarException`. SQL injection não é só segurança; é um bug funcional esperando um cliente com apóstrofo no nome.
- Escapar aspas à mão (`replace("'", "''")`) não é a correção. Cada banco tem regras próprias de escape, codificações e modos (barra invertida no MySQL, por exemplo), e a lista de exceções nunca termina. Parâmetro de bind elimina a classe inteira do problema.

<Callout tipo="atencao" titulo="LIKE também precisa de cuidado">
Em `WHERE titular LIKE :prefixo`, o parâmetro protege contra injeção, mas `%` e `_` digitados pelo cliente continuam funcionando como curingas: `%` sozinho lista tudo, e `%a%b%c%...` pode gerar uma consulta cara. Escape os curingas antes de acrescentar o seu `%` (com `ESCAPE '\'` no SQL) e limite o tamanho do termo.
</Callout>

### Passo 2: ordenação dinâmica com allowlist

**O que vamos fazer e por quê.** A listagem aceita `?ordenarPor=saldo`. A tentação é passar o nome da coluna como parâmetro de bind, mas parâmetros substituem **valores**: no `ORDER BY ?`, o banco recebe uma constante (ou, no H2, tenta interpretá-la como número da coluna, como você vê em "Quando dá errado"). Então o time concatena, e a injeção volta. A solução é uma allowlist que traduz nomes **públicos** para trechos de SQL **escritos pela equipe**.

**O que acabou de acontecer.**

- O primeiro teste manda `(SELECT COUNT(*) FROM conta)` como critério de ordenação, e a versão vulnerável executa. É a prova de que o texto do cliente virou SQL: uma subconsulta escrita por quem chama a API rodou no banco. Num banco real, isso permite inferir dados de outras tabelas pela **ordem** do resultado, sem nenhuma mensagem de erro.
- O segundo teste mostra o vazamento que acompanha: um apóstrofo no campo gera `BadSqlGrammarException`, cuja mensagem traz o SQL completo. Se essa mensagem chegar ao cliente (passo 8), o atacante aprende o nome da tabela e das colunas.
- A allowlist expõe **nomes públicos** (`abertura`) que não precisam coincidir com as colunas (`id`). Isso desacopla o contrato da API do esquema do banco e impede ordenar por colunas internas: o teste confere que `id`, uma coluna real, é recusado. A exceção vira 400 com a lista dos nomes aceitos, uma mensagem útil para o cliente legítimo e inútil para o atacante.

Com repositórios derivados e `Pageable`, o Spring Data monta o `ORDER BY` a partir de propriedades da entidade e recusa propriedades inexistentes. O risco volta quando você recebe `Sort` do cliente e o aplica numa `@Query(nativeQuery = true)` ou em SQL próprio. Nesse caso, filtre `sort.stream()` pela mesma allowlist antes de usar.
</Callout>

Se o e-mail contém `\r\n`, quem atacou escreve uma **segunda linha** no arquivo, por exemplo um falso "login-ok" do administrador, que confunde a investigação de um incidente ou dispara (ou esconde) um alerta baseado em texto.

Esse é o caminho recomendado para serviços novos: além de seguro, é o formato que as ferramentas de observabilidade leem.

### Passo 4: path traversal no download de nota fiscal

**O que vamos fazer e por quê.** O endpoint `GET /notas/{arquivo}` devolve o PDF de uma nota. A pasta de notas fica ao lado de uma pasta de configuração com a senha do banco. Vamos provar dois caminhos de fuga e a correção em três camadas.

```text
[INFO] Tests run: 4, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 0.343 s
```

**O que acabou de acontecer.**

- `../config/application.properties` sobe um nível e entra na pasta vizinha: a versão vulnerável devolveu a senha do banco.
- O segundo ataque é menos conhecido e mais perigoso: **`Path.resolve` com um caminho absoluto descarta a pasta base** e devolve o caminho absoluto. Quem só procura `..` na string deixa passar `/etc/passwd` ou `C:\app\config\application.properties`.
- A primeira camada da correção é o **formato fechado**: nome de nota tem letras, dígitos, hífen e `.pdf`. Barra, barra invertida, ponto extra e dois-pontos (unidade do Windows) caem aqui. A validação percorre os caracteres; não precisa de regex.
- A segunda camada é **confinamento**: `resolve` + `normalize` resolve os `..` e `startsWith(pasta)` confere que o resultado continua dentro. O último teste mostra por que tem de ser `Path.startsWith`, que compara **segmentos**, e não `String.startsWith`: como texto, `/dados/notas-antigas/x.pdf` "começa com" `/dados/notas`.
- A terceira camada é o **caminho real**: `toRealPath()` resolve links simbólicos. Sem ela, um link `notas/atalho.pdf → /etc/shadow`, criado por outro processo ou por um upload mal feito, passa pela segunda camada.
- A pasta base também passa por `toRealPath()` no construtor, para que a comparação seja entre caminhos reais dos dois lados.

A melhor correção, porém, está no Javadoc: **não aceite nome de arquivo**. Receba `GET /notas/{id}`, busque a nota no banco, confira que ela pertence a quem pediu (BOLA, aula 11.04) e leia o caminho gravado pelo próprio sistema. Assim a superfície de ataque some. Ao devolver o arquivo, defina `Content-Disposition` com um nome gerado por você e `Content-Type` fixo, como pede o requisito 5.4.1 do ASVS.

### Passo 5: SSRF no cadastro de webhook

**O que vamos fazer e por quê.** Lojistas cadastram uma URL para receber eventos de pagamento. O servidor vai fazer `POST` nessa URL. Se ela apontar para `169.254.169.254` (o serviço de metadados das nuvens), para `localhost:8080/actuator` ou para um banco na rede interna, o servidor vira o braço de quem cadastrou.

**O que acabou de acontecer.**

- A validação por texto aceitou os três truques. `parceiro.com.br.atacante.net` contém o domínio, mas pertence a quem registrou `atacante.net`. Em `https://api.parceiro.com.br@169.254.169.254/`, tudo antes do `@` é **usuário e senha** da URL; o host é o IP de metadados. E `?parceiro.com.br` na query string satisfaz o `contains`.
- A camada 1 usa `java.net.URI`, que separa esquema, usuário, host e porta como o cliente HTTP vai separar. A URL nunca é comparada como texto.
- A camada 2 fecha o esquema em `https` (sem `http`, `file`, `jar`), a porta em 443 e recusa usuário/senha na URL. Cada restrição remove uma família de truques que ninguém precisa num webhook.
- A camada 3 é a allowlist de domínios, com curinga só no começo. IP literal nunca está na lista, então `https://169.254.169.254` cai aqui.
- A camada 4 é a que mais gente esquece: **um domínio permitido pode apontar para dentro**. Quem controla o DNS de `interno.parceiro.com.br` pode fazê-lo resolver para `10.0.0.5`. O validador resolve o nome e recusa se **qualquer** IP for interno: loopback, privados (10/8, 172.16/12, 192.168/16), link-local (169.254/16, onde moram os metadados das nuvens), CGNAT (100.64/10), multicast e, em IPv6, `::1`, `fe80::/10` e `fc00::/7`. O caso `::ffff:169.254.169.254` (IPv4 embrulhado em IPv6) é detectado porque o `InetAddress` já o converte para `Inet4Address`.
- O validador devolve o IP conferido por causa do **DNS rebinding**: entre a validação e a conexão, o atacante troca o registro DNS (com TTL zero) para um IP interno. Se o cliente HTTP resolver de novo, a validação foi inútil. A conexão deve ir para o IP aprovado, mantendo o nome no `Host` e na verificação do certificado; na prática, com um resolvedor customizado no cliente HTTP ou, mais robusto, com um **proxy de saída** que aplica a mesma política na rede.

Dois complementos de produção: **não seguir redirecionamentos** (um `302` para o IP de metadados contorna tudo; no Spring Boot, `spring.http.clients.redirects=dont-follow` configura os clientes HTTP que ele cria) e **limitar a resposta** (timeout curto, tamanho máximo, e nunca devolver o corpo ao lojista).

Use a versão do serviço de metadados que exige token de sessão (na AWS, IMDSv2 obrigatório), dê ao serviço a menor permissão possível e, se o provedor permitir, bloqueie o acesso aos metadados para os contêineres que não precisam dele. Essas medidas não substituem a validação, mas reduzem o estrago se ela falhar.
</Callout>

### Passo 7: desserialização insegura, com Jackson 3 e com o Java nativo

## Quando dá errado

As mensagens abaixo foram copiadas da execução durante a construção desta aula. Cada uma ensina algo sobre a ferramenta.

### O Jackson 3 recusa o polimorfismo por classe

```text
tools.jackson.databind.exc.InvalidDefinitionException: Configured `PolymorphicTypeValidator` (of type `tools.jackson.databind.jsontype.DefaultBaseTypeLimitingValidator`) denies resolution of all subtypes of base type `java.lang.Object` as using too generic base type can open a security hole without checks on subtype: please configure a custom `PolymorphicTypeValidator` for this use case
```

**Como ler:** o Jackson 3 está protegendo você. A base `Object` é genérica demais para aceitar subtipos sem uma lista. **Como corrigir:** não configure um validador permissivo, como a mensagem parece sugerir. Troque `Id.CLASS` por `Id.NAME` com `@JsonSubTypes`, ou estreite a base para uma interface sua. Se precisar mesmo de `Id.CLASS` (dado interno, nunca de fora), use `BasicPolymorphicTypeValidator.builder().allowIfSubType(TipoEspecifico.class)` com a lista exata.

### O LaissezFaireSubTypeValidator sumiu

```text
tools.jackson.databind.jsontype.impl.LaissezFaireSubTypeValidator is not public in tools.jackson.databind.jsontype.impl; cannot be accessed from outside package
```

**Como ler:** código e respostas antigas do Jackson 2 usam esse validador "aceita tudo". No Jackson 3 ele não é mais acessível de fora do pacote. **Como corrigir:** é um sinal para rever o desenho, não para procurar outro jeito de aceitar tudo.

### O filtro de desserialização recusou o próprio carrinho

```text
java.io.InvalidClassException: filter status: REJECTED
	at ...SerializacaoNativaTest.carrinhoLegitimoPassaPeloFiltro(SerializacaoNativaTest.java:30)
```

**Como ler:** a primeira versão da lista não tinha as classes internas de `List.of` nem o `java.lang.Object` (para arrays, o filtro confere o tipo do **elemento**). A mensagem não diz qual classe foi recusada. **Como corrigir:** ligue o log do filtro (o logger `java.io.serialization`, em nível de depuração) ou escreva uma sonda: um filtro que imprime `info.serialClass()` e devolve `UNDECIDED`. Foi assim que a lista final saiu.

### O parser endurecido recusou o DOCTYPE

```text
[Fatal Error] :2:10: DOCTYPE fica desativado quando o recurso "http://apache.org/xml/features/disallow-doctype-decl" é definido como verdadeiro.
```

**Como ler:** é o comportamento esperado, e a mensagem segue o idioma da JVM (em inglês, ela diz que o DOCTYPE não é permitido quando a feature está ligada). **Como corrigir:** nada, se o XML vem de fora. Se um parceiro legítimo envia `DOCTYPE`, peça para remover; se não der, reabra só o `DOCTYPE` e mantenha entidades externas e DTDs remotos desligados. Num teste, confira o nome da feature, não o texto traduzido.

### SQL quebrado com o SQL inteiro na mensagem

```text
org.springframework.jdbc.BadSqlGrammarException: PreparedStatementCallback; bad SQL grammar [SELECT id, titular, agencia, saldo FROM conta WHERE agencia = ? ORDER BY saldo']
```

**Como ler:** além de mostrar a concatenação, a mensagem do Spring carrega o SQL completo. **Como corrigir:** a allowlist do passo 2 resolve a causa; o tratador do passo 8 garante que mensagens assim nunca saiam da aplicação.

### Coluna como parâmetro de bind

A tentativa intuitiva de "parametrizar a coluna", no H2:

```java
jdbc.sql("SELECT id, titular, agencia, saldo FROM conta ORDER BY :coluna DESC").param("coluna", "saldo")
```

```text
org.springframework.dao.DataIntegrityViolationException: PreparedStatementCallback; SQL [SELECT id, titular, agencia, saldo FROM conta ORDER BY ? DESC]; Data conversion error converting "saldo"
Caused by: java.lang.NumberFormatException: For input string: "saldo"
```

**Como ler:** o H2 tenta interpretar o parâmetro do `ORDER BY` como **número da coluna**. Em outros bancos, o parâmetro vira uma constante e a ordenação simplesmente não acontece, sem erro nenhum, o que é pior. **Como corrigir:** allowlist.

```java
if (!nomeValido(arquivo)) throw ...;        // formato
if (!alvo.startsWith(pasta)) throw ...;     // confinamento
if (!dominioPermitido(host)) throw ...;     // lista
if (!publico(ip)) throw ...;                // destino real
String sql = COLUNAS.get(ordenarPor);       // tradução
```
</Comparar>

As regras de bolso, cada uma com a falha que ela evita:

- **Valide no destino, não só na entrada.** Bean Validation no DTO (`@Pattern`, `@Size`) ajuda, mas o mesmo dado pode chegar ao `sql(...)` por outro caminho (uma fila, um job, um import de planilha). A proteção definitiva mora onde o dado é usado: parâmetro de bind no SQL, confinamento no `Files`, validador na chamada HTTP.
- **Não confie em "sanitizar".** Remover `../` da string é denylist disfarçada: `....//` vira `../` depois da remoção. Rejeite o que está fora do formato.
- **Não confie no front.** Quem ataca chama a API com `curl`.
- **Não use o Top 10 como checklist de conformidade.** "Passamos no Top 10" não é verificável; "atendemos ao ASVS nível 2 nos capítulos V1, V5, V8 e V16" é.
- **Não confunda WAF com correção.** Um *Web Application Firewall* compra tempo contra payloads conhecidos; não sabe o que é `ordenarPor` na sua API.
- **Falso positivo de SAST** se marca na ocorrência, com justificativa; não se desliga a regra no projeto.
- **Quando NÃO escrever o validador de SSRF.** Se o produto aceita receber o arquivo em vez da URL (upload de avatar em vez de "cole o link"), aceite o arquivo. Se as chamadas de saída vão para poucos parceiros fixos, a allowlist de URLs completas, sem DNS dinâmico, é mais simples. O validador desta aula é para quando o destino realmente varia por cliente.
- **Quando NÃO usar serialização nativa:** praticamente sempre que o dado cruza processo, rede ou disco compartilhado. Ela só se justifica em código legado que ainda não migrou, e aí com filtro.

## Visão de pleno e sênior: decisões e trade-offs

Saber corrigir um SQL injection é o mínimo. O que se espera de quem é Pleno ou Sênior é **organizar o trabalho de segurança do time**: decidir onde investir, como detectar em escala, como responder quando algo escapa e como justificar o custo.

**Onde colocar cada controle.** Uma defesa vale mais quanto mais perto do destino perigoso ela está e quanto menos depende da memória de quem escreve o código. Um sênior transforma correções pontuais em **componentes do projeto**: um `ClienteHttpDeSaida` que só aceita `DestinoAprovado`, sem redirecionamento e com timeout; um `ArmazemDeArquivos` que só lê por id; um `JsonMapper` configurado num único `@Bean`. E protege essas decisões com testes de arquitetura (o ArchUnit da aula 10.06): "nenhuma classe fora do pacote `saida` usa `RestClient`", "ninguém chama `ObjectInputStream`".

**SAST, DAST, SCA e testes: o que cada um encontra e quanto custa.** SAST roda em cada pull request, é barato e encontra padrões (`sql(` com concatenação, `Id.CLASS`, `MD5`), mas gera falsos positivos e não entende regra de negócio. DAST encontra configuração errada e vazamentos de verdade, mas é lento e só cobre o que alcança. SCA é quase gratuito e cobre a categoria A03, com o custo de triar alertas. Testes como os desta aula encontram só o que você pensou em testar, mas sem falsos positivos e com efeito de regressão. A combinação madura: SAST e SCA bloqueando o merge acima de uma severidade combinada; testes de segurança junto dos funcionais; DAST agendado contra homologação; revisão humana focada nos destinos perigosos. Comece com poucas regras de alta confiança e aumente aos poucos, para o time não aprender a ignorar alertas.

**Triagem.** A pergunta não é "qual a nota CVSS?", e sim "quem alcança isto, com que pré-requisito, e o que expõe?". Uma CVE crítica numa biblioteca usada só num job interno sem entrada externa pode esperar o ciclo normal; um path traversal num endpoint público é incidente.

**Falhar fechado tem custo, e alguém precisa decidir.** Negar todos os estornos quando o serviço de limites cai é seguro, mas para o atendimento. A decisão é uma conversa com o negócio, e as alternativas precisam ser explícitas: limite conservador em cache, fila de aprovação manual, disjuntor (*circuit breaker*) que falha rápido. O inaceitável é a decisão ficar escondida num `catch` que devolve `true`.

**Mensagens de erro: suporte versus segurança.** O código de rastreio resolve o dilema se a operação acha o log pelo código em segundos: log estruturado com o código como campo, retenção adequada e acesso para quem atende o cliente. Sem isso, o time volta a pedir "manda a mensagem completa", e o vazamento volta.

**Resposta a incidente.** Quando o e-mail do pesquisador chega: desde quando a falha existe (o Git responde), foi explorada (os logs de acesso respondem, se tiverem o necessário), quais dados estavam ao alcance, quem precisa ser avisado (a LGPD exige comunicação à ANPD e aos titulares em incidentes com risco relevante) e como eliminar a **classe** de falha, não só a ocorrência. Um `security.txt` com contato faz o próximo pesquisador escrever para você em vez de publicar direto.

**Como justificar para o time.** Funcionam: o custo de um incidente contra uma correção que cabe numa tarde; o fato de que várias correções também são funcionais (o `D'Ávila` do passo 1); e clientes e auditorias que pedem evidência de ASVS. O melhor argumento é um teste vermelho mostrando o ataque funcionando no código de vocês.

**Quando trocar de abordagem.** SQL dinâmico demais pede um construtor de consultas tipado (jOOQ, Criteria API). Validação de SSRF reimplementada em cada serviço pede um proxy de saída centralizado. Serialização nativa em vários caches pede uma migração para JSON, que custa uma vez e encerra a categoria.

## ASVS 5.0 como checklist

O **ASVS** (*Application Security Verification Standard*) é o que transforma "seja seguro" em requisitos verificáveis. A versão atual é a **5.0.0**, com cerca de 350 requisitos em 17 capítulos (de V1, *Encoding and Sanitization*, a V17, *WebRTC*) e três níveis: o **L1** é o mínimo (cerca de 20% dos requisitos), o **L2** é o que a maioria das aplicações deve buscar (L1 e L2 somam cerca de 70%) e o **L3** é para aplicações que precisam demonstrar o nível mais alto de segurança. Cada requisito tem um identificador no formato `v5.0.0-capítulo.seção.requisito`, que você pode citar num pull request ou num critério de aceite.

Os requisitos ligados ao que você praticou:

| 1.5.1 | L1 | parsers XML com configuração restritiva, entidades externas desligadas | passo 6 |

**Como usar no dia a dia.** Escolha o nível com o negócio (uma fintech mira L2, no mínimo) e os capítulos que se aplicam (sem front, V3 sai; sem WebRTC, V17 sai). Transforme os requisitos em critérios de aceite ("dado um nome de arquivo com `../`, então 404, conforme 5.3.2"), num checklist de pull request para os capítulos mais tocados (V1, V5, V8, V16) e em testes com o identificador no comentário, como evidência para auditoria. A cada trimestre, revise o que tem teste, o que depende só de revisão e o que ainda não é atendido. Essa planilha é a resposta quando um cliente grande pergunta "como vocês garantem segurança?".

Perguntas que aparecem para Pleno e Sênior, e o que uma boa resposta contém:

- **"Quais riscos do OWASP Top 10 você já corrigiu?"** Não recite a lista. - **"O que é desserialização insegura e como acontece em Java hoje?"** Bytes escolhendo a classe; gadgets; `ObjectInputStream` sem filtro e Jackson com `Id.CLASS` ou default typing permissivo. Correções: JSON com DTO, `Id.NAME` com subtipos fechados, `ObjectInputFilter` com allowlist. Bônus: o Jackson 3 recusa base `Object` por padrão.
- **"Como você organizaria a segurança no ciclo de desenvolvimento de um time?"** SCA e SAST no CI com política de bloqueio, testes de segurança junto dos funcionais, DAST agendado, ASVS como fonte de requisitos e checklist, modelagem de ameaças nas funcionalidades sensíveis, triagem por alcance e impacto, e componentes seguros por padrão protegidos por testes de arquitetura.

## Checkpoint

O time quer exportar extratos em CSV com `GET /extratos/exportar?ordenarPor=...&colunas=data,valor,descricao`. O cliente escolhe a ordenação e **quais colunas** saem no arquivo. As colunas possíveis são `data`, `valor`, `descricao` e `contraparte`; no banco elas se chamam `criado_em`, `valor`, `descricao` e `nome_contraparte`. O SQL precisa listar as colunas no `SELECT` e ordenar no `ORDER BY`.

**O desafio:** escreva uma classe `ColunasDoExtrato` com um método `String select(String colunasPedidas)` que devolve o trecho `SELECT` seguro (por exemplo, `criado_em AS data, valor AS valor`) e lança uma exceção com mensagem útil para colunas desconhecidas, repetidas ou para uma lista vazia. Depois escreva os testes: um que prova que `valor, (SELECT senha_hash FROM usuario LIMIT 1)` é recusado e outro que prova que a ordem pedida pelo cliente é respeitada. Pense também: o que mais pode dar errado num CSV gerado a partir de dados de clientes?

<details>
<summary>Solução comentada</summary>

```java
public final class ColunasDoExtrato {

    private static final Map<String, String> COLUNAS = Map.of(
            "data", "criado_em",
            "valor", "valor",
            "descricao", "descricao",
            "contraparte", "nome_contraparte");

    private ColunasDoExtrato() {
    }

    public static String select(String colunasPedidas) {
        if (colunasPedidas == null || colunasPedidas.isBlank()) {
            throw new IllegalArgumentException("Informe ao menos uma coluna: " + new TreeSet<>(COLUNAS.keySet()));
        }
        var vistas = new LinkedHashSet<String>();
        var trechos = new ArrayList<String>();
        for (String bruta : colunasPedidas.split(",")) {
            String nome = bruta.strip();
            String coluna = COLUNAS.get(nome);
            if (coluna == null) {
                throw new IllegalArgumentException("Coluna desconhecida. Use: " + new TreeSet<>(COLUNAS.keySet()));
            }
            if (!vistas.add(nome)) {
                throw new IllegalArgumentException("Coluna repetida: " + nome);
            }
            trechos.add(coluna + " AS " + nome);   // os dois lados vêm do mapa, nunca do cliente
        }
        return "SELECT " + String.join(", ", trechos);
    }
}
```

```java
@Test
void recusaSubconsulta() {
    assertThatThrownBy(() -> ColunasDoExtrato.select("valor, (SELECT senha_hash FROM usuario LIMIT 1)"))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessageStartingWith("Coluna desconhecida");
}

@Test
void respeitaAOrdemPedida() {
    assertThat(ColunasDoExtrato.select("valor, data"))
            .isEqualTo("SELECT valor AS valor, criado_em AS data");
}
```

**Por que assim.** O apelido depois do `AS` também é um identificador; ele vem do mapa (a chave já validada), nunca do texto bruto. A mensagem de erro não repete o que o cliente mandou, para não refletir conteúdo arbitrário. A ordenação usa a mesma ideia do passo 2, com o mesmo mapa.

**O que mais pode dar errado no CSV.** *CSV injection* (ou *formula injection*): uma descrição que começa com `=`, `+`, `-` ou `@` é interpretada como fórmula quando o arquivo é aberto numa planilha. Prefixe esses valores com um apóstrofo ou espaço, e sempre escape aspas e separadores. Além disso: limite o período e o número de linhas (A10 e API4), confira que o extrato é da conta de quem pediu (BOLA) e registre a exportação como evento de segurança (A09), porque exportação em massa é um sinal clássico de conta comprometida.

</details>

## Resumo

- O **OWASP Top 10:2025**: A01 Broken Access Control (agora com SSRF), A02 Security Misconfiguration, **A03 Software Supply Chain Failures** (nova), A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures e **A10 Mishandling of Exceptional Conditions** (nova).
- A maioria dos bugs de backend está onde **dado de fora encontra um destino perigoso**: SQL, caminho de arquivo, URL de saída, log, desserializador, parser XML. Revise a partir dos destinos.
- **Injeção:** parâmetro de bind para valores, allowlist para identificadores (`ORDER BY`, colunas), neutralização ou log estruturado contra CRLF.
- **Path traversal:** prefira id a nome; se precisar de nome, formato fechado, `normalize` + `Path.startsWith` e `toRealPath`. `Path.resolve` com caminho absoluto descarta a base.
- **SSRF:** parser, forma, allowlist de domínio, DNS com recusa de faixas internas, conexão no IP conferido, sem redirecionamento.
- **XXE:** `disallow-doctype-decl`; o JDK 25 padrão ainda resolve entidade externa local.
- **Desserialização:** JSON com DTO, `Id.NAME` com subtipos fechados, `ObjectInputFilter` com allowlist; o Jackson 3 recusa `Id.CLASS` em `Object` por padrão, e afrouxar isso reabre a falha.
- **A10:** Problem Details genérico com código de rastreio, detalhe no log, falhar fechado, transação em operações de várias escritas.
- Cada correção entra com o teste que **prova o ataque e o bloqueio**. Para requisitos verificáveis, use o **ASVS 5.0**; para APIs, cruze com o **API Security Top 10 (2023)**.
