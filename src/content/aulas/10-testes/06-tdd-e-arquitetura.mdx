Nas aulas anteriores você escreveu testes para código que já existia. Esta aula fecha o módulo com duas ideias que mudam **quando** e **o quê** você testa.

A primeira é uma disciplina: **escrever o teste antes do código** (TDD, *Test-Driven Development*). O teste vira a especificação executável, cada linha de produção nasce para fazer um teste passar, e o design sai mais simples de usar, porque o primeiro cliente da classe é o próprio teste. A segunda é uma ferramenta: o **ArchUnit**, que transforma decisões de arquitetura ("controller não fala com o repositório", "o domínio não depende do Spring") em testes que quebram o build. As duas têm o mesmo espírito: **o que importa precisa ser verificado automaticamente, não lembrado**.

Na parte 1, você constrói com TDD um **simulador de parcelamento** em sete ciclos, vendo a falha real de cada teste antes de escrever a linha que o faz passar. Na parte 2, escreve seis regras de arquitetura para a API de um **consultório**, prova que cada uma consegue falhar e aprende a adotá-las num sistema legado.

## A intuição: a corda do alpinista e o fiscal da obra

Um alpinista não sobe a parede inteira para só depois pensar na segurança: a cada poucos metros, prende a corda num grampo. Se escorregar, cai só até o último grampo. E o intervalo depende do trecho: curto onde é difícil, maior onde é fácil.

TDD é isso. Cada teste é um grampo: você escreve um teste pequeno, faz o código passar e está preso de novo. Se a próxima mudança der errado, você volta só até o último verde. Nos trechos difíceis (centavos, virada de mês), os passos encurtam: são os **baby steps**.

O ArchUnit é outra proteção. A planta do prédio diz que a fiação não passa pela coluna estrutural; com prazo apertado, alguém fura a coluna "só desta vez", e dez atalhos depois o prédio não é mais o da planta. O ArchUnit é o fiscal que confere a obra contra a planta a cada build e reprova a entrega que fura a coluna, dizendo onde e por quê.

## Vocabulário

| Termo | O que significa |
|---|---|
| **TDD** | Desenvolvimento guiado por testes: o teste é escrito **antes** do código que ele verifica, um de cada vez |
| **Vermelho** | Existe um teste que falha. Não compilar também conta como vermelho |
| **Verde** | Todos os testes passam, inclusive o novo |
| **Refatorar** | Mudar a estrutura do código (nomes, extrações, duplicação) sem mudar o comportamento, com os testes verdes o tempo todo |
| **Baby steps** | Passos pequenos: um teste por vez, o menor código possível. O tamanho do passo diminui quando o terreno fica difícil |
| **Fake it** ("finja até conseguir") | No verde, devolver uma resposta fixa que faz o teste passar |
| **Triangulação** | Um segundo exemplo que a resposta fixa não satisfaz, forçando a generalização |
| **Implementação óbvia** | Quando a solução é clara e o passo é seguro, escrevê-la direto |
| **ArchUnit** / **ArchRule** | Biblioteca que lê o bytecode e verifica regras de arquitetura como testes JUnit / uma dessas regras |
| **Camada** e **fatia** (*layer*, *slice*) | Grupos de classes definidos por pacote, usados nas regras de acesso e de ciclos |
| **FreezingArchRule** | Envoltório que grava as violações atuais de uma regra e passa a acusar só as novas |

## Parte 1: TDD de verdade

### A funcionalidade que vamos construir

A loja do seu time vai mostrar, na página do produto, uma simulação de parcelamento: "R$ 100,00 em 3x de R$ 33,34 + R$ 33,33 + R$ 33,33, vencendo em 10/04, 10/05 e 10/06". O time de produto escreveu as regras:

1. A compra pode ser à vista (1 parcela) ou parcelada em até **12** parcelas.
2. As parcelas têm valor igual; os centavos que sobram da divisão vão para a **primeira** parcela. A soma das parcelas é **sempre** o total, nenhum centavo a mais ou a menos.
3. A parcela N vence N meses depois da compra. Uma compra no dia 31 vence no último dia dos meses mais curtos (28/02, 30/04).
4. Com mais de uma parcela, cada uma tem no mínimo **R$ 5,00**.

Nada disso existe ainda. É o cenário ideal para TDD: regras claras, cheias de bordas e fáceis de expressar como exemplos.

### Passo 1 (ciclo 1, vermelho): o primeiro teste, antes de qualquer classe

**O que vamos fazer e por quê.** O teste mais simples possível: à vista, uma parcela com o total. Parece bobo, e é de propósito: o primeiro teste serve para desenhar a **API** (nome da classe, do método, o que recebe e devolve) do ponto de vista de quem vai **usar** a classe.

```java
class SimuladorDeParcelamentoTest {

    SimuladorDeParcelamento simulador = new SimuladorDeParcelamento();

    @Test
    void aVistaEhUmaParcelaComOTotal() {
        List<Parcela> parcelas = simulador.simular(new BigDecimal("100.00"), 1);

        assertThat(parcelas).extracting(Parcela::valor)
                .containsExactly(new BigDecimal("100.00"));
    }
}
```

Decisões tomadas só por escrever o teste: a classe se chama `SimuladorDeParcelamento`; o método `simular` recebe o total como `BigDecimal` (dinheiro nunca é `double`) e a quantidade como `int`; e devolve uma lista de `Parcela`, com pelo menos um `valor`. Rode:

### Passo 2 (ciclo 1, verde): fake it

**O que vamos fazer e por quê.** O mínimo para passar. Não "o que eu sei que vai ser necessário", mas o mínimo **para este teste**:

```java
public List<Parcela> simular(BigDecimal total, int quantidade) {
    return List.of(new Parcela(1, total));
}
```

```text
[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

**O que acabou de acontecer.** O código ignora `quantidade`. Para a regra final, está errado; para a especificação escrita até agora (um teste), está completo. Esse é o *fake it*: a resposta fixa leva ao verde rápido e deixa a pergunta "como dividir?" para quando um teste a fizer.

### Passo 3 (ciclo 2): triangulação

**O que vamos fazer e por quê.** A resposta fixa só cai quando um **segundo exemplo** a contradiz. É isso que "triangular" quer dizer: com dois pontos, você é obrigado a traçar a reta.

```java
@Test
void duasParcelasDividemOTotalAoMeio() {
    List<Parcela> parcelas = simulador.simular(new BigDecimal("100.00"), 2);

    assertThat(parcelas).extracting(Parcela::valor)
            .containsExactly(new BigDecimal("50.00"), new BigDecimal("50.00"));
}
```

```text

  [50.00, 50.00]
but some elements were not found:
  [50.00, 50.00]
```

A mensagem do AssertJ diz tudo: veio uma parcela de 100,00, eram esperadas duas de 50,00. O verde agora exige dividir de verdade:

```java
public List<Parcela> simular(BigDecimal total, int quantidade) {
    BigDecimal valor = total.divide(BigDecimal.valueOf(quantidade));
    List<Parcela> parcelas = new ArrayList<>();
    for (int numero = 1; numero <= quantidade; numero++) {
        parcelas.add(new Parcela(numero, valor));
    }
    return parcelas;
}
```

**O que acabou de acontecer.** `100.00 / 2` deu `50.00`, com duas casas: numa divisão exata, o `divide` mantém a escala do dividendo. Isso importa porque `containsExactly` usa `equals`, e para `BigDecimal.equals` `50.0` e `50.00` são **diferentes**. E se a divisão não for exata? O próximo teste pergunta.

### Passo 4 (ciclo 3): os centavos, e o verde que não chegou de primeira

**O que vamos fazer e por quê.** A regra dos centavos é a parte difícil da funcionalidade, então o passo encurta. Um exemplo só, o clássico: R$ 100,00 em 3x.

```java
@Test
void centavosQueSobramVaoParaAPrimeiraParcela() {
    List<Parcela> parcelas = simulador.simular(new BigDecimal("100.00"), 3);

    assertThat(parcelas).extracting(Parcela::valor).containsExactly(
            new BigDecimal("33.34"), new BigDecimal("33.33"), new BigDecimal("33.33"));
}
```


Repare no `<<< ERROR!` em vez de `<<< FAILURE!`: o código **lançou uma exceção** antes da asserção. `divide` sem arredondamento exige resultado exato, e 100/3 é uma dízima. A tentação é arredondar para duas casas:

A exceção sumiu, mas o teste continua vermelho: três vezes 33,33 são 99,99, e **um centavo desapareceu** (em cada venda parcelada, até a contabilidade achar a diferença). Sem o teste, essa versão iria para produção, porque "parece certa".

A saída é trabalhar em **centavos**, que são inteiros: 10.000 centavos divididos por 3 dão 3.333, com resto 1, que vai para a primeira parcela.

```java
public List<Parcela> simular(BigDecimal total, int quantidade) {
    long centavos = total.movePointRight(2).longValueExact();
    long base = centavos / quantidade;
    long resto = centavos % quantidade;
    List<Parcela> parcelas = new ArrayList<>();
    for (int numero = 1; numero <= quantidade; numero++) {
        long valor = numero == 1 ? base + resto : base;
        parcelas.add(new Parcela(numero, BigDecimal.valueOf(valor).movePointLeft(2)));
    }
    return parcelas;
}
```

```text
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

**O que acabou de acontecer.** `movePointRight(2)` transforma 100.00 em 10000; `longValueExact()` **lança exceção** se sobrar fração (100.005 não é dinheiro válido, e é melhor falhar alto do que truncar em silêncio). Divisão inteira (`/`) e resto (`%`) fazem o resto sem arredondamento. Os dois testes antigos continuam verdes: a rede confirmou que a troca de algoritmo não quebrou nada.

### Passo 5 (ciclo 3, refatorar): com tudo verde, arrume a casa

**O que vamos fazer e por quê.** O código funciona, mas lê mal: conversões misturadas com a regra, nomes vagos. E os testes repetem `new BigDecimal(...)` em toda linha. Refatorar é a etapa que mais se pula, e é a que paga o TDD.

O código de produção depois da refatoração:

```java
public List<Parcela> simular(BigDecimal total, int quantidade) {
    long centavos = emCentavos(total);
    long valorBase = centavos / quantidade;
    long sobra = centavos % quantidade;

    List<Parcela> parcelas = new ArrayList<>(quantidade);
    for (int numero = 1; numero <= quantidade; numero++) {
        long valor = numero == 1 ? valorBase + sobra : valorBase;
        parcelas.add(new Parcela(numero, emReais(valor)));
    }
    return List.copyOf(parcelas);
}

private static long emCentavos(BigDecimal valor) {
    return valor.movePointRight(2).longValueExact();
}

private static BigDecimal emReais(long centavos) {
    return BigDecimal.valueOf(centavos, 2);
}
```

E os testes também, porque teste é código e merece o mesmo cuidado:

```java
@Test
void centavosQueSobramVaoParaAPrimeiraParcela() {
    assertThat(valoresDe("100.00", 3)).containsExactly(reais("33.34", "33.33", "33.33"));
}

private List<BigDecimal> valoresDe(String total, int quantidade) {
    return simulador.simular(new BigDecimal(total), quantidade).stream()
            .map(Parcela::valor)
            .toList();
}

private static BigDecimal[] reais(String... valores) {
    return Arrays.stream(valores).map(BigDecimal::new).toArray(BigDecimal[]::new);
}
```

```text
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

**O que acabou de acontecer.** Nenhum comportamento mudou, e os testes provam isso. `BigDecimal.valueOf(centavos, 2)` cria o valor com escala 2 (3334 vira 33.34); `List.copyOf` devolve uma lista imutável. Nos testes, cada caso virou uma linha que se lê como a regra. Regra de ouro: **rode os testes a cada mudancinha**; se algo ficar vermelho, você sabe qual foi.

### Passo 6 (ciclo 4): o teste que nasce verde

**O que vamos fazer e por quê.** A regra 2 diz que a soma das parcelas é **sempre** o total. Até aqui ela foi verificada em um exemplo. Vamos cobrir vários totais e quantidades de uma vez, com um teste parametrizado (aula 2):

```java
@ParameterizedTest(name = "{0} em {1}x")
@CsvSource({"100.00, 3", "999.99, 7", "1500.00, 12", "10.01, 2", "59.99, 11"})
void aSomaDasParcelasEhSempreOTotal(String total, int quantidade) {
    BigDecimal soma = valoresDe(total, quantidade).stream().reduce(BigDecimal.ZERO, BigDecimal::add);

    assertThat(soma).isEqualByComparingTo(total);
}
```

```text
[INFO] Tests run: 8, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

**O que acabou de acontecer.** Passou de primeira, sem vermelho. Armadilha: **um teste que nunca falhou não provou que consegue falhar**. A saída é sabotar o código por um minuto: trocamos a linha do valor por `long valor = valorBase;` (a sobra some) e rodamos:

```text
[ERROR] Tests run: 8, Failures: 5, Errors: 0, Skipped: 0 <<< FAILURE!
[ERROR] …aSomaDasParcelasEhSempreOTotal(String, int)[1] <<< FAILURE!
expected: 100.00
 but was: 99.99
[ERROR] …aSomaDasParcelasEhSempreOTotal(String, int)[2] <<< FAILURE!
expected: 999.99
 but was: 999.95
[ERROR] …aSomaDasParcelasEhSempreOTotal(String, int)[4] <<< FAILURE!
expected: 10.01
 but was: 10.00
[ERROR] …aSomaDasParcelasEhSempreOTotal(String, int)[5] <<< FAILURE!
expected: 59.99
 but was: 59.95
[ERROR] …centavosQueSobramVaoParaAPrimeiraParcela <<< FAILURE!
```

### TDD e design: o teste como primeiro cliente

O passo 8 mostrou o efeito mais importante do TDD, e o menos comentado: **testabilidade força um design melhor**. Compare as duas versões do simulador:

<Comparar antes="O código decide sozinho que dia é hoje" depois="O relógio chega de fora">
```java
public class SimuladorDeParcelamento {

    public List<Parcela> simular(BigDecimal total, int n) {
        LocalDate hoje = LocalDate.now();   // relógio do sistema
        // ...
    }
}

// No teste: qual data esperar?
// Muda todo dia. Teste com data "calculada"
// repete a lógica do código e prova nada.
```

```java
public class SimuladorDeParcelamento {

    private final Clock relogio;

    public SimuladorDeParcelamento(Clock relogio) {
        this.relogio = relogio;
    }
    // ... LocalDate.now(relogio)
}

// No teste: Clock.fixed(...) em 31/01/2026.
// Em produção: um @Bean Clock do sistema.
```
</Comparar>

Quem escreve o código primeiro chega naturalmente à versão da esquerda: funciona e é mais curta. Quem escreve o teste primeiro **não consegue** escrevê-la, porque o teste esbarra em "que dia é hoje?" antes da primeira linha de produção. O mesmo vale para o gateway, o repositório, o gerador de UUID: o teste força cada dependência a chegar pelo construtor. É a injeção de dependência do módulo 8, exigida pelo teste, não por um framework.

Outros sinais de design que o TDD traz à tona:

- **Teste difícil de escrever é um alarme.** Vinte linhas de cenário e oito mocks indicam uma classe fazendo coisas demais, e com TDD você sente isso **antes** de ela existir.
- **A API nasce do uso**, do ponto de vista de quem chama, e não do lado de dentro.
- **Nada de código especulativo.** Se nenhum teste pediu juros, não há juros.

### Quando TDD ajuda e quando atrapalha

| Ajuda muito | Atrapalha ou não compensa |
|---|---|
| Regras de negócio com casos claros: cálculos, estados, validações, datas | Exploração: você ainda não sabe o que está construindo (um *spike*, um protótipo) |
| Correção de bug: primeiro o teste que reproduz o bug, depois a correção | Código de cola trivial: configuração, DTOs, mapeamentos campo a campo |
| APIs que outras pessoas vão usar | Integração com um SDK que você ainda não entende: aprenda como ele se comporta primeiro |
| Bordas perigosas: dinheiro, fusos, arredondamento | Interfaces visuais, em que o "certo" é decidido olhando |

O protótipo exploratório **se joga fora**: quando você entende o problema, recomeça com TDD. E, mesmo sem TDD estrito, um hábito vale ouro: **todo bug corrigido ganha um teste que o reproduz**, escrito antes da correção. Ele falha (o bug existe), passa (a correção funciona) e impede que o bug volte.

<Callout tipo="erro" titulo="As formas mais comuns de fazer TDD errado">
- **Vários testes de uma vez**, depois todo o código: quando algo falha, você não sabe qual mudança causou.
- **Pular o vermelho**: o teste nunca provou que consegue falhar (lembre do caso `-1` do passo 7).
- **Pular a refatoração**: em um mês, a suíte protege um código que ninguém quer tocar.
- **Testar a implementação**: um teste que verifica que `emCentavos` foi chamado quebraria na refatoração do passo 5 sem nenhum comportamento ter mudado.
</Callout>

### Por que a arquitetura se degrada

#### Passo 1: importar as classes com @AnalyzeClasses

**O que vamos fazer e por quê.** O ArchUnit não lê o código-fonte: **importa o bytecode** e monta um modelo das classes, campos, métodos e de quem chama quem. `@AnalyzeClasses` diz o que importar:

```java
@AnalyzeClasses(
        packages = "dev.trilhajava.m10.aulas.arquitetura.consultorio",
        importOptions = ImportOption.DoNotIncludeTests.class)
class ArquiteturaDoConsultorioTest {
    // as regras vêm aqui, cada uma num campo @ArchTest
}
```

**O que acabou de acontecer.**

- `packages` importa o pacote e os subpacotes. O resto (o `legado`, as bibliotecas) só aparece como **destino** de dependências.
- `ImportOption.DoNotIncludeTests` deixa de fora as classes de `src/test/java`: um teste que usa um repositório direto (normal num teste) não vira violação de camadas. Há outras opções prontas, como `DoNotIncludeJars`.
- A importação é a parte cara, e o ArchUnit a guarda em cache para todas as regras da classe.
- Cada regra é um campo `static final ArchRule` com `@ArchTest`; para o JUnit, cada campo vira um teste.

#### Passo 2: a regra de camadas

**O que vamos fazer e por quê.** A regra mais importante é a da figura: quem pode acessar quem. O arquivo completo já tem as seis regras; olhe por enquanto só as linhas destacadas.

<CodigoJava caminho="m10-testes/aulas/src/test/java/dev/trilhajava/m10/aulas/arquitetura/ArquiteturaDoConsultorioTest.java" semImports destacar="10-19" />

**O que acabou de acontecer, linha a linha.**

- `consideringOnlyDependenciesInLayers()`: só contam as dependências **entre** as camadas declaradas; a web usar `java.time` ou o Spring não interessa a esta regra.
- `.layer("Web").definedBy("..consultorio.web..")` nomeia uma camada por um padrão de pacote. Os dois pontos significam "qualquer quantidade de pacotes", então o padrão casa com `…arquitetura.consultorio.web` e seus subpacotes.
- `mayNotBeAccessedByAnyLayer()` na web (quem a chama é o HTTP) e na persistência (quem a encontra é o Spring, que injeta a `AgendaEmMemoria` onde se pede uma `Agenda`); `mayOnlyBeAccessedByLayers("Web")` na aplicação. O domínio pode ser usado por todos.
- `.because(...)` entra na mensagem de erro e transforma "o build quebrou" em "entendi o motivo".

#### Passo 3: dependências proibidas

**O que vamos fazer e por quê.** Algumas decisões dizem o que uma parte do código **nunca** deve usar. As linhas 21 a 33 do arquivo acima têm duas:

- `DOMINIO_SEM_SPRING` se lê como uma frase: nenhuma classe do domínio deve depender de classes de `org.springframework..`. O domínio precisa sobreviver a uma troca de framework e ser testado sem nenhum.
- `TEMPO_SO_PELO_RELOGIO`: `callMethod(LocalDate.class, "now")`, com `orShould()` para `LocalDateTime` e `Instant`. Depois do nome vêm os **tipos dos argumentos**; como não passamos nenhum, a regra casa só com o `now()` **sem argumentos**, e o `now(clock)` continua liberado. É o passo 8 da parte 1 virando regra do projeto.

A espinha de quase toda regra é `classes()` ou `noClasses()` → `that()` (quais classes) → `should()` (o que devem ou não fazer). Há outros pontos de partida (`noMethods()`, `noFields()`...), e o autocompletar da IDE guia o resto.

#### Passo 4: ciclos entre módulos com slices

**O que vamos fazer e por quê.** `agenda` pode depender de `paciente`; o contrário criaria um **ciclo**, e nenhum dos dois poderia ser entendido ou extraído sem o outro. A regra das linhas 35 a 40 usa `slices().matching("..consultorio.dominio.(*)..")`: o `(*)` é um grupo de captura, e cada subpacote de `dominio` vira uma **fatia** (`agenda`, `paciente`). `beFreeOfCycles()` falha diante de qualquer ciclo entre fatias, de qualquer tamanho.

#### Passo 5: convenções de nome e de anotação

**O que vamos fazer e por quê.** Convenções permitem achar as coisas. As linhas 42 a 55:

- `CONTROLLERS`: classes com `@RestController` devem terminar em `Controller` **e** morar no pacote `web` (o `andShould()` junta as duas exigências).
- `REPOSITORIOS`: classes concretas da persistência devem ter `@Repository`, que também faz o Spring traduzir exceções do banco para `DataAccessException`.

### Código legado: FreezingArchRule

**O problema.** Adotar a regra de camadas num sistema com 300 violações quebra o build no mesmo dia, e ninguém vai parar o time para corrigir tudo. Desistir da regra deixa as violações virarem 400. O **FreezingArchRule** é o meio-termo: **as violações existentes ficam registradas e toleradas; qualquer violação nova quebra o build**. A dívida para de crescer no primeiro dia.

#### Passo 1: congelar as regras do legado

A regra congelada é a mesma regra, envolvida em `freeze(...)`:

Na primeira execução, sem nenhuma configuração, o ArchUnit se recusa a continuar:

```text

com.tngtech.archunit.library.freeze.StoreInitializationFailedException: Creating new violation store is disabled (enable by configuration freeze.store.default.allowStoreCreation=true)
```

**O que isso significa.** As violações congeladas ficam num **store** (por padrão, uma pasta de arquivos de texto), e criar um store novo vem desligado de propósito: senão, um store apagado por engano seria recriado no CI com **todas** as violações atuais, em silêncio.

#### Passo 2: configurar e criar o store

A configuração fica em `archunit.properties`, na raiz do classpath de testes (`src/test/resources`). Na primeira execução, local, ligamos a criação e escolhemos o caminho:

```properties

freeze.store.default.allowStoreCreation=true
```

```text

```

A pasta `archunit_store` apareceu com um `stored.rules` (que liga a descrição de cada regra a um identificador) e um arquivo por regra, com uma violação por linha. O passo final é **commitar** a pasta e voltar `allowStoreCreation` para `false`. O arquivo do projeto:

```properties

freeze.store.default.path=src/test/resources/archunit_store
# true só na primeira execução, para criar o store; depois de commitá-lo, fica false:
# assim o CI nunca cria, em silêncio, um store novo que aceitaria todas as violações.
freeze.store.default.allowStoreCreation=false
```

### Armadilhas e quando NÃO usar

As regras de bolso:

- **Toda regra precisa ter falhado uma vez**, num exemplo de violação mantido no projeto ou numa sabotagem antes do commit.
- **Sempre `because`.** Regra sem motivo é contornada; regra com motivo é discutida.
- **Poucas regras, e fortes.** Camadas, ciclos e o domínio sem framework dão a maior parte do valor; cinquenta regras de nome viram `@ArchIgnore`.
- **Estrutura, não estilo.** Formatação é do formatador; vulnerabilidades, do scanner de dependências. ArchUnit é para quem depende de quem.
- **Não congele regras em projeto novo.** `FreezingArchRule` é para legado; num projeto novo, a regra entra estrita no primeiro commit.
- **Com Spring Modulith** (módulo 13), a verificação de módulos e ciclos vem pronta, construída sobre o ArchUnit.

## Resumo

- **TDD**: vermelho (um teste que falha pelo motivo certo), verde (o mínimo para passar), refatorar (código e testes, com tudo verde), em ciclos de minutos.
- **Fake it** leva ao verde rápido; **triangulação** força a generalização; **baby steps** encurtam no terreno difícil.
- Teste que nasce verde deve ser **sabotado** uma vez. Confira a mensagem das exceções, não só o tipo.
- Escrever o teste primeiro força **dependências explícitas** (o `Clock` no construtor). Teste difícil de escrever é alarme de design.
- TDD brilha em regras de negócio, bugs e APIs; não compensa em exploração e cola trivial. Todo bug corrigido ganha um teste.
- **ArchUnit** importa o bytecode (`@AnalyzeClasses`, `ImportOption`) e verifica camadas, dependências proibidas, ciclos (`slices`) e convenções, sempre com `because`.
- A violação traz a regra, a contagem e uma linha por dependência. Toda regra precisa ter falhado contra um exemplo de violação.
- **FreezingArchRule** adota regras no legado: aceita as violações antigas (store versionado) e acusa só as novas.
