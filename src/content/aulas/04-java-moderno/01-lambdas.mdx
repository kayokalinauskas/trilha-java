## De classe anônima a lambda

No módulo 02, o teste do exercício 02.02 criou uma forma nova assim:

```java
Forma hexagono = new Forma() {
    @Override public double area() { return 2.598; }
    @Override public String descricao() { return "Hexágono"; }
};
```

É uma **classe anônima**: implementa uma interface ali mesmo, sem nome. Quando a interface tem **um único método abstrato**, o Java permite uma forma muito mais curta, a **lambda**:

```java
Comparator<Pedido> porValor = new Comparator<>() {             // antes do Java 8
    @Override
    public int compare(Pedido a, Pedido b) {
        return a.valor().compareTo(b.valor());
    }
};

Comparator<Pedido> porValor = (a, b) -> a.valor().compareTo(b.valor());   // lambda
```

A sintaxe:

```java
x -> x * 2                          // um parâmetro: parênteses opcionais
(a, b) -> a + b                     // vários parâmetros
() -> LocalDate.now()               // nenhum parâmetro
(Pedido p) -> p.pago()              // tipo explícito (raramente necessário)
p -> {                              // corpo com várias instruções: chaves e return
    BigDecimal taxa = calcularTaxa(p);
    return p.valor().add(taxa);
}
```

## Interfaces funcionais

Uma interface com exatamente um método abstrato é uma **interface funcional**. A anotação `@FunctionalInterface` é opcional, mas faz o compilador reclamar se alguém adicionar um segundo método abstrato.

O pacote `java.util.function` traz as mais usadas:

| Interface | Método | Assinatura | Exemplo |
|---|---|---|---|
| `Function<T, R>` | `apply` | T → R | `Pedido::valor` |
| `BiFunction<T, U, R>` | `apply` | (T, U) → R | `BigDecimal::add` |
| `Predicate<T>` | `test` | T → boolean | `p -> p.valor() > 100` |
| `Supplier<T>` | `get` | () → T | `ArrayList::new` |
| `Consumer<T>` | `accept` | T → (nada) | `System.out::println` |
| `UnaryOperator<T>` | `apply` | T → T | `String::strip` |
| `BinaryOperator<T>` | `apply` | (T, T) → T | `Integer::sum` |

Existem também versões para primitivos, que evitam o custo de *boxing*: `IntPredicate`, `ToIntFunction<T>`, `IntUnaryOperator`, `LongSupplier`…

<Callout tipo="dica" titulo="Não decore a tabela">
Pergunte-se: "recebe o quê e devolve o quê?". Recebe um e devolve outro → `Function`. Devolve `boolean` → `Predicate`. Não recebe nada → `Supplier`. Não devolve nada → `Consumer`.
</Callout>

## Method references

Quando a lambda só chama um método existente, dá para referenciá-lo diretamente com `::`:

| Tipo | Lambda equivalente | Method reference |
|---|---|---|
| Método estático | `s -> Integer.parseInt(s)` | `Integer::parseInt` |
| Método de um objeto específico | `x -> System.out.println(x)` | `System.out::println` |
| Método de instância do próprio parâmetro | `p -> p.valor()` | `Pedido::valor` |
| Construtor | `() -> new ArrayList<>()` | `ArrayList::new` |

O terceiro caso é o mais comum e o que mais confunde: `Pedido::valor` significa "dado um pedido, chame `valor()` nele". É por isso que `Comparator.comparing(Pedido::valor)` funciona.

## Closures e "effectively final"

Uma lambda pode usar variáveis do método onde foi criada — ela as **captura**:

```java
BigDecimal limite = new BigDecimal("500");
Predicate<Pedido> acimaDoLimite = p -> p.valor().compareTo(limite) > 0;   // captura "limite"
```

Mas há uma regra: a variável capturada precisa ser **final** ou **effectively final** (nunca reatribuída):

```java
int contador = 0;
pedidos.forEach(p -> contador++);   // não compila: contador é reatribuída
```

O motivo: a lambda guarda uma **cópia do valor**, e ela pode rodar depois, em outro momento ou em outra thread. Se a variável pudesse mudar, a lambda enxergaria um valor desatualizado. A solução não é "driblar" a regra com um array de um elemento; é usar a ferramenta certa, como `count()` de uma Stream (próxima aula).

<Callout tipo="erro" titulo="Lambdas com efeito colateral">
Lambdas passadas para `filter`, `map` e `Comparator` devem ser **puras**: calculam e devolvem, sem alterar nada fora delas. Um `map` que grava no banco ou incrementa um contador externo é um bug esperando para acontecer, especialmente com streams paralelas.
</Callout>

## Fábricas de comportamento

Métodos que **devolvem** lambdas são uma técnica poderosa para montar regras configuráveis:

```java
static Predicate<Proposta> scoreMinimo(int minimo) {
    return p -> p.score() >= minimo;
}

static Predicate<Proposta> rendaMinima(BigDecimal minimo) {
    return p -> p.rendaMensal().compareTo(minimo) >= 0;
}

Predicate<Proposta> politica = scoreMinimo(600).and(rendaMinima(new BigDecimal("1500")));
```

É exatamente o que você vai construir no exercício 04.03: um motor de regras de crédito em que cada regra é um `Predicate`, e regras novas entram sem mudar o motor.

## Compondo funções

As interfaces funcionais trazem métodos `default` para combinação:

```java
Predicate<Pedido> pago = Pedido::pago;
Predicate<Pedido> grande = p -> p.valor().compareTo(MIL) >= 0;

pago.and(grande);          // os dois
pago.or(grande);           // qualquer um
grande.negate();           // o contrário
Predicate.not(Pedido::pago); // útil com method references

Function<String, String> limpar = String::strip;
Function<String, String> normalizar = limpar.andThen(String::toLowerCase);   // strip, depois lower
normalizar.apply("  PIX ");   // "pix"

Comparator<Pedido> ordem = Comparator.comparing(Pedido::cliente).thenComparing(Pedido::data).reversed();
```

## Resumo

- Uma **lambda** implementa uma **interface funcional** (um único método abstrato) de forma concisa.
- `Function`, `Predicate`, `Supplier`, `Consumer` e seus parentes cobrem quase todos os casos.
- **Method references** (`Classe::metodo`) deixam lambdas simples ainda mais legíveis.
- Variáveis capturadas precisam ser **effectively final**; lambdas devem ser **puras**.
- Funções se **compõem** (`and`, `or`, `negate`, `andThen`, `thenComparing`) e podem ser **fabricadas** por métodos.
