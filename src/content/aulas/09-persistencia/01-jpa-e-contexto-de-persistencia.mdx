No módulo 07 você escreveu SQL e JDBC na mão: cada consulta, cada `ResultSet` convertido em objeto, cada `UPDATE` montado campo a campo. Um **ORM** (*Object-Relational Mapper*) automatiza essa tradução entre objetos Java e tabelas. É produtivo — e perigoso para quem não sabe o que ele faz por baixo. Esta aula é sobre o "por baixo".

## JPA, Hibernate e Spring Data

| Camada | O que é | Você usa para |
|---|---|---|
| **Jakarta Persistence (JPA)** | a especificação (`jakarta.persistence.*`) | anotações (`@Entity`, `@Id`…), `EntityManager`, JPQL |
| **Hibernate ORM** | a implementação (versão 7 no Boot 4) | o motor: gera SQL, gerencia cache, faz dirty checking |
| **Spring Data JPA** | camada de produtividade | repositórios por interface, consultas derivadas do nome, paginação |

Com o `spring-boot-starter-data-jpa`, o Boot configura o pool de conexões (HikariCP), o Hibernate e o `EntityManager`, e cria implementações para as suas interfaces de repositório.

## Mapeando uma entidade

```java
@Entity
@Table(name = "conta")
public class Conta {

    @Id
    private UUID id;                                   // chave primária

    @Column(nullable = false, length = 120)
    private String titular;

    @Convert(converter = CpfConverter.class)           // value object ↔ coluna texto
    @Column(nullable = false, length = 11)
    private Cpf cpf;

    @Enumerated(EnumType.STRING)                       // grava "CORRENTE", não 0
    @Column(nullable = false, length = 10)
    private TipoConta tipo;

    @Column(nullable = false, precision = 15, scale = 2)
    private BigDecimal saldo;

    private Instant criadaEm;                          // → criada_em (a estratégia do Spring converte o nome)

    @Version
    private long versao;                               // lock otimista (aula 6)

    protected Conta() { }                              // o JPA exige um construtor sem argumentos

    public Conta(UUID id, String titular, Cpf cpf, TipoConta tipo, Instant criadaEm) { ... }
}
```

Algumas decisões que importam:

- **Identificadores**: `IDENTITY` (a coluna gera o número; simples) ou `SEQUENCE` (permite *batch insert*; preferido no PostgreSQL para alto volume), ou **UUID** gerado pela aplicação (não revela volume nem permite adivinhar `id + 1`; ótimo em APIs públicas e sistemas distribuídos — o UUID v7, ordenado pelo tempo, reduz a fragmentação do índice).
- **`EnumType.STRING` sempre**: `ORDINAL` grava a posição, e alguém que reordena o enum corrompe os dados.
- **Construtor `protected` sem argumentos** para o Hibernate, e um construtor público com o que é obrigatório para você: a entidade nasce válida.
- **Sem setters públicos** para tudo: métodos de negócio (`depositar`, `sacar`) mantêm as regras dentro da entidade.
- **Records não podem ser entidades** (precisam de estado mutável e proxy), mas funcionam como **embeddables** e como **projeções** de consulta.

<Callout tipo="dica" titulo="ddl-auto: validate, e quem cria o schema é o Flyway">
Em projetos reais, `spring.jpa.hibernate.ddl-auto` fica em `validate` (ou `none`): o schema é criado e evoluído por migrações versionadas (aula 6), e o Hibernate apenas **confere** se as entidades batem com as tabelas, falhando na subida se não baterem. `create-drop` e `update` servem para protótipos, nunca para produção.
</Callout>

## O contexto de persistência

O conceito mais importante do JPA é o **contexto de persistência** (*persistence context*): um mapa das entidades que o `EntityManager` está **gerenciando** naquela unidade de trabalho — no Spring, em geral, **uma transação**.

### Dirty checking: o UPDATE que você não escreveu

```java
@Transactional
public Conta depositar(UUID id, BigDecimal valor) {
    Conta conta = contas.findById(id).orElseThrow();   // SELECT — a conta fica "managed"
    conta.depositar(valor);                            // só muda o objeto em memória
    return conta;                                      // nenhum save()!
}                                                      // commit → flush → UPDATE conta SET saldo = ...
```

No **flush** (antes do commit, ou antes de uma consulta que dependa das mudanças), o Hibernate compara cada entidade gerenciada com o estado que carregou e gera `UPDATE` para o que mudou. Chamar `save()` numa entidade já gerenciada não é errado, mas é redundante.

### Cache de primeiro nível

Dentro da mesma transação, `findById(42)` duas vezes devolve **a mesma instância**, e o segundo `SELECT` não acontece. É também por isso que o Hibernate garante uma única representação de cada linha por contexto.

<Callout tipo="atencao" titulo="Consultas não passam pelo cache de primeiro nível">
`findById` consulta o contexto primeiro; uma consulta JPQL (`findByChaveIdempotencia`) sempre vai ao banco. É isso que permite ao marco 2 do projeto integrador **conferir de novo** a chave de idempotência depois de obter o lock: a segunda consulta enxerga o que outra transação acabou de gravar.
</Callout>

### Detached e o `LazyInitializationException`

Quando a transação termina, o contexto fecha e as entidades ficam **detached**: mudanças nelas não são mais salvas, e acessar uma associação LAZY ainda não carregada lança `LazyInitializationException`. A solução **não** é ligar `open-in-view` nem mudar tudo para EAGER — é carregar o que você precisa dentro da transação, com a consulta certa (aula 4).

<Callout tipo="erro" titulo="spring.jpa.open-in-view=true (o padrão!)">
Com *open-in-view*, o Spring mantém o contexto aberto durante toda a requisição HTTP, inclusive na serialização do JSON. Parece conveniente, mas esconde consultas N+1 disparadas pela camada web, segura conexões do pool por mais tempo e faz o comportamento depender de onde o código roda. O Boot inclusive loga um aviso. Desligue: `spring.jpa.open-in-view=false`.
</Callout>

## `equals` e `hashCode` em entidades

Entidades gerenciadas pelo Hibernate podem ser *proxies* e ganham id só depois do `persist` (com `IDENTITY`). Regras práticas:

- se o id é **gerado pela aplicação** (UUID no construtor), `equals`/`hashCode` pelo id funcionam bem;
- se o id é **gerado pelo banco**, use uma chave natural imutável (CPF, código) ou `hashCode` constante por classe com `equals` pelo id não nulo;
- **nunca** inclua associações em `equals`/`hashCode`/`toString` (e cuidado com o `@Data` do Lombok): isso dispara carregamentos e laços infinitos.

<Callout tipo="entrevista">
"O que é o contexto de persistência?" separa quem usa JPA de quem entende JPA. Responda com os **estados** (transient, managed, detached, removed), o **dirty checking** (UPDATE sem `save`), o **flush** e o **cache de primeiro nível**, e conecte com problemas reais: `LazyInitializationException`, `open-in-view` e por que `ddl-auto=update` não vai para produção.
</Callout>

## Resumo

- **JPA** é a especificação, **Hibernate** a implementação, **Spring Data** a camada de repositórios.
- Entidades: construtor protegido + construtor válido, `EnumType.STRING`, ids pensados (IDENTITY, SEQUENCE ou UUID), regras em métodos de negócio.
- O **contexto de persistência** gerencia entidades: **dirty checking** gera UPDATE, o **flush** decide quando o SQL sai, e o **cache de primeiro nível** evita SELECTs repetidos.
- **Detached** + LAZY = `LazyInitializationException`: carregue o necessário dentro da transação e desligue o `open-in-view`.
- `ddl-auto=validate`: o schema pertence às migrações.
