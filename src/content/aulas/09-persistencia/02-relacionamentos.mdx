Tabelas se relacionam por **chaves estrangeiras**; objetos se relacionam por **referências**. Mapear uma coisa na outra é onde a maioria dos problemas de desempenho e de dados inconsistentes nasce. Esta aula mostra os mapeamentos e, principalmente, as **decisões** por trás deles.

## `@ManyToOne`: o relacionamento mais comum

Muitos pedidos pertencem a um cliente. No banco, `pedido.cliente_id` referencia `cliente.id`:

```java
@Entity
public class Pedido {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)   // ← LAZY explícito!
    @JoinColumn(name = "cliente_id")
    private Cliente cliente;
}
```

O lado com a chave estrangeira é o **dono** da relação: é por ele que o Hibernate grava a FK.

<Callout tipo="erro" titulo="@ManyToOne é EAGER por padrão">
Pela especificação, `@ManyToOne` e `@OneToOne` carregam a outra ponta **sempre** (EAGER). Parece inofensivo até você listar 500 pedidos e o Hibernate carregar os 500 clientes, cada um com seu próprio SELECT, mesmo quando a tela não mostra o cliente. **Declare `fetch = LAZY` em todo `@ManyToOne`** e busque o que precisar na consulta (aula 4).
</Callout>

## `@OneToMany`: o lado inverso

Se o cliente precisa navegar até os pedidos, a relação vira **bidirecional**:

```java
@Entity
public class Pedido {
    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<ItemPedido> itens = new ArrayList<>();

    public void adicionar(Produto produto, int quantidade) {     // mantém os DOIS lados coerentes
        itens.add(new ItemPedido(this, produto, quantidade));
    }
}

@Entity
public class ItemPedido {
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "pedido_id")
    private Pedido pedido;                                       // ← o dono da relação
}
```

- `mappedBy = "pedido"` diz: "esta coleção é o espelho do campo `pedido` em `ItemPedido`". Sem ele, o Hibernate criaria uma **tabela de junção** extra.
- Só o lado dono grava a FK. Se você adicionar um item à lista sem setar `item.pedido`, **nada é gravado**. Por isso existe o método auxiliar `adicionar`.
- `@OneToMany` já é LAZY. Nem sempre você precisa dele: um `ItemPedido` com `@ManyToOne` e uma consulta `findByPedidoId` resolvem sem carregar coleções enormes. No marco 2 do projeto, a conta **não** tem uma lista de movimentos: o extrato é uma consulta.

## Cascade e orphanRemoval

| Opção | Efeito | Use quando |
|---|---|---|
| `cascade = PERSIST` | salvar o pai salva os filhos novos | agregado criado junto (pedido + itens) |
| `cascade = ALL` | persist, merge, remove… propagam | o filho **não existe** sem o pai |
| `orphanRemoval = true` | tirar o filho da coleção → `DELETE` | itens de um pedido, linhas de um carrinho |

Cascata vai **do pai (agregado) para os filhos**, nunca ao contrário: `CascadeType.ALL` num `@ManyToOne` para `Cliente` faria remover um item remover o cliente. E cascata entre agregados independentes (cliente → pedidos) é um convite para apagar histórico sem querer.

## `@ManyToMany` e quando fugir dele

Alunos e turmas: um aluno cursa várias turmas, uma turma tem vários alunos.

```java
@ManyToMany
@JoinTable(name = "aluno_turma",
           joinColumns = @JoinColumn(name = "aluno_id"),
           inverseJoinColumns = @JoinColumn(name = "turma_id"))
private Set<Turma> turmas = new HashSet<>();
```

Funciona enquanto a associação for **só** a associação. No momento em que surge um dado dela — **data** da matrícula, **status**, **nota** —, não há onde guardá-lo. E quase sempre surge. A solução é promover a tabela de junção a **entidade**, com dois `@ManyToOne`:

```java
@Entity
public class Matricula {
    @ManyToOne(fetch = FetchType.LAZY, optional = false) private Aluno aluno;
    @ManyToOne(fetch = FetchType.LAZY, optional = false) private Turma turma;
    @Enumerated(EnumType.STRING) private StatusMatricula status;
    private Instant matriculadaEm;
}
```

Com a constraint `UNIQUE (aluno_id, turma_id)` no banco, é o modelo do exercício 09.01. Se usar `@ManyToMany`, prefira `Set` a `List` (com `List`, o Hibernate apaga e reinsere todas as linhas da junção a cada alteração).

## `@OneToOne`

Raro e cheio de armadilhas: o lado inverso de um `@OneToOne` **não pode ser LAZY** de verdade (o Hibernate precisa consultar para saber se é nulo). Prefira `@MapsId` (a entidade filha compartilha a chave primária) ou modele como `@ManyToOne` com `UNIQUE` na FK.

## `@Embedded`: objetos de valor na mesma tabela

Nem toda classe é entidade. Um endereço sem identidade própria vive nas colunas da tabela do dono:

```java
@Embeddable
public record Endereco(String logradouro, String cidade, String cep) { }

@Entity
public class Cliente {
    @Embedded
    private Endereco endereco;          // colunas logradouro, cidade, cep na tabela cliente
}
```

Records funcionam como `@Embeddable` desde o Hibernate 6.2.

<Callout tipo="entrevista">
"Explique o lado dono de uma relação" e "por que evitar EAGER" são clássicos. Mostre o exemplo pedido–item: a FK mora em `item_pedido`, então `ItemPedido.pedido` é o dono; `mappedBy` marca o inverso; tudo LAZY, com carregamento explícito na consulta. Um diferencial: dizer que `@ManyToMany` com atributos vira entidade — e que muitas vezes a coleção bidirecional nem é necessária.
</Callout>

## Resumo

- O **dono** da relação é o lado com a FK (normalmente `@ManyToOne`); o inverso usa `mappedBy` e mantém os dois lados coerentes com métodos auxiliares.
- **LAZY em tudo**, inclusive `@ManyToOne` (EAGER por padrão); carregue explicitamente na consulta.
- **Cascade** do agregado para os filhos; `orphanRemoval` para filhos que não existem sem o pai; nunca cascata para "cima".
- `@ManyToMany` com dados vira **entidade** com dois `@ManyToOne`; `@Embeddable` para objetos de valor.
