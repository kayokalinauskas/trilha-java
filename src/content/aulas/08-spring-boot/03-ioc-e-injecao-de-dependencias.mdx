Antes do Spring, você já sabe escrever uma aplicação Java inteira. Então por que praticamente toda vaga de backend Java pede Spring? Porque ele resolve, de um jeito padronizado, um problema que cresce junto com a aplicação: **quem cria os objetos e como eles se encontram**.

## O problema: objetos que se montam sozinhos

```java
public class ServicoDePedidos {
    private final RepositorioDePedidos repositorio = new RepositorioJdbc(new DataSourceHikari("jdbc:postgresql://..."));
    private final Notificador notificador = new NotificadorEmail("smtp.empresa.com", 587);
    // ...
}
```

Esse serviço **sabe demais**: qual banco, qual servidor de e-mail, quais portas. Para testá-lo, você precisa de um PostgreSQL e de um SMTP. Para trocar e-mail por WhatsApp, precisa editá-lo. E se dez classes precisam do mesmo `DataSource`, cada uma cria o seu.

## A solução: receber em vez de criar

```java
public class ServicoDePedidos {
    private final RepositorioDePedidos repositorio;
    private final Notificador notificador;

    public ServicoDePedidos(RepositorioDePedidos repositorio, Notificador notificador) {
        this.repositorio = repositorio;
        this.notificador = notificador;
    }
}
```

Isso é **injeção de dependências** (DI): a classe declara **do que precisa** (interfaces, de preferência) e alguém de fora entrega. No teste, você passa um repositório em memória e um notificador falso; em produção, os reais. A classe não muda.

Mas agora alguém precisa montar tudo:

```java
var dataSource = new DataSourceHikari(config.url());
var repositorio = new RepositorioJdbc(dataSource);
var notificador = new NotificadorEmail(config.smtp(), config.porta());
var servico = new ServicoDePedidos(repositorio, notificador);
var controller = new PedidoController(servico);
// ... multiplicado por 200 classes
```

Esse "alguém" é o **container de IoC** do Spring. **Inversão de controle** é exatamente isso: o controle de criar e ligar objetos sai do seu código e vai para o framework.

## Beans: como o Spring descobre o que criar

Um **bean** é um objeto criado e gerenciado pelo container. Há duas formas de declará-los:

**1. Estereótipos + component scan** — para as **suas** classes:

```java
@Service                     // também: @Component, @Repository, @Controller/@RestController
public class ServicoDePedidos {
    public ServicoDePedidos(RepositorioDePedidos repositorio, Notificador notificador) { ... }
}
```

O `@SpringBootApplication` liga o *component scan* no pacote da classe principal **e nos subpacotes**. Uma classe fora dessa árvore não é encontrada — erro clássico de iniciante.

**2. Métodos `@Bean`** — para classes que **não são suas** (bibliotecas) ou que exigem montagem:

```java
@Configuration
public class ConfiguracaoGeral {

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }

    @Bean
    CotacaoClient cotacaoClient(RestClient.Builder builder, CambioProperties props) { ... }
}
```

Os parâmetros de um método `@Bean` também são injetados. Com um único construtor, o Spring o usa automaticamente — **não é preciso `@Autowired`**.

<Comparar antes="Injeção em campo" depois="Injeção por construtor">
```java
@Service
public class ServicoDePedidos {
  @Autowired
  private RepositorioDePedidos repositorio;
  @Autowired
  private Notificador notificador;
}
```

```java
@Service
public class ServicoDePedidos {
  private final RepositorioDePedidos repositorio;
  private final Notificador notificador;

  public ServicoDePedidos(RepositorioDePedidos r,
                          Notificador n) { ... }
}
```
</Comparar>

Por construtor: dependências **explícitas**, campos **`final`**, objeto nunca "meio montado", e o teste unitário é só `new ServicoDePedidos(fakeRepo, fakeNotificador)`. Um construtor com oito parâmetros é um aviso honesto de que a classe faz coisas demais.

## Escopo e ciclo de vida

| Escopo | Instâncias | Uso |
|---|---|---|
| `singleton` (padrão) | uma por aplicação | quase tudo: serviços, repositórios, clientes HTTP |
| `prototype` | uma por injeção | objetos com estado próprio (raro) |
| `request` / `session` | uma por requisição/sessão HTTP | raro em APIs stateless |

<Callout tipo="erro" titulo="Singleton com estado de requisição">
```java
@Service
public class ServicoDeCarrinho {
    private List<Item> itens = new ArrayList<>(); // compartilhado entre TODOS os usuários!
}
```
Um bean singleton atende todas as requisições **ao mesmo tempo**, em threads diferentes (módulo 06). Estado mutável nele é uma race condition e um vazamento de dados entre clientes. Guarde estado no banco, no cache ou em objetos locais do método. Quando o estado é do próprio serviço (um cache, um contador), use estruturas thread-safe — como os exercícios 08.02 e 08.04 fazem.
</Callout>

Para executar código na subida ou no desligamento, use `@PostConstruct`/`@PreDestroy` ou implemente `ApplicationRunner` — sem gambiarras no construtor.

## Várias implementações da mesma interface

O que acontece se existirem `NotificadorEmail` e `NotificadorSms`, ambos `@Component`, e alguém pedir um `Notificador`? O Spring não adivinha: falha na subida com `NoUniqueBeanDefinitionException`. Você escolhe:

| Quero… | Faça |
|---|---|
| **todas** as implementações | peça `List<Notificador>` (ou `Map<String, Notificador>`, chave = nome do bean) |
| uma **padrão** | `@Primary` numa delas |
| uma **específica** | `@Qualifier("notificadorSms")` no parâmetro |
| ligar/desligar por configuração | `@ConditionalOnProperty` (ou perfis) |

Pedir `List<RegraDeComissao>` é o coração do exercício 08.01: um canal novo é só uma classe nova, e a calculadora nunca muda. É o **princípio aberto/fechado** do SOLID (módulo 13), conseguido de graça com DI — e é o padrão **Strategy** sem nenhuma fábrica manual.

## Configuração externa

Nada de URL, senha ou limite de negócio "chumbado" no código. O Spring junta propriedades de várias fontes, em ordem de prioridade (da maior para a menor, simplificando):

1. argumentos de linha de comando (`--cambio.timeout=5s`)
2. variáveis de ambiente (`CAMBIO_TIMEOUT=5s` — o *relaxed binding* converte o nome)
3. `application-{perfil}.yml`
4. `application.yml`
5. valores padrão no código

### Configuração tipada com `@ConfigurationProperties`

```yaml
comissao:
  teto-por-venda: 500.00
  parceiro:
    percentual: 2
```

```java
@Validated
@ConfigurationProperties("comissao")
public record ComissaoProperties(
        @DefaultValue("500.00") @Positive BigDecimal tetoPorVenda,
        @DefaultValue @Valid Parceiro parceiro) {

    public record Parceiro(@DefaultValue("2") @PositiveOrZero BigDecimal percentual) {}
}
```

Registre com `@ConfigurationPropertiesScan` (ou `@EnableConfigurationProperties`) e injete o record onde precisar. Com `@Validated`, uma configuração inválida **impede a aplicação de subir** — muito melhor do que descobrir em produção que o teto de comissão é negativo. Tipos como `Duration` (`"500ms"`, `"24h"`) e `DataSize` (`"10MB"`) são convertidos sozinhos.

`@Value("${comissao.teto-por-venda}")` também funciona, mas espalha strings pelo código e não valida nada: prefira-o só para um valor isolado.

### Perfis

```yaml
# application-dev.yml
cambio:
  base-url: http://localhost:9090
# application-prod.yml
cambio:
  base-url: https://api.cotacoes.com.br
```

Ative com `SPRING_PROFILES_ACTIVE=prod`. Beans também podem ser condicionados a um perfil (`@Profile("dev")`). Segredos **não** vão para arquivos versionados: use variáveis de ambiente ou um cofre (módulo 11).

## Resumo

- **DI**: classes recebem dependências (por **construtor**) em vez de criá-las; o **container** (IoC) cria e liga tudo.
- Beans vêm de **estereótipos** (suas classes, via component scan) ou de métodos **`@Bean`** (bibliotecas, montagem).
- O escopo padrão é **singleton**: nada de estado de requisição em campos; estado próprio precisa ser thread-safe.
- Várias implementações: `List<...>`, `@Primary`, `@Qualifier`, condicionais.
- Configuração externa e **tipada** com `@ConfigurationProperties` + `@Validated`; perfis por ambiente; segredos fora do Git.
