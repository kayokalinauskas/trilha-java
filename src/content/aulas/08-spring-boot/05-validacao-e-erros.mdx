A diferença entre uma API amadora e uma profissional aparece quando algo dá errado. O cliente recebe `500` com o stack trace do Hibernate? Um `200` com `{"erro": true}`? Cada endpoint devolve erro num formato diferente? Nesta aula você resolve isso de uma vez: **valida na entrada** e **traduz toda falha num formato único**.

## Bean Validation

A especificação **Jakarta Validation** (implementada pelo Hibernate Validator, trazido pelo `spring-boot-starter-validation`) define anotações de restrição que você coloca nos DTOs:

```java
public record DadosPaciente(
        @NotBlank @Size(max = 120) String nome,
        @NotBlank @CpfValido String cpf,
        @Email @Size(max = 254) String email,
        @NotNull @Past LocalDate nascimento) {
}
```

| Anotação | Garante |
|---|---|
| `@NotNull` / `@NotBlank` / `@NotEmpty` | presente / texto com conteúdo / coleção não vazia |
| `@Size(min, max)` | tamanho de texto ou coleção |
| `@Min`, `@Max`, `@Positive`, `@PositiveOrZero` | faixas numéricas |
| `@Digits(integer, fraction)` | casas decimais (dinheiro: `fraction = 2`) |
| `@Email`, `@Pattern(regexp)` | formato |
| `@Past`, `@Future`, `@FutureOrPresent` | datas |
| `@Valid` | valida em cascata um objeto aninhado |

Ative com `@Valid` no parâmetro do controller:

```java
@PostMapping
public ResponseEntity<PacienteResposta> cadastrar(@Valid @RequestBody DadosPaciente dados, ...) { ... }
```

Se algo violar, o método **nem roda**: o Spring lança `MethodArgumentNotValidException`, que vira `400`.

<Callout tipo="atencao" titulo="Nulo passa na maioria das anotações">
`@Email`, `@Size`, `@Past` e `@Pattern` consideram `null` **válido** — o trabalho de exigir presença é do `@NotNull`/`@NotBlank`. Isso é proposital: permite campos opcionais que, **se informados**, precisam ter formato correto (como o e-mail do paciente).
</Callout>

### Parâmetros também

Desde o Spring 6.1, restrições em `@RequestParam` e `@PathVariable` são validadas **sem nenhuma anotação extra** na classe:

```java
@GetMapping
public Pagina<PacienteResposta> listar(@RequestParam(defaultValue = "20") @Min(1) @Max(50) int tamanho) { ... }
```

Violou? `HandlerMethodValidationException` → `400`.

<Callout tipo="atencao" titulo="A pegadinha: quando o corpo também passa a ser 'validação de método'">
Se o método tem restrições em **algum** parâmetro simples (um `@RequestHeader @NotBlank`, por exemplo), o Spring valida o **método inteiro** — e os erros do `@Valid @RequestBody` passam a chegar como `HandlerMethodValidationException`, não mais como `MethodArgumentNotValidException`. Um tratador que só personaliza o segundo devolve esses 400 no formato padrão. O projeto integrador trata os dois (`handleHandlerMethodValidationException`), e foi um teste de fatia (`@WebMvcTest`) que revelou o problema — o teste de aceitação só olhava o status.
</Callout>

### Sua própria restrição

Regras de formato do seu domínio viram anotações reutilizáveis:

```java
@Constraint(validatedBy = ValidadorDeCpf.class)
@Target({FIELD, PARAMETER, RECORD_COMPONENT})
@Retention(RUNTIME)
public @interface CpfValido {
    String message() default "CPF inválido";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class ValidadorDeCpf implements ConstraintValidator<CpfValido, String> {
    @Override
    public boolean isValid(String cpf, ConstraintValidatorContext contexto) {
        if (cpf == null) return true;                 // presença é papel do @NotBlank
        return cpf.matches("\\d{11}") && digitosVerificadoresCorretos(cpf);
    }
}
```

<Callout tipo="dica" titulo="Validação de formato × regra de negócio">
Bean Validation é ótimo para **formato** ("CPF tem 11 dígitos válidos", "valor tem 2 casas"). Regras que dependem do **estado** ("CPF já cadastrado", "saldo suficiente", "quarto livre") ficam no serviço/domínio, que lança exceções de negócio — tratadas logo abaixo. Consultar o banco dentro de um `ConstraintValidator` mistura as responsabilidades e ainda tem *check-then-act*.
</Callout>

## Problem Details (RFC 9457)

Em vez de cada API inventar seu JSON de erro, a **RFC 9457** (que substituiu a RFC 7807 em 2023) padroniza um formato:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.hotel.dev/problemas/quarto-indisponivel",
  "title": "Quarto indisponível",
  "status": 409,
  "detail": "O quarto 7 já está reservado em parte do período de 2026-12-01 a 2026-12-05",
  "instance": "/reservas",
  "quartoId": 7
}
```

| Campo | Significado |
|---|---|
| `type` | URI que **identifica o tipo** de problema (idealmente, uma página que o documenta). O cliente decide o que fazer olhando o `type`, não o texto |
| `title` | resumo legível do tipo — igual em todas as ocorrências |
| `status` | o status HTTP, repetido no corpo |
| `detail` | explicação **desta** ocorrência |
| `instance` | URI desta ocorrência (o Spring preenche com o caminho da requisição) |
| extensões | campos extras úteis: `quartoId`, `saldoDisponivel`, `erros`, `codigoRastreio` |

O Spring tem suporte nativo: a classe `ProblemDetail`, a interface `ErrorResponse` e a base `ResponseEntityExceptionHandler`. Retornar um `ProblemDetail` já define o `Content-Type: application/problem+json`.

## Tratamento centralizado

Nenhum `try/catch` nos controllers. As exceções sobem e são traduzidas num **único lugar**:

```java
@RestControllerAdvice
public class TratadorDeErros extends ResponseEntityExceptionHandler {

    private static final String BASE = "https://api.hotel.dev/problemas/";

    @ExceptionHandler(QuartoIndisponivelException.class)
    public ProblemDetail quartoIndisponivel(QuartoIndisponivelException e) {
        ProblemDetail problema = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.getMessage());
        problema.setType(URI.create(BASE + "quarto-indisponivel"));
        problema.setTitle("Quarto indisponível");
        problema.setProperty("quartoId", e.quartoId());     // extensão
        return problema;
    }

    @Override   // personaliza o 400 de Bean Validation, incluindo a lista de campos
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ...
    }
}
```

Por que **estender `ResponseEntityExceptionHandler`**? Ele já trata as exceções do próprio Spring MVC — `405` (método não suportado), `415` (tipo de conteúdo), `404` de rota inexistente, parâmetro com tipo errado — e todas passam a sair como Problem Details. Sem ele, cada uma teria um formato diferente. (Alternativa: `spring.mvc.problemdetails.enabled=true` liga o mesmo comportamento sem classe nenhuma, mas você não personaliza nada.)

### A rede de segurança: 500 sem vazamento

```java
@ExceptionHandler(Exception.class)
public ProblemDetail inesperado(Exception e) {
    String codigo = UUID.randomUUID().toString();
    log.error("Erro inesperado [codigoRastreio={}]", codigo, e);      // o detalhe vai para o LOG
    ProblemDetail problema = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
            "Ocorreu um erro inesperado. Informe o código de rastreio ao suporte.");
    problema.setProperty("codigoRastreio", codigo);                   // o cliente recebe só o código
    return problema;
}
```

<Callout tipo="erro" titulo="Mensagens que ajudam atacantes">
`"detail": "PSQLException: relation \"usuarios_admin\" does not exist"` conta ao atacante que você usa PostgreSQL e o nome de uma tabela. Mensagens do Jackson revelam nomes de classes. Stack traces revelam bibliotecas e versões vulneráveis. O OWASP Top 10 2025 tem uma categoria inteira para isso: **A10 — Mishandling of Exceptional Conditions**. Regra: **detalhe técnico no log, mensagem genérica + código de rastreio na resposta**.
</Callout>

## Um catálogo de erros

Trate o `type` como parte do contrato e documente-o. Um catálogo típico:

| type | Status | Quando |
|---|---|---|
| `dados-invalidos` | 400 | Bean Validation falhou (com a lista `erros`) |
| `requisicao-malformada` | 400 | JSON inválido ou tipo errado |
| `nao-autenticado` / `acesso-negado` | 401 / 403 | módulo 11 |
| `recurso-nao-encontrado` | 404 | |
| `conflito` (ex.: `conta-duplicada`) | 409 | estado atual impede |
| `regra-de-negocio` (ex.: `saldo-insuficiente`) | 422 | dados válidos, regra violada |
| `limite-excedido` | 429 | rate limiting (módulo 11) |
| `erro-interno` | 500 | com `codigoRastreio` |

<Callout tipo="entrevista">
"Como você trata erros numa API Spring?" — `@RestControllerAdvice` estendendo `ResponseEntityExceptionHandler`, exceções de negócio específicas mapeadas para status corretos, formato **Problem Details (RFC 9457)**, validação de formato com Bean Validation e de regras no domínio, e 500 genérico com código de rastreio e log. Citar a RFC (e que ela substituiu a 7807) é um diferencial.
</Callout>

## Resumo

- **Bean Validation** nos DTOs (`@Valid`) e nos parâmetros; crie restrições próprias para formatos do domínio; regras que dependem de estado ficam no serviço.
- **Problem Details (RFC 9457)**: `type`, `title`, `status`, `detail`, `instance` + extensões, com `application/problem+json`.
- **`@RestControllerAdvice` + `ResponseEntityExceptionHandler`**: um lugar só, cobrindo negócio, validação e framework.
- **500**: mensagem genérica + código de rastreio; o detalhe fica no log (OWASP A10:2025).
