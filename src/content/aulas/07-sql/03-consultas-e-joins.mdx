SQL é **declarativo**: você diz **o que** quer, e o banco decide **como** buscar. Isso é poderoso e é também a fonte de confusões — principalmente sobre a **ordem** em que as partes de uma consulta são avaliadas.

Os exemplos usam a base de vendas dos exercícios 07.02 e 07.03: `cliente`, `produto`, `pedido` e `item_pedido`.

## O básico

```sql
SELECT id, nome, cidade
  FROM cliente
 WHERE cidade IN ('São Paulo', 'Recife')
   AND nome ILIKE 'a%'              -- ILIKE: sem diferenciar maiúsculas (PostgreSQL)
 ORDER BY nome
 LIMIT 20 OFFSET 40;                -- terceira página de 20
```

Consequências práticas:

- um **alias** criado no `SELECT` (`AS faturamento`) **não existe** no `WHERE` — mas existe no `ORDER BY`;
- o `WHERE` filtra **linhas**, antes de agrupar; o `HAVING` filtra **grupos**, depois;
- *window functions* (aula 4) são calculadas no `SELECT`, então também não podem ir no `WHERE`.

## JOINs

```sql
-- INNER JOIN: só pedidos que têm cliente correspondente (todos, graças à FK)
SELECT p.id, c.nome, p.data
  FROM pedido p
  JOIN cliente c ON c.id = p.cliente_id;

-- LEFT JOIN: TODOS os clientes; quem não tem pedido aparece com colunas de pedido NULL
SELECT c.nome, p.id AS pedido_id
  FROM cliente c
  LEFT JOIN pedido p ON p.cliente_id = c.id;
```

| JOIN | Resultado |
|---|---|
| `[INNER] JOIN` | só linhas com correspondência |
| `LEFT [OUTER] JOIN` | todas da esquerda + correspondências (ou `NULL`) |
| `RIGHT JOIN` | o espelho do LEFT (raro; reescreva como LEFT) |
| `FULL JOIN` | todas dos dois lados |
| `CROSS JOIN` | todas as combinações (produto cartesiano) |

<Callout tipo="erro" titulo="O filtro que transforma LEFT em INNER">
`LEFT JOIN pedido p ON p.cliente_id = c.id WHERE p.status = 'PAGO'` descarta os clientes sem pedido, porque `NULL = 'PAGO'` não é verdadeiro. Se a intenção é "todos os clientes, com seus pedidos pagos", coloque a condição **no `ON`**: `LEFT JOIN pedido p ON p.cliente_id = c.id AND p.status = 'PAGO'`.
</Callout>

## "Quem não tem…": anti-join

```sql
-- clientes que nunca fizeram pedido
SELECT c.nome
  FROM cliente c
 WHERE NOT EXISTS (SELECT 1 FROM pedido p WHERE p.cliente_id = c.id);

-- equivalente com LEFT JOIN
SELECT c.nome
  FROM cliente c
  LEFT JOIN pedido p ON p.cliente_id = c.id
 WHERE p.id IS NULL;
```

`EXISTS`/`NOT EXISTS` expressam a intenção diretamente e o otimizador do PostgreSQL costuma transformá-los em *semi-join*/*anti-join* eficientes.

## NULL: a lógica de três valores

`NULL` significa **"desconhecido"**. Qualquer comparação com ele resulta em **desconhecido** (nem verdadeiro, nem falso):

```sql
WHERE email = NULL          -- nunca verdadeiro! Use: WHERE email IS NULL
WHERE email <> 'x@y.com'    -- NÃO traz as linhas com email NULL
COUNT(*)                    -- conta linhas
COUNT(email)                -- conta só os valores NÃO nulos
COALESCE(desconto, 0)       -- primeiro valor não nulo
```

E a armadilha mais famosa:

```sql
SELECT nome FROM cliente
 WHERE id NOT IN (SELECT cliente_id FROM indicacao);   -- se ALGUM cliente_id for NULL, volta VAZIO
```

`x NOT IN (1, 2, NULL)` vira `x <> 1 AND x <> 2 AND x <> NULL` → o último termo é desconhecido, e o resultado nunca é verdadeiro. **Use `NOT EXISTS`.**

<Callout tipo="entrevista">
"Diferença entre INNER e LEFT JOIN" é certa em entrevista Júnior. Para se destacar: mostre o filtro no `WHERE` que "anula" o LEFT JOIN, prefira `NOT EXISTS` a `NOT IN` explicando o caso do `NULL`, e cite a ordem lógica (`WHERE` antes de `GROUP BY`, `HAVING` depois).
</Callout>

## Resumo

- Ordem lógica: `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`.
- `INNER` só correspondências; `LEFT` preserva a esquerda — filtros da direita vão no `ON`.
- "Quem não tem" → `NOT EXISTS` (ou `LEFT JOIN … IS NULL`); evite `NOT IN` com subconsulta.
- `NULL` = desconhecido: `IS NULL`, `COALESCE`, `COUNT(coluna)` ignora nulos.
