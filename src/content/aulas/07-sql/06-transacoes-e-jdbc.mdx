Transferir dinheiro envolve dois `UPDATE`s: debitar uma conta e creditar outra. Se o servidor cai entre os dois, o dinheiro some. **Transações** existem para que isso nunca aconteça.

## ACID

| Propriedade | Significa | Exemplo |
|---|---|---|
| **Atomicidade** | tudo ou nada | débito e crédito juntos, ou nenhum |
| **Consistência** | a transação leva o banco de um estado válido a outro | `CHECK (saldo >= 0)` nunca é violado |
| **Isolamento** | transações simultâneas não enxergam o "meio" umas das outras | ninguém vê o débito sem o crédito |
| **Durabilidade** | confirmado é permanente | depois do `COMMIT`, sobrevive a uma queda |

```sql
BEGIN;
UPDATE conta SET saldo = saldo - 100 WHERE id = 1;
UPDATE conta SET saldo = saldo + 100 WHERE id = 2;
COMMIT;          -- ou ROLLBACK, para desfazer tudo
```

## Isolamento e anomalias

Isolamento total (como se as transações rodassem uma de cada vez) custa desempenho. Os níveis de isolamento trocam garantias por concorrência:

| Nível | Evita | Ainda permite |
|---|---|---|
| READ UNCOMMITTED | (no PostgreSQL, age como READ COMMITTED) | — |
| **READ COMMITTED** (padrão PostgreSQL) | ler dados não confirmados (*dirty read*) | leitura não repetível, *lost update* por leitura + escrita na aplicação |
| REPEATABLE READ | leitura não repetível | no PostgreSQL, conflitos viram erro de serialização a tratar |
| SERIALIZABLE | todas as anomalias | exige *retry* das transações que falharem |

A anomalia que mais aparece no backend é o **lost update**:

```text
T1: SELECT saldo → 100          T2: SELECT saldo → 100
T1: UPDATE saldo = 100 - 30      T2: UPDATE saldo = 100 - 50
                     resultado: 50 (deveria ser 20)
```

É o *check-then-act* do módulo 06, agora no banco.

## Três formas de evitar o lost update

**1. Atualização atômica e condicional** — a mais simples, quando cabe:

```sql
UPDATE conta SET saldo = saldo - 30 WHERE id = 1 AND saldo >= 30;
-- 1 linha afetada: debitou. 0 linhas: saldo insuficiente (ou conta inexistente).
```

O banco lê e grava a linha de forma atômica, travando-a durante o comando. É o que o exercício 07.04 usa.

**2. Lock pessimista** — trava a linha ao ler:

```sql
SELECT saldo FROM conta WHERE id = 1 FOR UPDATE;   -- outras transações esperam
UPDATE conta SET saldo = ... WHERE id = 1;
```

**3. Lock otimista** — uma coluna `versao`; o `UPDATE ... WHERE versao = ?` falha se alguém mudou antes, e a aplicação tenta de novo. O JPA faz isso com `@Version` (módulo 09).

## JDBC: o Java falando com o banco

O **JDBC** é a API básica do Java para bancos relacionais. JPA, Spring Data e `JdbcTemplate` são camadas em cima dele — entender o JDBC é entender o que elas fazem por você.

```java
String sql = "SELECT saldo FROM conta WHERE id = ?";
try (Connection c = dataSource.getConnection();
     PreparedStatement ps = c.prepareStatement(sql)) {
    ps.setLong(1, contaId);                      // parâmetros começam em 1
    try (ResultSet rs = ps.executeQuery()) {
        return rs.next() ? Optional.of(rs.getBigDecimal("saldo")) : Optional.empty();
    }
}
```

- **`DataSource`**: fornece conexões (em produção, de um **pool**, como o HikariCP).
- **`PreparedStatement` com `?`**: os valores vão **separados** do SQL. Isso evita **SQL injection** e deixa o banco reaproveitar o plano.
- **try-with-resources** fecha `ResultSet`, `PreparedStatement` e `Connection`, que devolve a conexão ao pool. Uma conexão não fechada é um vazamento que derruba a aplicação quando o pool esgota.

### Transação com JDBC

```java
try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);                // por padrão, cada comando é commitado sozinho
    try {
        debitar(c, origem, valor);
        creditar(c, destino, valor);
        c.commit();
    } catch (RuntimeException | SQLException e) {
        c.rollback();                      // desfaz tudo que foi feito nesta conexão
        throw e;
    }
}
```

**Todos os comandos da transação precisam usar a mesma conexão.** É exatamente isso que o `@Transactional` do Spring gerencia para você no módulo 09: ele liga uma conexão à thread, desliga o autocommit e faz commit ou rollback no final.

## Resumo

- **ACID**: tudo ou nada, constraints válidas, isolamento e durabilidade.
- PostgreSQL usa **READ COMMITTED**; o **lost update** exige atualização condicional, lock pessimista ou otimista.
- JDBC: `PreparedStatement` com `?` (nunca concatenar), try-with-resources para tudo.
- Transação JDBC: `setAutoCommit(false)`, mesma conexão, `commit` no fim, `rollback` em qualquer erro — o que o `@Transactional` faz por você.
