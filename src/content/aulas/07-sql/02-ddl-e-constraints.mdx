  - frente: Qual tipo usar para dinheiro no PostgreSQL?

  - frente: Qual a diferença entre TIMESTAMP e TIMESTAMPTZ?
    verso: TIMESTAMPTZ guarda um instante absoluto (convertido para UTC); TIMESTAMP é só data e hora "de parede", sem fuso. Para eventos, prefira TIMESTAMPTZ.

A aplicação valida os dados, mas ela não é a única que escreve no banco: scripts de correção, jobs, outras aplicações, o analista com acesso de escrita… e bugs. **Constraints** garantem as regras **no próprio banco**, para qualquer um que escreva. Elas também resolvem condições de corrida que a aplicação sozinha não resolve, como você viu no módulo 06.

## Tipos: escolha com intenção

| Dado | Tipo PostgreSQL | Evite |
|---|---|---|
| Identificador | `BIGINT GENERATED ALWAYS AS IDENTITY` ou `UUID` | `SERIAL` (legado), `INT` (pode estourar) |
| Dinheiro | `NUMERIC(12, 2)` | `REAL`, `DOUBLE PRECISION`, `MONEY` |
| Texto curto com limite de negócio | `VARCHAR(n)` | `CHAR(n)` para textos variáveis |
| Texto livre | `TEXT` | — |
| Instante de um evento | `TIMESTAMPTZ` | `TIMESTAMP` sem fuso |
| Data sem hora | `DATE` | texto |
| Sim/não | `BOOLEAN` | `CHAR(1)` com 'S'/'N' |
| Documento flexível | `JSONB` | JSON em `TEXT` |

<Callout tipo="atencao" titulo="TIMESTAMP sem fuso é uma armadilha">
`TIMESTAMP` guarda "2026-03-02 23:59" sem dizer em que fuso. Se uma instância da aplicação roda em UTC e outra em `America/Sao_Paulo`, os mesmos dados significam instantes diferentes. `TIMESTAMPTZ` guarda o instante absoluto; é o equivalente de `Instant`/`OffsetDateTime` no Java.
</Callout>

## Constraints

```sql
CREATE TABLE consulta (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    paciente_id  BIGINT        NOT NULL REFERENCES paciente (id),
    medico_id    BIGINT        NOT NULL REFERENCES medico (id),
    inicio       TIMESTAMP     NOT NULL,
    duracao_min  INT           NOT NULL CHECK (duracao_min BETWEEN 15 AND 120),
    status       VARCHAR(10)   NOT NULL DEFAULT 'AGENDADA'
                               CHECK (status IN ('AGENDADA', 'REALIZADA', 'CANCELADA')),
    valor        NUMERIC(10,2) NOT NULL CHECK (valor >= 0),
    CONSTRAINT uk_consulta_medico_inicio UNIQUE (medico_id, inicio)
);
```

| Constraint | Garante |
|---|---|
| `PRIMARY KEY` | identificador único e não nulo |
| `NOT NULL` | campo obrigatório |
| `UNIQUE` | sem repetição (em uma coluna ou **combinação**) |
| `CHECK (expr)` | regra de valor: faixas, listas, relações entre colunas (`fim > inicio`) |
| `REFERENCES` (FK) | o valor existe na outra tabela |
| `DEFAULT` | valor quando não informado |

Dê **nomes** às constraints importantes (`CONSTRAINT uk_consulta_medico_inicio …`): a mensagem de erro fica legível e, no Spring, dá para traduzir a violação em uma mensagem de negócio.

### `UNIQUE` composto resolve concorrência

"O mesmo médico não pode ter duas consultas no mesmo horário": validar na aplicação com um `SELECT` antes do `INSERT` é *check-then-act* — duas requisições simultâneas passam. O `UNIQUE (medico_id, inicio)` faz o banco rejeitar a segunda, **sempre**.

## Chaves estrangeiras e exclusão

O que acontece ao apagar um paciente que tem consultas?

| Ação | Comportamento | Quando |
|---|---|---|
| `NO ACTION` / `RESTRICT` (padrão) | impede a exclusão | quase sempre: dados com histórico |
| `ON DELETE CASCADE` | apaga os filhos junto | filhos que não fazem sentido sozinhos (itens de um rascunho) |
| `ON DELETE SET NULL` | anula a referência | vínculo opcional |

<Callout tipo="erro" titulo="CASCADE em cadeia">
Um `DELETE` de cliente com `CASCADE` em pedidos, itens e pagamentos pode apagar anos de histórico financeiro com um comando. Em domínios com auditoria, prefira `RESTRICT` e **exclusão lógica** (uma coluna `ativo` ou `excluido_em`).
</Callout>

<Callout tipo="dica" titulo="FK não cria índice sozinha no PostgreSQL">
A PK e as colunas `UNIQUE` ganham índice automaticamente; **as FKs não**. Buscas por `consulta.paciente_id` (e exclusões de pacientes, que verificam os filhos) ficam lentas sem um `CREATE INDEX` explícito — tema da aula 5.
</Callout>

## Evoluindo o esquema

```sql
ALTER TABLE paciente ADD COLUMN telefone VARCHAR(20);
ALTER TABLE paciente ALTER COLUMN telefone SET NOT NULL;     -- falha se já houver NULLs
ALTER TABLE consulta ADD CONSTRAINT ck_valor_max CHECK (valor <= 10000);
ALTER TABLE paciente RENAME COLUMN email TO email_contato;   -- quebra quem usa o nome antigo!
```

Em produção, cada alteração vira uma **migração versionada** (Flyway, módulo 09) e precisa conviver com a versão anterior da aplicação durante o deploy — o padrão *expand and contract* que aparece no simulador de entrevista.

## Resumo

- Tipos com intenção: `NUMERIC` para dinheiro, `TIMESTAMPTZ` para instantes, `BIGINT`/`UUID` para ids.
- Constraints (`NOT NULL`, `UNIQUE`, `CHECK`, FK) são a última linha de defesa — e resolvem concorrência.
- FK: prefira `RESTRICT`; `CASCADE` só onde apagar em cadeia é o desejado.
- FKs não ganham índice automático; alterações de esquema viram migrações versionadas.
