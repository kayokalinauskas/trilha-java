A consulta que roda em 3 ms com 1.000 linhas no seu computador pode levar 8 segundos com 20 milhões em produção. Na maioria das vezes, a diferença é **um índice** — ou a falta dele.

## Como um índice funciona

Sem índice, para achar `WHERE cpf = '52998224725'` o banco lê **a tabela inteira** (*sequential scan*): O(n). Um índice **B-tree** é uma árvore ordenada e balanceada, como o `TreeMap` do módulo 03: o banco desce poucos níveis até a folha com o valor e de lá vai direto à linha. O(log n) — com milhões de linhas, 3 ou 4 níveis.

Índices B-tree servem para `=`, `<`, `>`, `BETWEEN`, `IN`, `ORDER BY` e `LIKE 'prefixo%'`.

## O custo

Nada é de graça: cada índice ocupa espaço e **toda escrita** na tabela precisa atualizá-lo. Uma tabela de eventos com 15 índices "por via das dúvidas" fica lenta para inserir. Crie índices para **consultas reais e frequentes**, e remova os que ninguém usa (o PostgreSQL mostra isso em `pg_stat_user_indexes`).

## Índices compostos: a ordem importa

```sql
CREATE INDEX ix_pedido_cliente_data ON pedido (cliente_id, data);
```

Esse índice é ordenado primeiro por `cliente_id` e, dentro de cada cliente, por `data` — como uma lista telefônica ordenada por sobrenome e depois por nome.

| Consulta | Usa bem o índice? |
|---|---|
| `WHERE cliente_id = 42` | sim |
| `WHERE cliente_id = 42 AND data >= '2026-01-01'` | sim |
| `WHERE cliente_id = 42 ORDER BY data DESC LIMIT 10` | sim, e evita ordenar |
| `WHERE data >= '2026-01-01'` | não (a data não é a primeira coluna) |

Regra prática: colunas de **igualdade** primeiro, depois as de **intervalo** ou **ordenação**.

## Quando o índice não é usado

- **Função na coluna**: `WHERE lower(email) = ?` ou `WHERE date(criado_em) = ?`. Solução: índice de expressão (`CREATE INDEX … ON cliente (lower(email))`) ou reescrever como intervalo (`criado_em >= '2026-03-02' AND criado_em < '2026-03-03'`).
- **Curinga no início**: `LIKE '%silva'`. Para busca textual, use índices de texto (`pg_trgm`, *full-text search*).
- **Baixa seletividade**: se `status = 'ATIVO'` corresponde a 90% da tabela, ler a tabela inteira é mais barato — e o planejador sabe disso.
- **Tipos diferentes**: comparar uma coluna `BIGINT` com um parâmetro texto pode exigir conversão e anular o índice.
- **Estatísticas desatualizadas**: o planejador estima mal; `ANALYZE tabela` atualiza.

## EXPLAIN: pergunte ao banco

Nunca adivinhe; peça o **plano de execução**:

```sql
EXPLAIN ANALYZE
SELECT * FROM pedido WHERE cliente_id = 42 ORDER BY data DESC LIMIT 10;
```

```text
Limit  (cost=0.43..8.61 rows=10) (actual time=0.031..0.045 rows=10 loops=1)
  ->  Index Scan Backward using ix_pedido_cliente_data on pedido
        (actual time=0.030..0.042 rows=10 loops=1)
        Index Cond: (cliente_id = 42)
Planning Time: 0.120 ms
Execution Time: 0.068 ms
```

O que procurar:

- **`Seq Scan`** em tabela grande com filtro seletivo → provável índice faltando.
- **Estimativa × real** (`rows=10` × `actual rows=48000`) muito diferentes → estatísticas ruins.
- **`Sort`** caro → um índice na ordem certa pode eliminá-lo.
- **Nested Loop** com milhares de repetições (`loops=`) → o N+1 do banco.

<Callout tipo="atencao">
`EXPLAIN ANALYZE` **executa** a consulta. Com `UPDATE`/`DELETE`, faça dentro de uma transação e dê `ROLLBACK`.
</Callout>

<Callout tipo="entrevista">
"Uma consulta ficou lenta em produção. O que você faz?" Resposta estruturada: **medir** (log de consultas lentas, `pg_stat_statements`, tracing), **explicar** (`EXPLAIN ANALYZE`), **agir** (índice composto na ordem certa, reescrever a consulta, eliminar N+1 na aplicação) e **validar** comparando os planos — sem esquecer o custo do índice nas escritas.
</Callout>

## Resumo

- B-tree: busca O(log n) para igualdade, intervalos, ordenação e prefixos — ao custo de espaço e escritas mais lentas.
- Índice composto: igualdade primeiro, depois intervalo/ordenação.
- Funções na coluna, `LIKE '%x'`, baixa seletividade e tipos diferentes impedem o uso.
- `EXPLAIN ANALYZE`: procure `Seq Scan`, estimativas erradas, `Sort` caro e loops repetidos.
