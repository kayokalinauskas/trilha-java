## Sequenced Collections (Java 21)

Até o Java 20, pegar o último elemento dependia da coleção: `list.get(list.size() - 1)`, `deque.getLast()`, `sortedSet.last()`, e para `LinkedHashSet`… não havia jeito direto. O Java 21 unificou isso com a interface **`SequencedCollection`**:

```java
List<String> etapas = new ArrayList<>(List.of("pedido", "pagamento", "envio"));

etapas.getFirst();        // "pedido"
etapas.getLast();         // "envio"
etapas.addFirst("carrinho");
etapas.removeLast();
etapas.reversed();        // visão invertida: ["pagamento", "pedido", "carrinho"]
```

- `List`, `Deque`, `LinkedHashSet` e `SortedSet` implementam `SequencedCollection`.
- `LinkedHashMap` e `SortedMap` implementam **`SequencedMap`**: `firstEntry()`, `lastEntry()`, `pollFirstEntry()`, `putFirst()`…
- `reversed()` devolve uma **visão**, sem copiar os dados.

<Callout tipo="novidade">
Se você vê `lista.get(lista.size() - 1)` em um código novo, é um sinal de que dá para modernizar com `getLast()`.
</Callout>

## `PriorityQueue`: sempre o próximo mais importante

```java
record Tarefa(String nome, int prioridade) { }

PriorityQueue<Tarefa> fila = new PriorityQueue<>(
        Comparator.comparingInt(Tarefa::prioridade).reversed());

fila.offer(new Tarefa("enviar e-mail", 1));
fila.offer(new Tarefa("estornar pagamento", 10));
fila.offer(new Tarefa("gerar relatório", 5));

fila.poll();   // estornar pagamento (10)
fila.poll();   // gerar relatório (5)
```

Inserir e remover custam **O(log n)**; espiar o topo (`peek`) é O(1). Usos típicos: agendadores, "os K maiores de um fluxo enorme" (mantenha uma fila de tamanho K) e o algoritmo de Dijkstra.

<Callout tipo="atencao">
Iterar uma `PriorityQueue` com for-each **não** devolve os elementos em ordem: só `poll()` garante a ordem.
</Callout>

## `TreeMap` para perguntas de intervalo

```java
TreeMap<LocalTime, String> agenda = new TreeMap<>();
agenda.put(LocalTime.of(9, 0), "Daily");
agenda.put(LocalTime.of(14, 0), "Revisão de código");
agenda.put(LocalTime.of(16, 30), "1:1");

agenda.ceilingKey(LocalTime.of(13, 0));    // 14:00 — próximo compromisso a partir das 13h
agenda.floorEntry(LocalTime.of(15, 0));    // 14:00=Revisão — o último antes das 15h
agenda.headMap(LocalTime.of(12, 0));       // tudo antes do meio-dia
```

"Qual a faixa de frete para este CEP?", "qual a alíquota para este salário?", "qual o próximo horário livre?" — perguntas de intervalo são resolvidas em O(log n) com `floorEntry`/`ceilingEntry`.

## A classe `Collections`

| Método | Uso |
|---|---|
| `Collections.sort(lista)` | Ordena (hoje, prefira `lista.sort(comparator)`) |
| `Collections.shuffle(lista)` | Embaralha (sorteios, testes) |
| `Collections.frequency(col, x)` | Conta ocorrências |
| `Collections.max(col)` / `min` | Maior / menor pela ordem natural ou por um `Comparator` |
| `Collections.unmodifiableList(l)` | Visão somente leitura (atenção: não é cópia!) |
| `Collections.emptyList()` | Lista vazia imutável (hoje, `List.of()`) |
| `Collections.nCopies(n, x)` | Lista imutável com n cópias de x |

## Estudo de caso: cache LRU

Um **cache LRU** (*Least Recently Used*) guarda no máximo N itens e, quando enche, descarta o que foi **usado há mais tempo**. Está em todo lugar: cache de páginas do sistema operacional, cache de sessões e cache de consultas caras. E é uma das perguntas de entrevista mais clássicas do mundo.

O requisito que torna o problema interessante: **`obter` e `colocar` em O(1)**.

- Um `HashMap` dá acesso O(1) pela chave, mas não sabe **quem foi usado há mais tempo**.
- Uma lista sabe a ordem de uso, mas mover um item para a frente é O(n) se for preciso procurá-lo.

A solução é **combinar os dois**: o `HashMap` aponta direto para os **nós** de uma lista duplamente encadeada.

- **`obter(k)`**: o mapa acha o nó (O(1)); o nó é desligado e religado logo após a cabeça (O(1)).
- **`colocar(k, v)`** com o cache cheio: o nó antes da cauda é o menos recente; remova-o da lista e do mapa (O(1)).
- **Nós sentinela** (cabeça e cauda vazias) eliminam os casos especiais de "lista vazia" e "primeiro/último elemento".

Você vai implementar essa estrutura no exercício 03.05 — é o exercício mais difícil do módulo, e o que mais se parece com uma pergunta real de entrevista.

<Callout tipo="info" titulo="O atalho da JDK">
Na vida real, um `LinkedHashMap` com `accessOrder = true` e `removeEldestEntry` sobrescrito já é um LRU. Em produção, você provavelmente usaria o **Caffeine**, a biblioteca de cache mais usada no ecossistema Java (e padrão no Spring Cache). Mas implementar do zero é o que ensina **por que** essas estruturas funcionam — e é o que a entrevista pede.
</Callout>

## Resumo

- **Sequenced Collections**: `getFirst`, `getLast`, `addFirst`, `reversed` em `List`, `Deque`, `LinkedHashSet`, `LinkedHashMap`…
- `PriorityQueue` para "sempre o próximo mais importante"; `TreeMap` para perguntas de intervalo.
- `Collections` tem utilitários prontos — mas prefira `List.of`/`List.copyOf` para imutáveis.
- **Cache LRU** = `HashMap` + lista duplamente encadeada, tudo em O(1).
