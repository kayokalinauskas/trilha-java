Em um sistema backend, **erros não são exceção** — são rotina. O cliente informa um CPF inválido, o estoque acaba no meio da compra, o banco de dados demora, o arquivo de importação vem quebrado. A forma como você modela esses erros determina se o sistema falha com clareza ou esconde problemas até eles virarem incidentes.

- **`Error`**: problemas graves da JVM (`OutOfMemoryError`, `StackOverflowError`). Não se trata; se registra e se deixa o processo cair.
- **Exceções checked** (herdam de `Exception`, mas não de `RuntimeException`): o compilador **obriga** quem chama a tratar (`catch`) ou declarar (`throws`).
- **Exceções unchecked** (herdam de `RuntimeException`): o tratamento é opcional.

## Checked ou unchecked?

Esta é uma das discussões mais antigas do Java. O critério mais aceito hoje:

| Use **checked** quando… | Use **unchecked** quando… |
|---|---|
| A falha é **esperada** e **recuperável** | A falha é um **erro de programação** (argumento inválido, estado ilegal) |
| Quem chama tem uma **ação razoável** a tomar | Quem chama não pode fazer nada útil ali |
| Ex.: arquivo de importação inválido → avisar o operador e pedir outro | Ex.: livro não encontrado → um handler global devolve HTTP 404 |

Na prática, **aplicações Spring usam quase só unchecked** para regras de negócio: a exceção "sobe" até um tratador global (`@RestControllerAdvice`, módulo 08), que a converte em uma resposta HTTP padronizada. Assim, os métodos não ficam poluídos de `throws` em todas as camadas. Checked fica para situações pontuais, como o importador do exercício 03.03.

## Exceções de negócio com código

Exceções genéricas (`RuntimeException("deu erro")`) não dizem nada. Modele as falhas do seu domínio:

```java
public abstract class BibliotecaException extends RuntimeException {
    private final String codigo;

    protected BibliotecaException(String codigo, String mensagem) {
        super(mensagem);
        this.codigo = codigo;
    }

    public String codigo() { return codigo; }
}

public class LivroIndisponivelException extends BibliotecaException {
    public LivroIndisponivelException(String isbn) {
        super("LIVRO_INDISPONIVEL", "Nenhum exemplar disponível para o ISBN " + isbn);
    }
}
```

- A **superclasse abstrata** permite tratar todas as falhas do domínio de uma vez (`catch (BibliotecaException e)`) e impede lançar uma genérica sem significado.
- O **código estável** (`LIVRO_INDISPONIVEL`) é o que APIs, front-ends e alertas usam. A **mensagem** é para humanos e pode mudar.
- A mensagem traz **contexto** (qual ISBN, qual usuário, qual limite). "Livro indisponível" sozinho não ajuda ninguém às 3h da manhã.

## Lançar, capturar, relançar

```java
public Emprestimo emprestar(String isbn, String usuario, LocalDate data) {
    Livro livro = acervo.get(isbn);
    if (livro == null) {
        throw new LivroNaoEncontradoException(isbn);     // fail-fast
    }
    // ...
}
```

```java
try {
    servico.emprestar(isbn, usuario, hoje);
} catch (LivroIndisponivelException e) {
    fila.entrarNaEspera(isbn, usuario);                  // tratamento específico
} catch (BibliotecaException e) {
    log.warn("Empréstimo recusado [{}]: {}", e.codigo(), e.getMessage());
    throw e;                                             // registra e deixa subir
}
```

- Os `catch` são avaliados **em ordem**: o mais específico primeiro.
- `catch (A | B e)` trata vários tipos no mesmo bloco (*multi-catch*).
- `finally` executa sempre, com ou sem exceção — mas para liberar recursos, prefira o próximo tópico.

## try-with-resources

Arquivos, conexões e *streams* precisam ser **fechados**, mesmo quando algo dá errado. O jeito antigo era verboso e cheio de armadilhas. O moderno:

```java
try (BufferedReader leitor = Files.newBufferedReader(arquivo, UTF_8)) {
    return processar(leitor);
}   // leitor.close() é chamado aqui, com ou sem exceção
```

Funciona com qualquer objeto que implemente `AutoCloseable`. Com vários recursos, eles são fechados na **ordem inversa** da abertura. Se o `close()` também falhar, a exceção dele fica anexada como *suppressed*, sem esconder a original.

## Tradução de exceções: mude o nível, preserve a causa

Quem chama `ImportadorAcervo.importar(arquivo)` não deveria precisar conhecer `IOException`, `NumberFormatException` e mais dez exceções de baixo nível. **Traduza** para o vocabulário de quem chama — **sempre preservando a causa**:

```java
try (Reader leitor = Files.newBufferedReader(arquivo)) {
    return importar(leitor);
} catch (IOException e) {
    throw new ArquivoAcervoInvalidoException("Não foi possível ler " + arquivo, 0, e);  // e = causa
}
```

Sem o `e` no construtor, o stack trace original some, e com ele a pista de **por que** a leitura falhou (arquivo inexistente? permissão? disco cheio?).

## Anti-padrões

<Comparar antes="Não faça" depois="Faça">
```java
try { processar(); } catch (Exception e) { }

try { ... } catch (Exception e) {
    throw new RuntimeException("erro");
}

catch (Exception e) {
    e.printStackTrace();
    return null;
}

if (erro) return -1;   // código de erro "mágico"
```

```java
// deixe subir ou trate de verdade

try { ... } catch (IOException e) {
    throw new ImportacaoException("contexto", e);
}

catch (PagamentoRecusadoException e) {
    log.warn("Recusado: {}", e.codigo(), e);
    throw e;
}

throw new SaldoInsuficienteException(...);
```
</Comparar>

1. **Engolir exceções** (`catch` vazio): o sistema segue em estado inválido e ninguém sabe.
2. **Perder a causa**: `new RuntimeException("erro")` sem o `e`.
3. **`printStackTrace` + `return null`**: joga o problema para frente como um `NullPointerException` distante e sem contexto.
4. **Capturar `Exception` genérica** sem necessidade: captura também bugs que deveriam derrubar o fluxo.
5. **Usar exceção para controle de fluxo normal** (ex.: `try { parseInt } catch` para descobrir se é número em um laço de milhões): é caro e esconde a intenção.
6. **Códigos de retorno mágicos** (`-1`, `null`) para sinalizar erro: quem chama esquece de checar.

## Resumo

- `Error` não se trata; **checked** obriga tratamento; **unchecked** não.
- Checked para falhas **esperadas e recuperáveis**; unchecked para erros de programação e regras tratadas globalmente (padrão em Spring).
- Modele **exceções de negócio** com superclasse abstrata, **código estável** e mensagens com contexto.
- **try-with-resources** para tudo que precisa ser fechado.
- **Traduza** exceções para o nível de quem chama e **sempre preserve a causa**. Nunca engula exceções.
