Grafos modelam qualquer coisa com **conexões**: rotas entre centros de distribuição, dependências entre módulos de um build, seguidores numa rede social, microsserviços que chamam uns aos outros. Esta aula cobre os três algoritmos que resolvem a maioria dos problemas de grafo em entrevistas — BFS, DFS e ordenação topológica — e fecha o módulo com intervalos.

## Representando um grafo

A forma mais comum é a **lista de adjacência**: para cada vértice, a lista de vizinhos.

```java
Map<String, List<String>> vizinhos = new HashMap<>();
for (List<String> trecho : trechos) {
    String a = trecho.get(0), b = trecho.get(1);
    vizinhos.computeIfAbsent(a, k -> new ArrayList<>()).add(b);
    vizinhos.computeIfAbsent(b, k -> new ArrayList<>()).add(a);   // não direcionado: mão dupla
}
```

Em grafos **direcionados** (A depende de B, mas não o contrário), adicione só uma direção.

## BFS: o menor número de passos

A **busca em largura** visita o grafo em **camadas**: primeiro os vizinhos diretos, depois os vizinhos dos vizinhos… Por isso, a primeira vez que ela alcança o destino é pelo caminho com **menos arestas**.

```java
Map<String, String> veioDe = new HashMap<>();
veioDe.put(origem, null);
Deque<String> fila = new ArrayDeque<>(List.of(origem));
while (!fila.isEmpty()) {
    String atual = fila.poll();
    if (atual.equals(destino)) return reconstruir(veioDe, destino);
    for (String proximo : vizinhos.get(atual)) {
        if (!veioDe.containsKey(proximo)) {        // marca ao ENFILEIRAR
            veioDe.put(proximo, atual);
            fila.offer(proximo);
        }
    }
}
```

- O mapa `veioDe` serve ao mesmo tempo de **conjunto de visitados** e de **trilha** para reconstruir o caminho de trás para frente.
- **Marque ao enfileirar**, não ao tirar da fila: senão o mesmo vértice entra na fila várias vezes.
- Complexidade: **O(V + E)** (vértices + arestas).
- Com **pesos** nas arestas (distâncias em km), BFS não serve: use Dijkstra, que é uma BFS com `PriorityQueue`.

## DFS: explorar tudo

A **busca em profundidade** vai o mais fundo possível antes de voltar. Ela serve para **explorar** o grafo inteiro: contar regiões desconectadas, detectar ciclos, listar todos os caminhos.

```java
int regioes = 0;
Set<String> visitados = new HashSet<>();
for (String inicio : vizinhos.keySet()) {
    if (!visitados.add(inicio)) continue;       // já pertence a uma região contada
    regioes++;
    Deque<String> pilha = new ArrayDeque<>(List.of(inicio));
    while (!pilha.isEmpty()) {
        for (String v : vizinhos.get(pilha.pop())) {
            if (visitados.add(v)) pilha.push(v);
        }
    }
}
```

A versão recursiva é mais curta, mas lembre-se da aula 1: grafos grandes podem estourar a pilha de chamadas. A versão com `ArrayDeque` explícita não tem esse limite.

## Ordenação topológica: a ordem das dependências

> Os módulos `app`, `infra`, `dominio`, `cli` e `docs` têm dependências entre si. Em que ordem compilar?

Uma **ordenação topológica** lista os vértices de um grafo direcionado de modo que cada um apareça **depois de todas as suas dependências**. É o que Maven, Gradle, npm e o próprio Spring (ao criar beans) fazem.

O **algoritmo de Kahn**:

1. Calcule o **grau de entrada** de cada vértice (quantas dependências ainda faltam).
2. Coloque numa fila todos os de grau **zero** (prontos).
3. Tire um da fila, adicione à ordem e "libere" quem dependia dele (grau − 1). Quem chegar a zero entra na fila.
4. Se ao final a ordem tiver **menos vértices** que o grafo, há um **ciclo**: os que sobraram nunca ficaram prontos.

Usar uma `PriorityQueue` em vez de uma fila comum dá uma ordem **determinística** (alfabética entre os prontos) — útil para builds reproduzíveis e para testes.

<Callout tipo="info" titulo="Ciclos na vida real">
Ciclos de dependência são um problema de design: no Spring, dois beans que dependem um do outro pelo construtor impedem a aplicação de subir (`BeanCurrentlyInCreationException`). A correção raramente é técnica — quase sempre é separar uma responsabilidade que está no lugar errado.
</Callout>

## Intervalos: ordenar e varrer

Problemas com intervalos (reuniões, reservas, janelas de manutenção) seguem quase sempre o mesmo padrão: **ordenar pelo início** e fazer **uma passada**.

**Mesclar intervalos sobrepostos:**

```java
List<Intervalo> ordenados = intervalos.stream().sorted(comparingInt(Intervalo::inicio)).toList();
for (Intervalo atual : ordenados) {
    if (!resultado.isEmpty() && atual.inicio() <= resultado.getLast().fim()) {
        Intervalo ultimo = resultado.removeLast();
        resultado.add(new Intervalo(ultimo.inicio(), Math.max(ultimo.fim(), atual.fim())));
    } else {
        resultado.add(atual);
    }
}
```

**Mínimo de salas de reunião:** percorra as reuniões por início, com uma `PriorityQueue` dos **términos** das salas ocupadas. Se a sala que libera mais cedo já está livre quando a reunião começa, reaproveite-a; senão, abra outra. O tamanho do heap no final é o número de salas.

Os dois são O(n log n), dominados pela ordenação.

## Resumo

- Grafo = **lista de adjacência** (`Map<V, List<V>>`).
- **BFS** (fila): menor número de passos. **DFS** (pilha): explorar, componentes, ciclos. Ambos O(V + E).
- **Ordenação topológica** (Kahn): ordem de dependências; sobra de vértices = ciclo.
- **Intervalos**: ordene pelo início e varra; `PriorityQueue` de términos para contar salas.
