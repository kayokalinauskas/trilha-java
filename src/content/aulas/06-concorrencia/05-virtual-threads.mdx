Por décadas, servidores Java seguiram o modelo **uma thread por requisição**: simples de escrever e de depurar. O problema é que threads de plataforma são caras, e um servidor fica limitado a algumas centenas de requisições simultâneas **esperando** banco ou APIs externas. A alternativa era a programação reativa: escalável, mas bem mais difícil. As **virtual threads**, oficiais desde o **Java 21**, trazem a escala do modelo reativo com a simplicidade do código síncrono.

## Plataforma × virtual

| | Thread de plataforma | Virtual thread |
|---|---|---|
| Mapeamento | 1:1 com thread do SO | muitas sobre poucas threads de plataforma (*carriers*) |
| Custo | ~1 MB de pilha reservada, criação cara | poucos KB, criação em microssegundos |
| Quantidade prática | centenas a poucos milhares | milhões |
| Ao bloquear em I/O | a thread do SO fica parada | é **desmontada**; a carrier roda outra |

## Usando

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (String id : pedidos) {
        executor.submit(() -> emitirNota(id));   // uma virtual thread por tarefa
    }
}   // close() espera todas

Thread.ofVirtual().start(() -> processar());      // criação direta
```

No **Spring Boot** (3.2+), uma propriedade basta:

```properties
spring.threads.virtual.enabled=true
```

O Tomcat passa a atender cada requisição numa virtual thread, e `@Async`, agendadores e outros executores do Spring também as usam. Código de controller, service e repositório continua **exatamente igual**.

## Não faça pool de virtual threads

O instinto de "limitar a 200 threads" vem das threads de plataforma, caras. Virtual threads são baratas: crie **uma por tarefa**. Se o que é escasso é outro recurso — conexões de banco, um fornecedor que aceita 50 chamadas simultâneas —, limite **o recurso**, com um **`Semaphore`**:

```java
Semaphore permissoes = new Semaphore(50);

executor.submit(() -> {
    permissoes.acquire();          // espera se já houver 50 em andamento
    try {
        return sefaz.emitir(id);
    } finally {
        permissoes.release();
    }
});
```

A virtual thread que espera no `acquire` também é desmontada: esperar é barato. O exercício 06.04 mede o pico de chamadas simultâneas para garantir que o limite é respeitado. Para o banco, o próprio pool de conexões (HikariCP) já faz o papel de limitador.

## Quando virtual threads não ajudam

- **Trabalho CPU-bound**: compactar arquivos ou calcular hashes continua limitado ao número de núcleos. Virtual threads não criam CPU.
- **Pinning**: em algumas situações, a virtual thread fica "presa" à carrier e não é desmontada ao bloquear. Até o Java 23, isso acontecia dentro de blocos `synchronized`. **Desde o Java 24 (JEP 491), `synchronized` não causa mais pinning**; ainda acontece em chamadas nativas (JNI). Se você estiver no Java 21, prefira `ReentrantLock` em trechos que bloqueiam em I/O.
- **`ThreadLocal` com dados pesados**: com milhões de threads, cada cópia custa memória. As **scoped values** (próxima aula) são a alternativa.

## Resumo

- Virtual threads são leves e **desmontadas** ao bloquear em I/O: milhões de tarefas concorrentes com código síncrono.
- `Executors.newVirtualThreadPerTaskExecutor()` ou `spring.threads.virtual.enabled=true`.
- **Uma por tarefa**, sem pool; limite recursos escassos com `Semaphore`.
- Não ajudam em CPU-bound; pinning por `synchronized` acabou no Java 24.
