Você talvez nunca tenha escrito `new Thread(...)`, mas todo código backend que você escrever será executado **por várias threads ao mesmo tempo**. Um servidor como o Tomcat atende cada requisição HTTP em uma thread; se 200 clientes chamam `/pedidos` ao mesmo tempo, o mesmo método do mesmo objeto roda 200 vezes em paralelo. Entender o que pode dar errado é o que separa um Júnior de um Pleno.

## Threads em 2 minutos

Uma **thread** é uma linha de execução dentro de um processo. As threads de um processo **compartilham a memória** (a heap), e cada uma tem sua própria pilha de chamadas.

```java
Runnable tarefa = () -> System.out.println("rodando em " + Thread.currentThread().getName());

Thread t = new Thread(tarefa, "worker-1");
t.start();       // começa a executar EM PARALELO (não use run(), que executa na thread atual)
t.join();        // espera terminar
```

Na prática, quase nunca se cria `Thread` diretamente: usam-se **executores** (aula 3) ou **virtual threads** (aula 5). Mas os problemas de memória compartilhada são os mesmos em qualquer caso.

## Problema 1: atomicidade

```java
class Contador {
    private long total = 0;
    void incrementar() { total++; }
}
```

`total++` parece uma operação, mas são **três**: ler `total`, somar 1, escrever. Duas threads podem ler o mesmo valor e escrever o mesmo resultado — um incremento se perde.

Esse é o **race condition** (condição de corrida). O exercício 06.01 roda 16 threads × 20 mil incrementos e verifica que nenhum se perde.

Outro formato do mesmo problema é o **check-then-act** (verificar e depois agir):

```java
if (!reservas.containsKey(assento)) {      // duas threads veem "livre"...
    reservas.put(assento, cliente);        // ...e as duas reservam: overbooking
}
```

## Problema 2: visibilidade

Por desempenho, cada núcleo da CPU tem caches, e o compilador JIT pode manter valores em registradores. Sem sincronização, **não há garantia de que uma thread veja o que outra escreveu**:

```java
class Tarefa implements Runnable {
    private boolean parar = false;          // sem volatile

    public void run() {
        while (!parar) { processar(); }     // pode NUNCA ver o parar = true
    }
    void solicitarParada() { parar = true; }
}
```

Esse laço pode rodar para sempre: o JIT pode "otimizar" a leitura de `parar` para fora do laço.

## Problema 3: ordenação

O compilador e a CPU podem **reordenar** instruções que não dependem entre si. Numa thread só, isso é invisível; entre threads, outra thread pode ver os efeitos "fora de ordem" — por exemplo, ver um objeto publicado antes de os campos terem sido inicializados.

## O Java Memory Model e o "happens-before"

O **Java Memory Model** (JMM) define quando uma escrita é garantidamente visível a outra thread, pela relação **happens-before**. As principais:

- liberar um lock (`synchronized`, `Lock.unlock`) *happens-before* adquirir o mesmo lock depois;
- escrever num campo `volatile` *happens-before* ler esse campo;
- `Thread.start()` *happens-before* qualquer ação da thread iniciada; tudo na thread *happens-before* o `join()` retornar;
- campos `final` inicializados no construtor são visíveis depois que o objeto é publicado corretamente.

## `volatile`: visibilidade, não atomicidade

```java
private volatile boolean parar = false;    // resolve o laço infinito acima
```

`volatile` garante que **toda leitura veja a última escrita** e impede reordenações ao redor. É ideal para **flags** escritas por uma thread e lidas por outras. Mas:

```java
private volatile long total;
void incrementar() { total++; }            // CONTINUA com race condition!
```

Ler-somar-escrever continua sendo três passos. Para isso, você precisa de **atomicidade**: `synchronized`, `Lock` ou tipos atômicos — a próxima aula.

<Callout tipo="atencao" titulo="O risco escondido nos beans do Spring">
Beans do Spring são **singletons** por padrão: uma instância para todas as requisições. Um atributo mutável num `@Service` (um contador, uma lista "de trabalho", um `SimpleDateFormat`) é compartilhado por todas as threads. Regra de ouro: **services stateless**; estado vai para variáveis locais, para o banco ou para estruturas thread-safe.
</Callout>

## A melhor sincronização é não precisar dela

- **Imutabilidade**: objetos imutáveis (records, `String`, `BigDecimal`) podem ser compartilhados sem nenhum cuidado.
- **Confinamento**: dados que só uma thread acessa (variáveis locais) não precisam de sincronização.
- **Estruturas prontas**: `ConcurrentHashMap`, `AtomicLong`, filas concorrentes.

<Callout tipo="entrevista">
"O que é uma race condition?" e "o que `volatile` faz?" são perguntas clássicas. A resposta que impressiona separa **visibilidade** de **atomicidade**: "`volatile` resolve visibilidade, mas `x++` num volatile continua com race condition, porque são três operações". E cite o risco prático: estado mutável em beans singleton.
</Callout>

## Resumo

- Todo backend é concorrente: cada requisição roda em uma thread, sobre os mesmos objetos.
- Três problemas: **atomicidade** (race condition, check-then-act), **visibilidade** e **ordenação**.
- O JMM define as garantias via *happens-before* (locks, volatile, start/join, final).
- `volatile` = visibilidade, **não** atomicidade.
- Prefira imutabilidade, confinamento e estruturas thread-safe; services stateless.
