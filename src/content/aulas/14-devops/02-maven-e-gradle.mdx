Desde o módulo 0 você roda `mvn test`. Agora é hora de entender o que acontece por trás desse comando, porque é exatamente ele que o pipeline de CI (aula 4) e o `Dockerfile` (aula 3) vão executar. Um build confiável é o primeiro degrau da entrega contínua: **o mesmo comando, com as mesmas versões, na sua máquina e no servidor**.

**Pré-requisitos:** ter rodado os testes dos módulos anteriores com Maven e conhecer os starters do Spring Boot (módulo 8).

## Intuição: uma linha de montagem

O Maven é uma linha de montagem com estações fixas, sempre na mesma ordem. Você não diz *como* compilar; diz **até qual estação** quer chegar, e ele passa por todas as anteriores. Os **plugins** são as ferramentas presas a cada estação.

```bash
mvn compile            # validate + compile
mvn test               # ... + testes unitários
mvn package            # ... + gera o jar em target/
mvn verify             # ... + testes de integração e checagens
mvn clean verify       # apaga target/ antes (o clean é outro ciclo de vida)

mvn -B verify          # no CI: modo batch, log limpo
mvn -pl m14-devops/solucao -am verify   # só um módulo (e o que ele precisa)
mvn dependency:tree    # de onde veio cada biblioteca
```

Fuja do `-DskipTests` como hábito: um jar que ninguém testou é o jeito mais rápido de levar um bug para produção.

## Dependências: escopos, BOM e dependencyManagement

| Escopo | Compila? | Testes? | Vai no jar final? | Exemplo |
|---|---|---|---|---|
| `compile` (padrão) | sim | sim | sim | `spring-boot-starter-webmvc` |
| `provided` | sim | sim | não (o ambiente fornece) | API de servlet num WAR |
| `runtime` | não | sim | sim | driver JDBC do PostgreSQL |
| `test` | só os testes | sim | não | JUnit, AssertJ, Testcontainers |

Escolher versões à mão para 60 bibliotecas que precisam funcionar juntas é receita de conflito. Um **BOM** (*bill of materials*) resolve: é um pom que só contém `dependencyManagement` com versões testadas em conjunto. O `trilha-spring-parent` deste curso importa o do Spring Boot:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>   <!-- 4.1.1 -->
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

E o módulo declara as dependências **sem versão**, como no `pom.xml` do módulo 14:

```xml
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>   <!-- versão vem do BOM -->
</dependency>
<dependency>
  <groupId>org.yaml</groupId>
  <artifactId>snakeyaml</artifactId>
  <scope>test</scope>
</dependency>
```

A diferença que cai em entrevista: `dependencies` **adiciona** a biblioteca; `dependencyManagement` só **decide a versão** caso alguém a declare. Quando duas bibliotecas trazem versões diferentes de uma mesma dependência transitiva, o Maven escolhe a mais **próxima** da raiz na árvore (*nearest wins*), não a mais nova; o BOM evita a surpresa.

## Multi-módulo e parent

O diretório `java/` deste repositório é um projeto **multi-módulo**: um `pom.xml` agregador lista os módulos, e um *parent* concentra configurações comuns (versão do Java, BOM, plugins).

```xml
<!-- pom agregador: packaging pom -->
<packaging>pom</packaging>
<modules>
  <module>spring-parent</module>
  <module>m14-devops/solucao</module>
  <!-- ... -->
</modules>
```

**Agregação** (`<modules>`) diz o que construir junto; **herança** (`<parent>`) diz de onde vêm as configurações. Muitas vezes o mesmo pom faz as duas coisas, mas são conceitos separados. Na Fintech Core real, um multi-módulo típico separa `dominio`, `aplicacao` e `api`, e o Maven os constrói na ordem das dependências.

## Maven Wrapper

```bash
mvn wrapper:wrapper        # gera mvnw, mvnw.cmd e .mvn/wrapper/maven-wrapper.properties
./mvnw -B verify           # Linux/macOS (no Windows: mvnw.cmd)
```

Commite os três. Quem clona o projeto (e o CI) usa a **mesma versão do Maven**, baixada automaticamente, sem instalar nada. O projeto gerado pelo start.spring.io já vem com o wrapper.

## Surefire × Failsafe

| | Surefire | Failsafe |
|---|---|---|
| Para | testes unitários | testes de integração |
| Nomes (padrão) | `*Test`, `Test*`, `*Tests`, `*TestCase` | `IT*`, `*IT`, `*ITCase` |
| Fase | `test` | `integration-test`, e reprova em `verify` |
| Numa falha | reprova ao fim da fase `test`; nada depois roda | deixa `post-integration-test` derrubar o ambiente, depois reprova |

O Surefire vem ativo por padrão; o Failsafe precisa ser declarado com os goals `integration-test` e `verify`. Com essa separação, `mvn test` fica rápido para o dia a dia e `mvn verify` roda tudo. Muitos projetos Spring Boot com Testcontainers (módulo 10) rodam tudo no Surefire mesmo, e funciona: a separação vale quando os testes de integração ficam lentos.

## O jar executável: spring-boot-maven-plugin

O `maven-jar-plugin` gera um jar só com as **suas** classes. Para rodar com `java -jar`, o Spring Boot precisa de um jar com as dependências dentro e um lançador. Quem faz isso é o goal `repackage`:

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <executions>
        <execution>
          <goals><goal>repackage</goal></goals>   <!-- ligado à fase package -->
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
```

Com o `spring-boot-starter-parent` como parent, essa execução já vem configurada; com um parent próprio (como o deste curso), declare-a. Se o módulo tiver mais de uma classe com `main` (o módulo 14 tem três aplicações de exercício), informe qual usar em `<configuration><mainClass>…</mainClass></configuration>`. O resultado, `target/app.jar`, é o que o `Dockerfile` da próxima aula copia. O mesmo plugin tem o goal `build-image`, que gera uma imagem OCI sem `Dockerfile`.

## O mesmo projeto em Gradle

O Gradle usa um script (Kotlin DSL ou Groovy) em vez de XML, tem build incremental e cache de tarefas, e é o padrão no Android. Nos projetos Spring de backend, os dois são comuns; saiba ler ambos.

| Maven | Gradle |
|---|---|
| `compile` / `test` (fases) | `compileJava` / `test` (tarefas) |
| `package` | `assemble` (`jar` e `bootJar`) |
| `verify` | `check` / `build` |
| `install` | `publishToMavenLocal` (plugin `maven-publish`) |
| escopo `compile` / `runtime` / `test` | `implementation` / `runtimeOnly` / `testImplementation` |
| BOM com `scope import` | `platform(...)` |
| `mvnw` | `gradlew` |

## Armadilhas comuns

- **Versão fixada à mão por cima do BOM**: um `<version>` no módulo sobrescreve a versão testada pelo Spring Boot e pode quebrar em tempo de execução (`NoSuchMethodError`).
- **Driver JDBC com escopo `compile`**: funciona, mas deixa o código depender da implementação; `runtime` é o escopo certo.
- **`mvn install` no CI**: gasta tempo copiando para um `~/.m2` descartável. Use `verify`.
- **Jar sem `repackage`**: `java -jar` responde "no main manifest attribute" (não há `Main-Class` no manifesto).
- **Commitar sem o wrapper**: o CI usa uma versão do Maven, você outra, e o build "funciona na minha máquina".

## Resumo

- O Maven é um **ciclo de vida** de fases (validate → compile → test → package → verify → install); cada fase roda as anteriores.
- **BOM** + `dependencyManagement` fixam versões compatíveis; declare dependências sem versão e com o **escopo** certo.
- **Multi-módulo**: agregação (`<modules>`) e herança (`<parent>`) são coisas diferentes.
- **Wrapper** (`mvnw`) fixa a versão do Maven; **`mvn -B verify`** é o comando do CI.
- **Surefire** roda `*Test`; **Failsafe** roda `*IT` e reprova em `verify`.
- O **spring-boot-maven-plugin** (`repackage`) gera o jar executável; no Gradle, `bootJar`.
