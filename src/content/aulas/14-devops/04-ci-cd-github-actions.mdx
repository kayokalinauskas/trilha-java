Você já tem um build reproduzível (aula 2) e uma imagem (aula 3). Falta tirar o humano do caminho: **toda mudança** deve ser compilada, testada e empacotada **automaticamente**, do mesmo jeito, antes de qualquer pessoa aprovar o merge. É isso que um pipeline faz.

**Pré-requisitos:** as aulas 1 a 3 deste módulo e os testes com Testcontainers do módulo 10.

## Intuição: a esteira com inspeção

Numa fábrica, cada peça passa por pontos de inspeção automáticos antes de chegar à embalagem; uma peça com defeito é barrada cedo, quando é barato consertar. O pipeline é a esteira: o PR só pode entrar na `main` se passar pelas inspeções (compilar, testar, empacotar), e só vai para produção se passar pelas seguintes.

## CI, entrega contínua e deploy contínuo

| Prática | O que garante | Quem aperta o botão de produção |
|---|---|---|
| **Integração contínua (CI)** | cada mudança é integrada na `main` e verificada (build + testes) | ninguém; CI não faz deploy |
| **Entrega contínua** (*continuous delivery*) | a `main` está **sempre pronta** para produção; o deploy é um clique | uma pessoa, quando o negócio quiser |
| **Deploy contínuo** (*continuous deployment*) | todo commit que passa no pipeline **vai** para produção | ninguém: é automático |

A sigla **CD** serve para as duas últimas; na entrevista, deixe claro de qual está falando.

## Anatomia de um workflow

Um **workflow** é um arquivo YAML em `.github/workflows/`. O do exercício 14.04 (`entrega/ci.yml`):

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: "25"
          cache: maven

      - name: Testes e empacotamento
        run: mvn -B verify

      - name: Imagem Docker
        run: docker build -f entrega/Dockerfile -t trilha-m14:${{ github.sha }} .
```

| Peça | Papel |
|---|---|
| `on` | os **eventos** que disparam: push na `main` e qualquer pull request |
| `jobs.build` | um **job**: roda numa máquina virtual nova (`runs-on: ubuntu-latest`) |
| `steps` | executados **em sequência**; `uses` chama uma *action* pronta, `run` executa um comando |
| `actions/checkout@v5` | baixa o código do repositório (sem ele, a máquina está vazia) |
| `actions/setup-java@v5` | instala o Temurin 25 e, com `cache: maven`, guarda o `~/.m2` entre execuções (chave pelo hash dos `pom.xml`) |
| `mvn -B verify` | compila, roda **todos** os testes (os com Testcontainers também: o runner Ubuntu tem Docker) e empacota |
| `${{ github.sha }}` | uma **expressão**: o hash do commit vira a tag da imagem, rastreável até o código |

Detalhes que valem ouro:

- `java-version: "25"` vai **entre aspas**. Sem elas, um valor como `21.10` seria lido como número, e não como texto.
- Fixe as actions numa versão (`@v5`). Para rigor máximo, times fixam o **hash do commit** da action, porque uma tag pode ser movida.
- Jobs diferentes rodam **em paralelo** e em máquinas separadas; use `needs: build` para criar ordem e passe arquivos entre eles com artefatos ou pelo registro de imagens.

<Callout tipo="info" titulo="Curiosidade: a chave on vira true">
O teste do exercício lê o `ci.yml` com o **SnakeYAML**, que implementa o YAML 1.1. Nessa versão da especificação, `on`, `off`, `yes` e `no` sem aspas são **booleanos**: a chave `on:` é lida como `true`. O GitHub trata o arquivo corretamente, mas qualquer ferramenta sua que leia workflows precisa lembrar disso (o teste procura `"on"` e, se não achar, `Boolean.TRUE`).
</Callout>

## Segredos e permissões

```yaml
permissions:
  contents: read          # o GITHUB_TOKEN só lê o repositório
  packages: write         # ... e pode publicar no GitHub Container Registry

jobs:
  publicar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - name: Login no registro
        run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
      - name: Push
        run: |
          docker build -t ghcr.io/minha-org/fintech-core:${{ github.sha }} .
          docker push ghcr.io/minha-org/fintech-core:${{ github.sha }}
```

- **Segredos** são cadastrados nas configurações do repositório (ou da organização, ou de um *environment*) e lidos com `secrets.NOME`. O GitHub mascara o valor nos logs, mas não conte com isso: nunca faça `echo` de um segredo.
- Pull requests vindos de **forks** não recebem os segredos do repositório: um estranho não pode abrir um PR que imprime as suas chaves.
- Dê ao `GITHUB_TOKEN` o **mínimo** de `permissions`. Em nuvem, prefira **OIDC** (o workflow troca um token temporário por credenciais do provedor) a guardar chaves de longa duração como segredo.

## Matriz

Para testar em mais de uma versão ou sistema, uma **matriz** gera um job por combinação:

```yaml
jobs:
  build:
    strategy:
      matrix:
        java: ["21", "25"]
        os: [ubuntu-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-java@v5
        with: { distribution: temurin, java-version: "${{ matrix.java }}", cache: maven }
      - run: mvn -B verify
```

Faz sentido em **bibliotecas** que precisam funcionar em vários ambientes. Um serviço que roda só numa imagem com Java 25 não precisa de matriz: ela só gasta minutos de CI.

## Proteção de branch

O pipeline só protege se for **obrigatório**. Nas configurações do repositório (*branch protection rules* ou *rulesets*), para a `main`:

- exigir **pull request** com pelo menos uma aprovação;
- exigir que os **status checks** (o job `build`) passem antes do merge;
- bloquear **push direto** e **force push**.

## Deploy: ambientes, aprovação e rollback

```yaml
  deploy-producao:
    needs: publicar
    runs-on: ubuntu-latest
    environment: producao        # regras do environment: revisores obrigatórios, segredos próprios
    steps:
      - run: kubectl set image deployment/fintech-core app=ghcr.io/minha-org/fintech-core:${{ github.sha }}
```

Um **environment** no GitHub (homologação, produção) pode exigir **aprovação** de pessoas específicas, restringir quais branches fazem deploy nele e ter **segredos próprios**: a credencial de produção só existe para o job que passou pela aprovação.

**Rollback** é voltar a rodar a imagem anterior, e fica fácil porque cada imagem tem a tag do commit: basta implantar o `sha` anterior. O que complica o rollback é o **banco**: se a versão nova removeu uma coluna, a antiga não funciona mais. Por isso, migrações seguem o padrão **expand/contract**: primeiro só adicione, publique o código que convive com os dois formatos, e remova o que sobrou num deploy posterior.

| Estratégia | Como funciona | Rollback | Custo |
|---|---|---|---|
| **Rolling update** | troca as instâncias aos poucos (padrão do Kubernetes) | novo rolling para a versão anterior | baixo |
| **Blue-green** | dois ambientes completos; o tráfego vira de uma vez para o novo | virar o tráfego de volta, em segundos | dobro de infraestrutura durante a troca |
| **Canary** | a versão nova recebe uma fração pequena do tráfego e cresce se as métricas estiverem boas | tirar o canário | exige métricas e roteamento por peso |

**Feature flags** completam o quadro: o código vai para produção desligado (*deploy*), e a funcionalidade é ligada depois (*release*), para uma parte dos clientes ou para todos, sem novo deploy.

## Armadilhas comuns

- **Pipeline lento** (20 minutos por PR): o time para de esperar e começa a mesclar sem ver o resultado. Use cache, paralelize jobs e mantenha os testes rápidos.
- **Testes instáveis** (*flaky*) ignorados com "roda de novo": em pouco tempo ninguém confia no vermelho. Corrija ou isole o teste.
- **Pipeline opcional**: sem proteção de branch, o botão de merge funciona mesmo com o CI vermelho.
- **Segredo impresso no log** ou passado como argumento de linha de comando.
- **Deploy de `latest`**: não há como saber o que está rodando, nem para onde voltar.
- **Migração destrutiva junto com o código novo**: o rollback deixa de ser possível.

## Resumo

- **CI** verifica cada mudança; **entrega contínua** deixa a main sempre publicável; **deploy contínuo** publica sozinho.
- Workflow = **eventos** (`on`) → **jobs** (máquinas, em paralelo, `needs` para ordem) → **steps** (`uses` ou `run`).
- `actions/checkout@v5`, `actions/setup-java@v5` (`temurin`, `"25"`, `cache: maven`) e `mvn -B verify`; imagem com a tag do commit.
- **Segredos** com permissões mínimas; **matriz** para bibliotecas; **proteção de branch** torna o pipeline obrigatório.
- **Environments** com aprovação; **rollback** pela tag anterior; migrações **expand/contract**; rolling, **blue-green** e **canary**.
