Chegou a hora de a imagem da aula 3 rodar em produção. Na maioria das empresas, isso significa **Kubernetes** (ou um serviço de containers de um provedor de nuvem) e bancos, filas e armazenamento **gerenciados**. Você não precisa ser especialista em infraestrutura, mas precisa saber ler um manifesto, entender por que o seu Pod foi reiniciado e conversar com o time de plataforma na mesma língua.

**Pré-requisitos:** a imagem Docker (aula 3) e as probes do Actuator (aula 5).

## Intuição: o gerente do restaurante

Você não diz ao Kubernetes "suba o container no servidor 3". Você declara o **estado desejado**: "quero 3 cópias desta imagem, cada uma com meio núcleo e 768 MB, atrás deste endereço". O Kubernetes é o gerente que fica olhando o salão: se um garçom passa mal, chama outro; se o movimento aumenta, escala mais gente. Esse ciclo de comparar o desejado com o real e corrigir a diferença é o **laço de reconciliação**, e é a ideia central do Kubernetes.

| Objeto | Para que serve |
|---|---|
| **Pod** | a menor unidade: um (ou mais) containers com um IP. Descartável: morre e é substituído por outro, com outro IP |
| **Deployment** | declara a imagem e o número de réplicas; recria Pods que morrem e faz o **rolling update** |
| **Service** | nome DNS e IP estáveis para um conjunto de Pods (escolhidos por *labels*); só encaminha para os **prontos** |
| **Ingress** | entrada HTTP do cluster: roteia por host e caminho (`api.fintech.com/pagamentos`) e termina o TLS. O **Gateway API** é a evolução mais recente desse papel |
| **ConfigMap** | configuração não sensível, injetada como variáveis de ambiente ou arquivos |
| **Secret** | configuração sensível (senhas, tokens). Os valores ficam em **base64, que não é criptografia**: ative criptografia em repouso, restrinja por RBAC ou use um cofre externo |

## Um Deployment de verdade

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fintech-core
spec:
  replicas: 3
  selector:
    matchLabels: { app: fintech-core }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # sobe um novo antes de derrubar um antigo
  template:
    metadata:
      labels: { app: fintech-core }
    spec:
      containers:
        - name: app
          image: ghcr.io/minha-org/fintech-core:3f9c2a1      # tag do commit, nunca latest
          ports: [{ containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: fintech-core-config }    # SPRING_DATASOURCE_URL etc.
          env:
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef: { name: fintech-core-db, key: senha }
          resources:
            requests: { cpu: 500m, memory: 768Mi }
            limits: { memory: 768Mi }
          startupProbe:                       # dá tempo para a JVM subir antes da liveness valer
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 2
            failureThreshold: 30
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
```

### Requests, limits e a JVM

- **`requests`** é a reserva: o agendador só coloca o Pod num nó com essa capacidade livre, e o HPA calcula o uso em relação a ela.
- **`limits`** é o teto. Acima do limite de **memória**, o container é morto (**OOMKilled**, sem `OutOfMemoryError` no log). Acima do limite de **CPU**, ele é estrangulado (*throttling*) e fica lento. Por isso, muitos times definem limite só de memória, igual ao request, e deixam a CPU sem teto; é uma decisão do time de plataforma.
- A JVM lê o limite do container: com 768 Mi e o `-XX:MaxRAMPercentage=75.0` do Dockerfile, o heap máximo fica em torno de 576 MB, e o resto sobra para metaspace, threads e buffers.

### Probes e o ciclo de vida

As probes chamam os endpoints da aula 5. **Liveness** falhando `failureThreshold` vezes seguidas: o container é reiniciado. **Readiness** falhando: o Pod sai do Service, sem reinício. A **startupProbe** segura as outras duas até a aplicação subir, para uma inicialização lenta não ser confundida com um processo travado.

No deploy (ou quando um nó é esvaziado), o Kubernetes manda `SIGTERM` ao container e espera `terminationGracePeriodSeconds` (30 s por padrão) antes do `SIGKILL`. Com o `ENTRYPOINT` em formato exec, o Spring Boot recebe o sinal e faz o desligamento gracioso. Como a remoção do Pod do Service acontece em paralelo, a documentação do Spring Boot sugere um pequeno `preStop` (uma pausa de alguns segundos) para não receber requisições novas depois de começar a desligar.

### Rolling update e HPA

O **rolling update** troca os Pods aos poucos: com `maxSurge: 1` e `maxUnavailable: 0`, ele sobe um Pod novo, espera a **readiness** passar e só então derruba um antigo. Uma versão que nunca fica pronta trava o rollout sem derrubar o serviço, e `kubectl rollout undo deployment/fintech-core` volta à versão anterior.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: fintech-core
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: fintech-core }
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }   # 70% dos requests de CPU
```

Escalar **horizontalmente** só funciona se a aplicação for **sem estado**: sessão, cache local e arquivos temporários não podem ser a única cópia de nada.

## Os 12 fatores

A metodologia *The Twelve-Factor App* resume o que torna uma aplicação boa para esse mundo. Os fatores que mais aparecem no dia a dia de um dev Spring:

| Fator | Na prática com Spring Boot |
|---|---|
| III. **Config** no ambiente | `SPRING_DATASOURCE_URL` via ConfigMap/Secret; a mesma imagem em todos os ambientes |
| IV. **Serviços de apoio** como recursos anexados | o banco e a fila são URLs; trocar de instância é mudar configuração |
| V. **Build, release, run** separados | o CI gera a imagem (build); imagem + config = release; o cluster executa (run) |
| VI. **Processos sem estado** | nada de sessão em memória; estado no banco ou no Redis |
| IX. **Descartabilidade** | sobe rápido, desliga graciosamente com `SIGTERM` |
| X. **Paridade** dev/prod | o mesmo PostgreSQL no Compose, no Testcontainers e em produção, nunca H2 em um e Postgres no outro |
| XI. **Logs** como fluxo de eventos | JSON no stdout; quem coleta e guarda é a plataforma, não a aplicação |

Os outros são: I. uma **base de código** versionada, II. **dependências** declaradas, VII. **vínculo de porta** (a aplicação expõe o próprio HTTP), VIII. **concorrência** por processos (escala adicionando instâncias) e XII. **tarefas administrativas** como processos pontuais (uma migração roda como job, não à mão no servidor).

## Cloud: os serviços que aparecem em toda vaga

| Necessidade | AWS | GCP | Azure |
|---|---|---|---|
| Kubernetes gerenciado | EKS | GKE | AKS |
| Containers sem gerenciar cluster | ECS (com Fargate) | Cloud Run | Container Apps |
| PostgreSQL gerenciado | RDS (e Aurora) | Cloud SQL | Azure Database for PostgreSQL |
| Armazenamento de objetos | S3 | Cloud Storage | Blob Storage |
| Fila | SQS | Pub/Sub | Service Bus (filas) |
| Publicação para vários assinantes | SNS | Pub/Sub | Service Bus (tópicos) / Event Grid |
| Kafka gerenciado | MSK | Managed Service for Apache Kafka | Event Hubs (compatível com Kafka) |
| Registro de imagens | ECR | Artifact Registry | Container Registry (ACR) |
| Segredos | Secrets Manager | Secret Manager | Key Vault |
| Logs e métricas | CloudWatch | Cloud Logging / Monitoring | Azure Monitor |

**Gerenciado × auto-hospedado.** Rodar o PostgreSQL você mesmo, numa VM ou no Kubernetes, parece mais barato na fatura, mas backup, atualização de versão, réplica, failover e o plantão da madrugada passam a ser do seu time. Para a maioria das empresas, o serviço gerenciado (RDS, Cloud SQL) sai mais barato no custo total. Auto-hospedar faz sentido com requisitos muito específicos, escala enorme ou equipe dedicada.

**Custo** é requisito de arquitetura. Os vilões mais comuns: recursos esquecidos ligados (ambientes de teste que ninguém desliga), `requests` superdimensionados, tráfego de saída entre regiões ou para a internet, volume de logs em `DEBUG` e réplicas de banco sem uso. Saber estimar a ordem de grandeza do custo de uma decisão é uma habilidade de pleno.

## O que é seu e o que é da plataforma

| Normalmente do dev (Jr/Pleno) | Normalmente do time de plataforma/SRE |
|---|---|
| Dockerfile, imagem enxuta e sem root | criar e atualizar o cluster, rede, nós |
| endpoints de health e as probes certas | Ingress controller, certificados, DNS |
| requests e limits coerentes com a JVM | políticas de segurança, RBAC, cotas |
| config por variáveis, sem segredo na imagem | o cofre de segredos e a rotação |
| logs em JSON, métricas e traces | a pilha de observabilidade (Prometheus, Grafana, coletor OTel) |
| ler `kubectl get pods`, `describe`, `logs` e entender um `CrashLoopBackOff` | templates de pipeline, Helm charts ou GitOps compartilhados |

A fronteira varia: em empresas pequenas, você faz as duas colunas; em grandes, a plataforma entrega um "caminho pavimentado" e você preenche um arquivo de valores. Em qualquer caso, a coluna da esquerda é sua.

## Armadilhas comuns

- **Banco na liveness**: uma instabilidade no RDS reinicia todos os Pods ao mesmo tempo.
- **Sem startupProbe e liveness agressiva**: a JVM ainda está subindo, a liveness falha, o Pod é reiniciado, e o ciclo se repete (`CrashLoopBackOff`).
- **Limite de memória menor que o heap** (`-Xmx` fixo): OOMKilled sem mensagem de erro na aplicação.
- **Secret tratado como cofre**: base64 se decodifica com um comando.
- **Estado local** (upload em disco, sessão em memória): some quando o Pod é recriado e diverge entre réplicas.
- **Tudo auto-hospedado para economizar**: a economia some no primeiro incidente de banco sem backup testado.

## Resumo

- **Pod** (descartável) → **Deployment** (réplicas, rolling update) → **Service** (endereço estável) → **Ingress** (entrada HTTP); **ConfigMap** e **Secret** (base64 não é criptografia) para configuração.
- **Requests** reservam, **limits** limitam (memória: OOMKilled; CPU: throttling); a JVM segue o limite com `MaxRAMPercentage`.
- **Probes** no Actuator: startup, liveness (sem dependências externas) e readiness; `SIGTERM` + desligamento gracioso.
- **HPA** escala réplicas; só funciona com aplicação **sem estado**.
- **12 fatores**: config no ambiente, processos sem estado, descartabilidade, paridade, logs no stdout.
- Nuvem: EKS/GKE/AKS, RDS/Cloud SQL, S3, SQS/SNS; prefira **gerenciado**; custo é requisito.
